Практика 14. Управление автоматизацией в сложных проектах.

ЭТА ПРАКТИКА — ПРО УПРАВЛЕНИЕ ПАРКОМ, А НЕ ПРО НАСТРОЙКУ ОДНОЙ
МАШИНЫ. Роль web_admin из практики 10 станет проектом: точка входа,
три плейбука, два окружения, отчёт о парке на управляющей машине
и обновление боевого парка по одной машине. Разберём, чем статическое
включение отличается от динамического и почему это видно на тегах.

=========================================================================
ЧТО МЫ СДЕЛАЕМ
=========================================================================

Соберём проект из каталогов — site.yml, playbooks/, inventory/,
group_vars/, tasks/ и roles/ — и разберём, почему «всё в одном файле»
перестаёт работать. Разберём import_playbook, import_tasks
и include_tasks, import_role и include_role: что Ansible разбирает
при загрузке, а что во время прогона, и как это отражается на тегах,
условиях и выводе --list-tasks. Поставим опыт: один и тот же файл
задач включим двумя способами и посмотрим на разницу.

Научим проект трём вещам, которых не было в практике 10: собирать
отчёт о парке в один файл на управляющей машине (delegate_to
и run_once), обновлять машины партиями (serial) и жить в двух
окружениях одним и тем же site.yml — dev и prod.

=========================================================================
ШАГ 1. ИЗ ЧЕГО СОСТОИТ ПРОЕКТ И ПОЧЕМУ НЕ «ВСЁ В ОДНОМ ФАЙЛЕ»
=========================================================================

В практике 10 проект состоял из одного play и роли. Задач теперь
больше: веб-часть, сервер баз данных, отчёт, два окружения. В одном
файле это три сотни строк, где работы переплетены.

  14_complex_projects/
  ├── ansible.cfg                 настройки Ansible для проекта
  ├── site.yml                    точка входа: только import_playbook
  ├── inventory/
  │   ├── dev.ini                 окружение dev: группа dev
  │   └── prod.ini                окружение prod: группа prod
  ├── group_vars/
  │   ├── all/
  │   │   ├── vars.yml            переменные всех машин проекта
  │   │   └── vault.yml.example   образец файла секретов
  │   ├── dev.yml                 переменные окружения dev
  │   └── prod.yml                переменные окружения prod
  ├── playbooks/
  │   ├── webservers.yml          веб-часть: роль web_admin, serial
  │   ├── db.yml                  настройка db1 (Rocky Linux 10)
  │   └── report.yml              отчёт о парке на управляющей машине
  ├── tasks/
  │   └── common_checks.yml       общие проверки машины
  └── roles/
      └── web_admin/              копия роли из практики 10

Каталога reports/ в проекте нет: его создаёт задача из report.yml
при первом прогоне. Настройки проекта — файл ansible.cfg:

  # ansible.cfg — настройки Ansible для проекта практики 14.
  # Инвентаря по умолчанию нет: окружение выбирается ключом -i,
  # а команды выполняются из каталога проекта.

  [defaults]
  host_key_checking = False
  remote_user = engineer
  interpreter_python = auto_silent
  stdout_callback = default
  callback_result_format = yaml
  forks = 10
  roles_path = ./roles
  # Автоинъекция фактов: короткие имена вида ansible_os_family объявлены
  # устаревшими и удаляются в ansible-core 2.24, поэтому она выключена.
  # Факты доступны только через словарь: ansible_facts['os_family'].
  inject_facts_as_vars = false

ПОЧЕМУ ИМЕННО ТАК: инвентаря по умолчанию нет, потому что у проекта
два равноправных окружения: забытый ключ -i молча настроил бы dev там,
где имели в виду prod. Параметр roles_path пригодится, когда плейбук
из playbooks/ запускают отдельно от точки входа.

ЧЕГО НЕ ДЕЛАТЬ: не копируйте плейбук под каждую группу машин:
в прежней версии курса файл «Install Apache and upload WebSite» лежал
в шести копиях.

=========================================================================
ШАГ 2. SITE.YML: ТОЧКА ВХОДА НА IMPORT_PLAYBOOK
=========================================================================

В точке входа нет задач: только включения плейбуков.

  ---
  # site.yml — точка входа проекта практики 14: только включения
  # плейбуков, ни одной задачи. Порядок включений — порядок работы.
  # Окружение выбирается ключом -i, сам файл от него не зависит.
  # Ключ import_playbook записан коротко, как в документации Ansible:
  # это ключ плейбука, а не модуль. Полное имя —
  # ansible.builtin.import_playbook, принимаются оба варианта.

  - name: Настроить веб-часть стенда
    import_playbook: playbooks/webservers.yml

  - name: Настроить сервер баз данных
    import_playbook: playbooks/db.yml

  - name: Собрать отчёт о парке машин
    import_playbook: playbooks/report.yml

Ansible читает указанный файл при разборе точки входа и подставляет
его plays на это место: порядок plays остаётся тем, в котором стоят
включения.

ПОЧЕМУ ИМЕННО ТАК: плейбук нельзя включить динамически. Для файла
задач есть include_tasks, для роли — include_role, а динамического
включения плейбука в Ansible нет: только import_playbook.

ВАЖНО: import_playbook — не задача: его нельзя поставить внутрь tasks,
завернуть в loop или пометить тегом. Теги, serial и условия задаются
в самих включаемых плейбуках.

ПРОВЕРКА: до запуска убедимся, что файлы разбираются:

  ansible-playbook --syntax-check site.yml -i inventory/dev.ini

Команда молчит. Вывод Ansible в этой практике напечатан сокращённо,
звёздочки после имени задачи и символ табуляции опущены.

=========================================================================
ШАГ 3. IMPORT_TASKS И INCLUDE_TASKS: ОДИН ФАЙЛ ДВУМЯ СПОСОБАМИ
=========================================================================

Общие проверки машины лежат в отдельном файле
tasks/common_checks.yml:

  ---
  # tasks/common_checks.yml — общие проверки машины.
  #
  # Один и тот же файл подключён в проекте тремя способами:
  #   * playbooks/webservers.yml — статически, ключом import_tasks;
  #   * playbooks/db.yml         — динамически, ключом include_tasks;
  #   * playbooks/report.yml     — статически, перед сбором отчёта.
  #
  # Файл ничего не меняет на машине: он читает факты и падает, если
  # машина не готова к работе проекта, поэтому повторный прогон не даёт
  # changed. Факты он собирает сам: при запуске с --tags сбор фактов
  # в play может не выполниться, если тег play не совпал с фильтром.

  - name: Собрать факты машины для проверок
    ansible.builtin.setup:
    tags:
      - checks
      - always

  - name: Проверить, что семейство ОС поддерживается проектом
    ansible.builtin.assert:
      that:
        - ansible_facts['os_family'] in supported_families
      fail_msg: >-
        Проект не умеет работать на семействе
        {{ ansible_facts['os_family'] }}: поддержаны
        {{ supported_families | join(', ') }}.
      success_msg: "Семейство {{ ansible_facts['os_family'] }} поддержано"
      quiet: true

  - name: Посчитать свободное место на корневом разделе
    ansible.builtin.set_fact:
      common_root_free_mb: "{{ ((ansible_facts['mounts'] | selectattr('mount', 'equalto', '/') | map(attribute='size_available') | list | first | default(0)) / 1024 / 1024) | round(0) | int }}"

  - name: Проверить, что на корневом разделе хватает места
    ansible.builtin.assert:
      that:
        - common_root_free_mb | int >= min_free_mb | int
      fail_msg: >-
        На {{ inventory_hostname }} свободно {{ common_root_free_mb }} МБ,
        а проекту нужно не меньше {{ min_free_mb }} МБ.
      success_msg: "Свободного места хватает: {{ common_root_free_mb }} МБ"
      quiet: true

  - name: Показать сводку по машине
    ansible.builtin.debug:
      msg: >-
        {{ inventory_hostname }}: {{ ansible_facts['distribution'] }}
        {{ ansible_facts['distribution_version'] }},
        ядро {{ ansible_facts['kernel'] }},
        свободно {{ common_root_free_mb }} МБ

Задачи ничего не меняют: они читают факты и останавливают прогон, если
машина не готова, поэтому проверки не портят changed=0.
Динамическое включение этого файла — в playbooks/db.yml:

  tasks:
    - name: Выполнить общие проверки машины
      ansible.builtin.include_tasks:
        file: ../tasks/common_checks.yml
        apply:
          tags:
            - checks
            - always
      when: common_checks_enabled | bool
      tags:
        - checks
        - always

Путь начинается с ../, потому что плейбуки лежат в playbooks/, а файл
задач — в tasks/. Кроме включения, в db.yml есть шапка play (hosts, db,
tags) и две простые задачи: каталог резервных копий и файл-описание.
Статическое включение того же файла написано в webservers.yml (шаг 4).

ТЕПЕРЬ ОПЫТ. Напишите динамическое включение без apply — так, как его
пишут по привычке, — и посмотрите на список задач:

  ansible-playbook --list-tasks site.yml -i inventory/dev.ini --tags checks

    play #1 (web): Веб-серверы: сайт, проверки и безопасное обновление
      TASK [Собрать факты машины для проверок]   TAGS: [always, checks, web]
      TASK [Проверить, что семейство ОС поддерживается проектом]
      TASK [Посчитать свободное место на корневом разделе]
      ...и ещё две задачи из файла
    play #2 (db): Сервер баз данных
      TASK [Выполнить общие проверки машины]     TAGS: [always, checks, db]

В play №1 файл разобран заранее: все пять задач стоят своими именами.
В play №2 только задача включения: что внутри файла, Ansible узнает
во время прогона.

ПОЧЕМУ ИМЕННО ТАК: apply передаёт теги задачам внутри включения.
Допишите его и повторите ту же команду — в play №2 появится всё
содержимое файла.

ВАЖНО: тег на динамическом включении не достаётся задачам внутри
файла: при запуске с --tags checks Ansible выполнит включение, а задачи
внутри, у которых тега checks нет, пропустит. Лечится это ключом apply
(наш вариант) или блоком с тегом вокруг включения.

ЧТО ОТЛИЧАЕТ СТАТИКУ ОТ ДИНАМИКИ: import_* разбирается при чтении
плейбука, include_* — во время прогона; параметры включения у import_*
достаются всем включённым задачам, у include_* — только включению;
задачи и теги include_* не видны в --list-tasks; when и loop возможны
только у include_*, а notify отдельного обработчика — только у import_*.

ПОЧЕМУ ИМЕННО ТАК: по умолчанию — статика. Она дешевле,
предсказуемее и видна в списках задач. Динамика нужна там, где без неё
не обойтись: включить файл по условию от предыдущей задачи или
выполнить его в цикле. В нашем проекте она стоит в одном месте —
в db.yml, где проверки выключаются переменной common_checks_enabled.

=========================================================================
ШАГ 4. IMPORT_ROLE И INCLUDE_ROLE: ТО ЖЕ РАЗЛИЧИЕ ДЛЯ РОЛЕЙ
=========================================================================

Веб-часть проекта — файл playbooks/webservers.yml целиком:

  ---
  # playbooks/webservers.yml — веб-часть проекта практики 14.
  # Здесь всё сделано статически: роль подключена ключом roles, общие
  # проверки — ключом import_tasks. Поэтому задачи видны в --list-tasks,
  # а тег на включении достаётся всем включённым задачам.
  # serial берётся из group_vars окружения: у dev это "100%", у prod — 1.

  - name: "Веб-серверы: сайт, проверки и безопасное обновление"
    hosts: web
    become: true
    gather_facts: true
    serial: "{{ update_serial | default(1) }}"
    max_fail_percentage: 0
    tags:
      - web

    roles:
      - role: web_admin

    tasks:
      - name: Выполнить общие проверки машины
        ansible.builtin.import_tasks: ../tasks/common_checks.yml
        tags:
          - checks
          - always

Ключ roles — тоже статическое включение: задачи роли появляются в play
до начала прогона, и тег web с play достаётся им всем. Динамический
вызов той же роли выглядит так:

  tasks:
    - name: Развернуть сайт только на Ubuntu
      ansible.builtin.include_role:
        name: web_admin
      when: ansible_facts['os_family'] == "Debian"

Тег и условие на include_role относятся к самому вызову, а не к задачам
роли. Свои особенности: include_role умеет tasks_from — вызвать,
например, tasks/checks.yml внутри роли (приём практики 15); параметры
роли через vars сильнее и defaults, и vars роли: выше них только
--extra-vars (практика 10).

ПОЧЕМУ ИМЕННО ТАК: роль вызывается ключом roles, потому что вызов
у нас один. Когда ролей станет несколько, удобнее станет import_role:
он позволяет задать параметры роли в вызове.

ПРОВЕРКА: убедимся, что роль нашлась:

  ansible-playbook --list-tasks site.yml -i inventory/dev.ini \
      | grep 'web_admin' | head -2
      TASK [web_admin : Проверить, что семейство ОС поддерживается ролью]
      TASK [web_admin : Взять имена пакетов и служб своего семейства ОС]

=========================================================================
ШАГ 5. ТЕГИ НА ВЕСЬ ПРОЕКТ: WEB, DB, REPORT, CHECKS, ALWAYS
=========================================================================

  * web, db, report — теги plays в трёх плейбуках: веб-часть, сервер
    баз данных, отчёт;
  * checks — тег файла проверок и обоих включений: одни проверки,
    без настройки машин;
  * always — второй тег файла проверок: проверки идут в любом прогоне.

  ansible-playbook --list-tags site.yml -i inventory/dev.ini

    play #1 (web): Веб-серверы: сайт, проверки и безопасное обновление
      TASK TAGS: [always, checks, web]
    play #2 (db): Сервер баз данных
      TASK TAGS: [always, checks, db]
    play #3 (linux): Собрать отчёт о парке машин
      TASK TAGS: [always, checks, report]

  ansible-playbook site.yml -i inventory/dev.ini --tags db
  ansible-playbook site.yml -i inventory/dev.ini --skip-tags report
  ansible-playbook site.yml -i inventory/dev.ini --tags all,never

Первая команда настроит только db1, вторая сделает всё, кроме отчёта.
Последняя нужна для тега never: так помечают задачи, которые не должны
запускаться по умолчанию. Пропуск сильнее: --skip-tags побеждает.

ПОЧЕМУ ИМЕННО ТАК: тег always у проверок — не украшение. Он делает
так, что проверки выполняются при любом фильтре: и с --tags web,
и с --tags db, и без фильтра. Тег always ставят на то, что обязано
выполниться всегда: проверку, сбор фактов, страховку перед работой.

ВАЖНО: тег — это фильтр, а не зависимость. Записав --tags report,
вы получите только отчёт: Ansible не станет «заодно» настраивать
машины.

ПРОВЕРКА: ansible-playbook site.yml -i inventory/dev.ini --tags db
--limit db1 покажет play «Сервер баз данных» и задачи проверок (тег
always), и ни одной задачи роли web_admin.

=========================================================================
ШАГ 6. DELEGATE_TO И RUN_ONCE: ОТЧЁТ О ПАРКЕ В ОДИН ФАЙЛ
=========================================================================

Отчёт о парке просят постоянно: версии ОС, ядра и свободное место
по всем машинам одной страницей. Собираем его на управляющей машине.

  ---
  # playbooks/report.yml — отчёт о парке машин.
  #
  # Отчёт собирается не на узлах, а на управляющей машине: файл должен
  # быть один. Ключ delegate_to: localhost выполняет задачу на control,
  # а run_once — один раз, хотя play идёт по всем машинам парка.
  #
  # serial в этом play не задан намеренно: run_once выполняется один раз
  # на партию, и с serial: 1 каждая партия переписала бы файл заново.
  #
  # Строку отчёта считает каждая машина про себя, а записывает её один
  # хост, поэтому в тексте перебираются hostvars всех машин.

  - name: Собрать отчёт о парке машин
    hosts: linux
    become: false
    gather_facts: true
    tags:
      - report

    tasks:
      - name: Выполнить общие проверки машины
        ansible.builtin.import_tasks: ../tasks/common_checks.yml
        tags:
          - checks
          - always

      - name: Собрать строку отчёта по своей машине
        ansible.builtin.set_fact:
          fleet_row: >-
            {{ inventory_hostname }} | {{ ansible_facts['distribution'] }}
            {{ ansible_facts['distribution_version'] }} |
            ядро {{ ansible_facts['kernel'] }} |
            свободно {{ common_root_free_mb }} МБ

      - name: Создать каталог для отчётов на управляющей машине
        ansible.builtin.file:
          path: "{{ report_dir }}"
          state: directory
          mode: "0755"
        delegate_to: localhost
        run_once: true

      - name: Записать отчёт одним файлом на управляющей машине
        ansible.builtin.copy:
          content: |
            # Отчёт о парке машин учебного стенда.
            # Файл собран задачей с delegate_to: localhost и run_once: true,
            # поэтому он один, а не по копии на каждой машине.
            fleet_report:
              machines_total: {{ groups['linux'] | length }}
              environment: "{{ report_title }}"
              machines:
            {%- for host in groups['linux'] | sort %}
                - {{ hostvars[host]['fleet_row'] | default(host ~ ': данных нет') }}
            {%- endfor %}
          dest: "{{ report_dir }}/{{ report_file }}"
          mode: "0644"
        delegate_to: localhost
        run_once: true

      - name: Показать, где лежит отчёт
        ansible.builtin.debug:
          msg: "Отчёт собран на управляющей машине: {{ report_dir }}/{{ report_file }}"
        run_once: true

Без delegate_to: localhost задача copy создала бы reports/fleet-report.txt
на web1, web2 и db1 — три файла вместо одного. RUN_ONCE выполняет
задачу один раз, хотя play идёт по всем машинам, и применяет результат
ко всей партии. HOSTVARS нужен потому, что текст отчёта собирает один
хост, а говорит он обо всём парке.

ПОЧЕМУ ИМЕННО ТАК: можно было собрать отчёт циклом из задач lineinfile
по строке на машину. Минусов два: строка дописывается, а устаревшую
удалять некому, и порядок строк случайный; шаблон в copy отдаёт ровно
то, что получилось из фактов, поэтому второй прогон даёт changed=0.

ВАЖНО: если делегировать задачу адресу, которого нет в инвентаре,
машина в инвентарь не попадёт: переменные у неё будут только из группы
all. Если такая машина нужна по-настоящему, её добавляют add_host.

ПРОВЕРКА: отчёт лежит на управляющей машине:

  ls -l ~/ansible-lab/14_complex_projects/reports/

=========================================================================
ШАГ 7. DELEGATE_FACTS: ЧЬИ ЭТО ФАКТЫ И ЧЬЯ ПЕРЕМЕННАЯ
=========================================================================

Делегирование не меняет того, чья это задача. Формулировка
из документации Ansible: покупки принадлежат вам, даже если домой
их привёз кто-то другой. Отсюда два следствия.

ПЕРВОЕ: аргументы задачи (dest, content) подставляются из переменных
того хоста, по которому идёт play, а служебные параметры подключения —
интерпретатор Python, connection, become, shell — берутся у того хоста,
которому задача делегирована. Нужен адрес исходной машины — берите
его явно:

  delegate_to: localhost
  vars:
    source_host: "{{ hostvars[inventory_hostname]['ansible_host'] }}"

inventory_hostname остаётся именем исходной машины, а одноимённые
переменные могут относиться уже к машине, которой задача делегирована.

ВТОРОЕ: факты, собранные делегированной задачей, Ansible записывает
исходной машине play, а не той, на которой задача выполнилась. Чтобы
факты достались делегированной машине, ставят delegate_facts: true:

  - name: Собрать факты с машин парка в один play
    ansible.builtin.setup:
    delegate_to: "{{ item }}"
    delegate_facts: true
    loop: "{{ groups['linux'] }}"

Так делают, когда play идёт по одной группе машин, а факты нужны
о другой. В нашем отчёте delegate_facts не нужен: строку отчёта каждая
машина считает сама, обычной задачей set_fact.
ЧЕГО НЕ ДЕЛАТЬ: не ставьте delegate_facts: true «на всякий случай»:
факты — это то, на чём построены условия when, и перенос их на другую
машину делает условия неверными именно там, где их читают.

=========================================================================
ШАГ 8. SERIAL И MAX_FAIL_PERCENTAGE: ОБНОВЛЯЕМ ПО ОДНОЙ МАШИНЕ
=========================================================================

В веб-части проекта стоит строка, которой не было в прошлых практиках:

  serial: "{{ update_serial | default(1) }}"
  max_fail_percentage: 0

serial задаёт размер партии. Ansible выполняет play целиком на первой
партии машин и только потом переходит к следующей: при serial: 1 будет
две партии — сначала web1 (все задачи play), потом web2.

  serial: 1                  одна машина за заход
  serial: "50%"              половина машин парка за заход
  serial: [1, "20%"]         разные размеры партий по порядку

Проценты считаются от общего числа машин, которые попали в play. Если
число не делится нацело, остаток попадает в последнюю партию, а размер
партии никогда не бывает меньше единицы.

ВАЖНО: serial не отменяет параллельность внутри партии. Он задаёт
только размер партии; машины внутри неё обрабатываются одновременно,
и число одновременных подключений ограничено параметром forks.
Отсюда: serial: 1 — «по одной машине за раз», serial: 5 при forks = 10 —
«пять машин одновременно, остальные ждут».

Зачем это в работе. Обновить десять веб-серверов «всеми сразу» —
значит одновременно перезапустить службу на всех десяти, и часть
запросов уйдёт в никуда. Партиями делают иначе: одна-две машины
выведены из работы, обновлены, возвращены.

max_fail_percentage — страховка при обновлении партиями. Значение
считается внутри партии: если в партии отказало больше машин, чем
указано в процентах, Ansible останавливает play и не трогает остальные
партии. Проценты сравниваются строго: чтобы остановиться при отказе
двух машин из четырёх, указывают 49, а не 50. У нас стоит 0.

Различие окружений видно прямо здесь: в group_vars/dev.yml стоит
update_serial: "100%" (весь пробный парк за один заход), в
group_vars/prod.yml — update_serial: 1 (по одной машине).

ПОЧЕМУ ИМЕННО ТАК: serial берётся из переменной окружения, а не зашит
в плейбук числом. Число машин в партии — решение о безопасности работ,
а не свойство плейбука: на dev рисковать нечем, на prod есть чем.

ЧЕГО НЕ ДЕЛАТЬ: не ставьте serial: 1 «на всякий случай» на парк
из трёхсот машин: время прогона растёт линейно.

ПРОВЕРКА: ansible-playbook site.yml -i inventory/dev.ini --tags web
| grep -c '^PLAY' даст четыре строки при update_serial: "100%": три
play плюс последняя строка PLAY RECAP, которую команда тоже считает.
Замените в group_vars/dev.yml значение на 1 — строк станет пять:
веб-часть пойдёт двумя партиями, и строка PLAY напечатается дважды.

=========================================================================
ШАГ 9. ANY_ERRORS_FATAL, STRATEGY: FREE И THROTTLE
=========================================================================

ANY_ERRORS_FATAL. По умолчанию отказ на одной машине останавливает
работу только на ней: остальные продолжают. any_errors_fatal меняет
это: задача доработает на всех машинах текущей партии, после чего play
останавливается целиком, и следующие plays не запускаются. Ставят его
там, где половина сделанной работы хуже, чем несделанная: обновление
схемы базы, переключение балансировщика, смена сертификата. Ключ
работает и на уровне play, и на уровне блока.

STRATEGY: FREE. По умолчанию работает линейная стратегия: все машины
проходят первую задачу, потом все вторую. free (strategy: free в play)
отпускает каждую машину по её маршруту: машина, закончившая первую
задачу, сразу берётся за вторую, не дожидаясь остальных. free
выигрывает в скорости там, где задачи машин между собой
не связаны, и ломает порядок: пока web2 выполняет первую задачу, web1
может быть уже на пятой. Приёмы, которые рассчитывают на «партия
прошла play целиком» (serial), с free теряют смысл.

THROTTLE ограничивает число машин, которые выполняют конкретную задачу
одновременно. Ставится на задачу или на блок:

  - name: Обратиться к внешней системе, которая считает запросы
    ansible.builtin.uri:
      url: "https://api.example.com/register/{{ inventory_hostname }}"
      method: POST
    throttle: 1

Ключевое слово — ограничивает: увеличить параллельность throttle
не может. Чтобы он подействовал, его значение должно быть меньше forks
и размера партии.

ЗАЧЕМ ЭТО В РАБОТЕ: парк редко бывает однородным: есть машины, которые
можно обновлять пачками, и есть вызовы внешних систем, которые
не выдержат десяти одновременных запросов.

ВАЖНО: любой из этих ключей — решение о риске. Значения по умолчанию
безопасны для учебного стенда и опасны для парка из сотни серверов.

ПРОВЕРКА: какие стратегии есть в вашей сборке:

  ansible-doc -t strategy -l | grep -E 'linear|free|host_pinned'
  ansible.builtin.free         Executes tasks without waiting for all hosts
  ansible.builtin.linear       Executes tasks in a linear fashion

ШАГ 10. ДВА ОКРУЖЕНИЯ ОДНИМ И ТЕМ ЖЕ SITE.YML
=========================================================================

Теперь инвентарей два — по одному на окружение. Инвентарь окружения
dev, файл inventory/dev.ini:

  # inventory/dev.ini — окружение dev. Формат INI.
  # Группа dev нужна, чтобы Ansible нашёл файл group_vars/dev.yml:
  # машины попадают в неё через группу linux, а не перечислением.

  [web]
  web1 ansible_host=10.0.2.11
  web2 ansible_host=10.0.2.12

  [db]
  db1 ansible_host=10.0.2.13

  [linux:children]
  web
  db

  [dev:children]
  linux

Второй инвентарь, inventory/prod.ini, отличается группой окружения
и комментарием; остальные секции те же:

  [prod:children]
  linux

Имена групп dev и prod совпадают с именами файлов в group_vars: так
Ansible и понимает, какой файл переменных читать. В рабочем проекте
prod был бы другим парком машин, часто — динамическим (практика 16).

Переменные окружения dev — файл group_vars/dev.yml:

  ---
  # group_vars/dev.yml — переменные окружения dev. Файл применяется
  # к машинам группы dev из inventory/dev.ini.

  # Сайт разворачивается: в dev проверяем всё.
  web_admin_deploy_site: true

  # По заголовку страницы и подписи в отчёте видно, какое это окружение.
  web_admin_site_title: "DEV: учебный стенд курса Ansible"
  report_title: "Окружение dev: пробный парк, обновляем все машины сразу"

  # Обновление dev идёт сразу по всему парку: за один заход 100% машин.
  update_serial: "100%"

  # Владелец машины: значение из group_vars/all/vars.yml.
  web_admin_owner: "{{ lab_owner }}"

Переменные окружения prod — файл group_vars/prod.yml:

  ---
  # group_vars/prod.yml — переменные окружения prod. Тот же site.yml,
  # те же плейбуки и роли: отличается только этот файл.

  # Сайт разворачивается.
  web_admin_deploy_site: true

  # Заголовок страницы и подпись в отчёте — свои у prod.
  web_admin_site_title: "PROD: учебный стенд курса Ansible"
  report_title: "Окружение prod: боевой парк, обновляем по одной машине"

  # Обновление prod идёт по одной машине: значение подставляется
  # в serial в playbooks/webservers.yml.
  update_serial: 1

  # Владелец машины: значение из group_vars/all/vars.yml.
  web_admin_owner: "{{ lab_owner }}"

Общие переменные проекта — файл group_vars/all/vars.yml:

  ---
  # group_vars/all/vars.yml — переменные, общие для всех машин проекта
  # и для обоих окружений. Выбрана форма каталога group_vars/all/,
  # а не файл group_vars/all.yml: рядом лежит пример файла секретов
  # vault.yml.example, а обе формы одного места не держат — когда есть
  # и каталог all/, и файл all.yml, Ansible читает каталог, а файл
  # остаётся не прочитанным: молча, без единой ошибки.

  # Подключение: те же пользователь и ключ, что в практиках 2–10.
  ansible_user: engineer
  ansible_ssh_private_key_file: /home/engineer/.ssh/id_ed25519

  # Владелец машин стенда. Учебное значение.
  lab_owner: engineer

  # Роль web_admin: порт сайта и заголовок страницы по умолчанию.
  # Заголовок переопределяют окружения в group_vars/dev.yml и prod.yml.
  web_admin_port: 80
  web_admin_site_title: "Учебный стенд курса Ansible"

  # Общие проверки: на сервере баз данных их можно выключить.
  common_checks_enabled: true

  # Семейства ОС, с которыми работает проект.
  supported_families:
    - Debian
    - RedHat

  # Порог свободного места на корневом разделе: 500 МБ.
  min_free_mb: 500

  # Каталог для резервных копий на db1 (playbooks/db.yml).
  db_backup_dir: /var/backups/lab-db

  # Каталог и имя файла отчёта на управляющей машине.
  report_dir: /home/engineer/ansible-lab/14_complex_projects/reports
  report_file: fleet-report.txt

Каталоги group_vars и host_vars Ansible ищет рядом с инвентарём и рядом
с плейбуком: у нас найден group_vars в корне проекта. Приоритет: файл
группы окружения (group_vars/dev.yml) сильнее файла группы all
(group_vars/all/vars.yml), а переменные хоста (host_vars/<машина>)
сильнее переменных группы. Тот же порядок разобран в практике 5: там
на опыте с web_port видно, что значение из host_vars/web1.yml
перебивает group_vars/all.yml.

ПОЧЕМУ ИМЕННО ТАК: окружение описано не отдельным плейбуком, а именем
группы и её переменными. Третий стенд (например, stage) добавляется
двумя файлами — инвентарём и group_vars, без правок в site.yml и роли.

ВАЖНО: ключ -i обязателен. В ansible.cfg инвентаря по умолчанию нет
намеренно: запуск без -i уходит на /etc/ansible/hosts, Ansible
предупреждает, что список машин пуст, и «успешно» не делает ничего.

ПРОВЕРКА: ansible-inventory -i inventory/prod.ini --host web1 | grep
title покажет "PROD: учебный стенд курса Ansible": один и тот же хост,
разные значения, и ни одна строка плейбука не изменилась.

ШАГ 11. СЕКРЕТЫ ОКРУЖЕНИЯ: VAULT.YML РЯДОМ С GROUP_VARS
=========================================================================

Секреты живут там же, где переменные, — в group_vars, и открытым
текстом в репозиторий не попадают:

  ---
  # ОБРАЗЕЦ файла секретов проекта. Это не зашифрованный файл: в курс он
  # положен открытым текстом, потому что шифрование проверяется на стенде,
  # а непроверенный шифротекст студент своим паролем не откроет.
  #
  # Как из образца сделать рабочий файл:
  #   cp group_vars/all/vault.yml.example group_vars/all/vault.yml
  #   # впишите свои значения, затем зашифруйте файл:
  #   ansible-vault encrypt group_vars/all/vault.yml
  #
  # Значения ниже — УЧЕБНЫЕ ЗАГЛУШКИ. На своём стенде замените их своими.

  # Пароль, под которым приложение на веб-узлах ходит в базу данных db1.
  vault_db_password: "MyStrongPassword"

  # Ключ API учебного приложения.
  vault_api_token: "ЗАМЕНИТЕ_ЭТОТ_КЛЮЧ"

Это файл group_vars/all/vault.yml.example. Секреты бывают общие для
проекта (group_vars/all/vault.yml) и отдельные для окружения
(group_vars/dev/vault.yml и group_vars/prod/vault.yml): пароли боевой
и пробной баз разные, и доступ к ним у разных людей.

  cd ~/ansible-lab/14_complex_projects
  cp group_vars/all/vault.yml.example group_vars/all/vault.yml
  vi group_vars/all/vault.yml
  ansible-vault encrypt group_vars/all/vault.yml

Запуск проекта с секретами требует пароля Vault:

  ansible-playbook site.yml -i inventory/prod.ini --ask-vault-pass
ПОЧЕМУ ИМЕННО ТАК: у Ansible Vault нет понятия «окружение»: шифрование
это свойство файла, а не окружения. Значит, окружение секретов задаётся
тем же способом, что и окружение переменных: именами групп и файлов.

ЧЕГО НЕ ДЕЛАТЬ: не держите пароль Vault в репозитории: файл .vault_pass
и его копии попадают в .gitignore и в репозиторий не кладутся никогда.
И не переименовывайте vault.yml.example в vault.yml, не зашифровав его.

=========================================================================
ШАГ 12. --LIMIT ВМЕСТЕ С DELEGATE_TO, ADD_HOST И META
=========================================================================

ПЕРВЫЙ приём: --limit вместе с delegate_to. Ключ --limit сокращает
список машин, по которым идёт play:

  ansible-playbook site.yml -i inventory/prod.ini --tags report --limit web1

В файле отчёта будет одна строка, а остальные машины получат значение
по умолчанию — «данных нет»: их факты не собирались, потому что play
по ним не шёл. delegate_to меняет место выполнения задачи, а не список
машин play.

ВТОРОЙ: add_host добавляет машину в инвентарь во время прогона. Нужен
там, где машина появляется в процессе: создалась в облаке, поднялась
из шаблона. Добавленная машина действует только для следующих plays:

  - name: Добавить машину в инвентарь текущего прогона
    ansible.builtin.add_host:
      name: web3
      groups: web

ВАЖНО: add_host всегда выполняется на управляющей машине — это одна
из задач, которую делегировать нельзя, как и debug с include.
В рабочем проекте здесь же указывают ansible_host, если адрес новой
машины не совпадает с её именем.

ТРЕТИЙ: meta: end_play и meta: end_host — это не модули, а команды
самому Ansible:

  - name: Остановить play для всех машин
    ansible.builtin.meta: end_play

  - name: Вывести одну машину из работы
    ansible.builtin.meta: end_host

end_play заканчивает текущий play для всех машин (следующие plays
из site.yml выполнятся), end_host — только для той машины, на которой
сработал. Пример из работы: в dev-окружении отчёт собирать не нужно,
и play останавливается до тяжёлых задач.

ПРОВЕРКА: запустим только отчёт и посмотрим, где выполнилась задача:

  ansible-playbook site.yml -i inventory/prod.ini --tags report \
      --limit 'web:&debian'

  changed: [web1 -> localhost]

  PLAY RECAP
  db1  : ok=16 changed=2  unreachable=0 failed=0 rescued=0 ignored=0
  web1 : ok=28 changed=4  unreachable=0 failed=0 rescued=0 ignored=0
  web2 : ok=25 changed=2  unreachable=0 failed=0 rescued=0 ignored=0

ЧТО ЗДЕСЬ ЧИТАТЬ: строка PLAY для веб-части напечатана дважды —
serial: 1 в prod разбил две машины на две партии; в задачах отчёта видно
web1 -> localhost: задача идёт по машине web1, а выполняется
на управляющей (имя до стрелки — это inventory_hostname, чья это
задача); строка PLAY для отчёта одна, хотя машин три, потому что
serial в этом play не задан и run_once выполнился один раз.

ЧТО ВИДНО В ЧИСЛАХ. В ok входят все задачи, которые машина выполнила,
включая обработчики; они же попадают и в changed. Разница между web1
и web2 (28 против 25) — это три задачи отчёта: они выполняются один
раз, на первой машине play, и две из них меняют файлы на управляющей.
У db1 задач меньше всех: роль web_admin работает только на web1
и web2, а db1 настраивает свой плейбук. Столбца skipped в сводке нет
намеренно: он зависит от того, считать ли блок с ложным when одной
пропущенной задачей или всеми задачами ветки. Пропущенное видно
по строкам skipping в выводе: на web1 и web2 ложным оказалось условие
ветки RedHat, и обе её задачи — «Включить firewalld» и «Разрешить
порт сайта в firewalld» — пропущены; на db1 пропущенных задач нет.

Отчёт на управляющей машине:

  cat reports/fleet-report.txt
  # Отчёт о парке машин учебного стенда.
  # Файл собран задачей с delegate_to: localhost и run_once: true,
  # поэтому он один, а не по копии на каждой машине.
  fleet_report:
    machines_total: 3
    environment: "PROD: учебный стенд курса Ansible"
    machines:
      - db1 | Rocky Linux 10.1 | ядро 6.12.0-55.el10.x86_64 | свободно 15320 МБ
      - web1 | Ubuntu 26.04 LTS | ядро 6.14.0-24-generic | свободно 11240 МБ
      - web2 | Ubuntu 26.04 LTS | ядро 6.14.0-24-generic | свободно 11408 МБ

Повторный прогон ничего не меняет:

  ansible-playbook site.yml -i inventory/prod.ini
  PLAY RECAP
  ...у всех трёх машин changed=0 и failed=0

changed=0 на всех трёх машинах: проект описывает состояние, а не
выполняет действия. Отчёт тоже не изменился — в нём нет ни даты,
ни времени. Посмотрим на проект до запуска:

  ansible-playbook --list-hosts site.yml -i inventory/prod.ini

    play #1 (web): Веб-серверы: сайт, проверки и безопасное обновление
      hosts (2): web1, web2
    play #2 (db): Сервер баз данных
      hosts (1): db1
    play #3 (linux): Собрать отчёт о парке машин
      hosts (3): web1, web2, db1

Четыре машины стенда: три управляемых узла и управляющая машина,
на которую ложится файл отчёта. Одна команда — весь парк.

ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: тег на include_tasks не тегирует задачи внутри файла

Симптом: с --tags checks проверки идут на web1, а на db1 не идут,
и ошибки при этом нет:

  TASK [Выполнить общие проверки машины]
  included: /home/engineer/ansible-lab/14_complex_projects/tasks/common_checks.yml for db1

Причина: тег динамического включения относится к самому включению,
а задачи внутри файла остаются без тегов. Порядок проверки:

  grep -n -A6 'include_tasks' playbooks/db.yml
  ansible-playbook --list-tasks site.yml -i inventory/dev.ini --tags checks
Если в play №2 видна только строка «Выполнить общие проверки машины»,
apply написан не там: он должен стоять внутри словаря включения.

ПРОБЛЕМА: делегированная задача берёт не ту переменную

  fatal: [web1 -> localhost]: FAILED! => {"changed": false, "msg": "Destination /fleet-report.txt does not exist"}

Причина: при делегировании часть переменных берётся у машины, которой
задача делегирована, а у адреса не из инвентаря переменные только
из группы all. Порядок проверки:

  grep -n -A4 'delegate_to' playbooks/report.yml
  ansible-playbook site.yml -i inventory/dev.ini --tags report \
      --limit web1 -e report_dir=/tmp

Если с -e работает — дело в переменной: берите её явно, через
hostvars[inventory_hostname].

ПРОБЛЕМА: run_once вместе с serial выполняется по разу на партию

Симптом: в отчёте одна машина вместо трёх: файл перезаписывается
на каждой партии, и остаётся содержимое последней.

Причина: run_once выполняется один раз на партию, а не на прогон.
Порядок проверки:

  grep -n -E 'serial|run_once' playbooks/report.yml
  ansible-playbook site.yml -i inventory/prod.ini --tags report \
      | grep -c 'Записать отчёт'
Лечение: убрать serial из play с отчётом или заменить run_once
на условие, которое срабатывает один раз за прогон:

  when: inventory_hostname == ansible_play_hosts_all[0]

ПРОБЛЕМА: ERROR! the role 'web_admin' was not found in ...

  ERROR! the role 'web_admin' was not found in /home/engineer/ansible-lab/14_complex_projects/playbooks/roles:/home/engineer/.ansible/roles:/usr/share/ansible/roles:/etc/ansible/roles

Причина: команда запущена не от точки входа. Ansible ищет роли
в каталоге roles рядом с тем файлом, где написан play: у
playbooks/webservers.yml это playbooks/roles, где роли нет. Порядок
проверки:

  pwd
  ansible --version | grep 'config file'
  ls -d roles/*/ ; ansible-config dump | grep -i roles_path

Запускайте из корня проекта:

  ansible-playbook site.yml -i inventory/dev.ini

ПОЧЕМУ ИМЕННО ТАК: в проекте за это отвечает roles_path = ./roles.

ПРОБЛЕМА: отчёт перезаписывается на каждой машине

Симптом: reports/fleet-report.txt есть на web1, web2 и db1, а на
управляющей машине его нет; в каждой копии — своя одна строка.

Причина: в задаче записи нет delegate_to, и copy выполняется на тех
машинах, по которым идёт play. Порядок проверки:

  grep -n -B2 -A2 'copy:' playbooks/report.yml
  ssh engineer@web1 'ls ~/ansible-lab/14_complex_projects/reports/'

Каталог отчёта создаёт отдельная задача: она тоже должна быть
делегирована, иначе запись упадёт с «Destination ... does not exist».

ПРОБЛЕМА: повторный прогон снова changed=1

  TASK [Записать отчёт одним файлом на управляющей машине]
  changed: [web1 -> localhost]

Причина: задача каждый раз создаёт разное содержимое. Чаще всего
виновата дата в шаблоне:

  collected_at: "{{ ansible_facts['date_time']['iso8601'] }}"

  grep -rn 'date_time\|now()' tasks/ playbooks/ roles/

В нашем отчёте даты нет намеренно: отчёт описывает состояние машин,
а не время прогона.

ИСПРАВЛЕНО: в прежней версии курса эта работа делалась одним плейбуком
«Install Apache and upload WebSite», переписанным копипастой в шести
файлах: под web, под db, под каждую учебную группу. Роль в прежней
версии была, но одна, в самом конце курса, и с ошибками: перевёрнутое
объяснение defaults и vars и сломанные отступы в tasks/main.yml.
Окружений не было, порядок обновления не обсуждался: все машины
обновлялись сразу. Правку вносили в одну копию, а запускали другую.
В новой версии тот же набор работ описан одним проектом: одна роль,
два окружения, обновление партиями.

ПРОБЛЕМА: [WARNING]: No inventory was parsed, only implicit localhost is available

  [WARNING]: No inventory was parsed, only implicit localhost is available
  [WARNING]: provided hosts list is empty, only localhost is available

Причина: команда запущена без ключа -i, а инвентаря по умолчанию
в ansible.cfg нет. Опасен не текст предупреждения, а то, что прогон
после него завершается «успешно», не сделав ничего. Порядок проверки:

  ansible-inventory -i inventory/dev.ini --graph
  ansible-playbook --list-hosts site.yml -i inventory/prod.ini
Привычка, которая спасает: перед прогоном смотреть --list-hosts.
