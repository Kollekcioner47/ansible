=========================================================================
ШАГ 1. COPY, FILE, TEMPLATE: ЧТО ЧЕМ ДЕЛАЕТСЯ
=========================================================================

Три модуля постоянно путают. Разница не в том, «что умеет модуль»,
а в том, откуда берётся содержимое.

  ansible.builtin.copy      берёт готовое содержимое и кладёт как есть:
                            файл рядом с плейбуком или строку
                            в параметре content.
  ansible.builtin.template  берёт шаблон Jinja2, подставляет значения
                            переменных и кладёт результат.
  ansible.builtin.file      содержимое не трогает вообще: каталог,
                            ссылка, пустой файл, права, владелец,
                            удаление.

Правило выбора: нужны значения переменных — template; файл всегда
одинаковый — copy; надо поменять только права или владельца — file;
надо поменять одну строку в чужом файле, который принадлежит пакету,
— lineinfile из второй части.

ПОЧЕМУ ИМЕННО ТАК: модуль отвечает за результат, а не за способ.
Задача «файл на узле должен быть таким» описывается одним модулем,
и Ansible сам решает, надо ли что-то делать: второй прогон не делает
ничего, потому что состояние уже совпадает.

Параметры: src — что взять; dest — полный путь на узле; content —
содержимое строкой вместо src; owner, group, mode — владелец, группа
и права; backup: true — сохранить копию перед заменой; force: false —
не перезаписывать существующий файл. У модуля file вместо них два
своих: state (directory, file, touch, link, hard, absent) и recurse —
применить владельца и права ко всему дереву.

ВАЖНО: copy и template сравнивают содержимое и не перезаписывают
файл, если оно не изменилось. Поэтому backup: true не создаёт гору
копий при каждом прогоне, а notify у задачи не срабатывает зря.
Справка по параметрам всегда под рукой, без браузера:

  ansible-doc ansible.builtin.copy | head -40
  ansible-doc -s ansible.builtin.file

ЗАЧЕМ ЭТО В РАБОТЕ: разница между «скопировать» и «описать шаблоном»
на большом парке — это разница между пятьюдесятью почти одинаковыми
файлами и одним шаблоном.

ЧЕГО НЕ ДЕЛАТЬ: не создавайте каталоги командой shell с mkdir -p.
Модуль file делает то же самое, но сообщает changed только тогда,
когда каталог действительно появился, а команда — всегда.

=========================================================================
ШАГ 2. ПРАВА: ВОСЬМЕРИЧНАЯ И СИМВОЛИЧЕСКАЯ ЗАПИСЬ
=========================================================================

Права в Linux — три группы по три бита: владелец (u, user), группа
(g, group), остальные (o, other). Внутри группы три бита: чтение
r = 4, запись w = 2, выполнение x = 1. Сумма битов даёт цифру.

  0644 = владелец читает и пишет, группа читает, остальные читают.
  0755 = владелец читает, пишет и выполняет, группа и остальные
         читают и выполняют. Так выглядит каталог.
  0600 = только владелец читает и пишет. Так выглядит закрытый ключ.

Четыре цифры вместо трёх — другая группа битов: 0644 обычные права,
1644 плюс sticky bit (удалять файл в каталоге может только его
владелец), 2644 плюс setgid (новые файлы получают группу каталога),
4644 плюс setuid (программа выполняется от имени владельца файла).

Первая ловушка — запись без кавычек:

  # так делать нельзя
      mode: 0644
  # так правильно
      mode: "0644"

В первом случае YAML разбирает 0644 как восьмеричное число и передаёт
в модуль число, а не строку из четырёх символов. Ansible 2.19 такое
значение принимает и поправляет сам, но выдаёт предупреждение,
а в шаблонах и переменных то же самое число ведёт себя иначе.

ВАЖНО: правило курса — права всегда строкой в кавычках: mode: "0644",
mode: "0755", mode: "0600". Это же требует ansible-lint правилом
risky-octal, и на нём спотыкаются почти все, кто пишет mode: 0644.

Вторая ловушка — 0777. Запись означает «читать, писать и выполнять
всем». Она «работает» и именно поэтому опасна: файл может переписать
любой пользователь машины, то есть содержимое сайта может изменить
кто угодно и никто этого не заметит; на каталоге с 0777 любой может
удалить чужие файлы, а с ними и весь сайт. При этом 0777 ничего
не лечит: если файл не читается, причина почти всегда в правах
на каталог, а не в правах файла.

ЧЕГО НЕ ДЕЛАТЬ: не ставьте 0777 «чтобы точно заработало» и не
используйте 0555 «чтобы никто не испортил». 0555 на странице сайта
означает, что файл нельзя исправить, не сняв права: следующий плейбук
не сможет его обновить. Это ошибка прежней версии курса, и она
разобрана в пометке ИСПРАВЛЕНО.

Символическая запись нужна, когда меняют один бит, не трогая
остальные:

  - name: Разрешить чтение файла, остальное не менять
    ansible.builtin.file:
      path: /var/www/html/site/index.html
      mode: "u=rw,g=r,o=r"

Запись u=rw,g=r,o=r и запись 0644 дают одинаковый результат, но
символическая меняет только перечисленные биты. В курсе принята
числовая запись строкой: она короче и читается одинаково всеми.
Разбор umask и прав на служебные файлы — в практике 9, где права
файла sudoers задаются как 0440.

=========================================================================
ШАГ 3. КАТАЛОГИ, ССЫЛКИ, УДАЛЕНИЕ
=========================================================================

У каталога два отличия от файла. Первое: бит x у каталога означает
«можно войти и обратиться к файлу внутри», и без него страница
не откроется, даже если файл читается всеми. Второе: права на каталог
и права на содержимое задаются разными задачами.

  - name: Создать каталог сайта
    ansible.builtin.file:
      path: /var/www/html/site
      state: directory
      owner: root
      group: root
      mode: "0755"

  - name: Привести дерево сайта к одному владельцу
    ansible.builtin.file:
      path: /var/www/html/site
      state: directory
      owner: root
      group: root
      recurse: true

ПОЧЕМУ ИМЕННО ТАК: без recurse модуль file меняет только объект,
указанный в path. Это ровно то поведение, которое нужно почти
всегда: молчаливая правка прав во всём дереве — не то, чего ждут
от задачи с именем «поменять права на каталог».

Ссылки задаются словами link и hard, а удаление — словом absent:

  - name: Показать сайт по короткому адресу
    ansible.builtin.file:
      src: /var/www/html/site
      dest: /var/www/html/current
      state: link
      force: true

  - name: Убрать каталог, который оставил прошлый прогон
    ansible.builtin.file:
      path: /tmp/site_build
      state: absent

Параметр force: true у ссылки означает «заменить существующий объект
ссылкой». Без него задача упадёт, если по этому пути уже лежит файл
или каталог: это защита от случайной подмены, а не лишний параметр.
Если path указывает на каталог, state: absent удаляет каталог вместе
с содержимым, поэтому путь собирают из переменной, значение которой
видно в отчёте.

ЧЕГО НЕ ДЕЛАТЬ: не удаляйте каталоги командой shell с rm -rf: модуль
file с state: absent виден в отчёте одной строкой с понятным именем
задачи, а строка shell скрывает и то, что удаляется, и зачем.

ПРОВЕРКА: посмотрите результат глазами, а не по строке ok в отчёте:

  ssh engineer@web1 'ls -ld /var/www/html/site'

=========================================================================
ШАГ 4. КОПИРУЕМ КАТАЛОГ И ПИШЕМ ШАБЛОН
=========================================================================

Содержимое сайта — каталог site с двумя файлами. Скопировать его
целиком можно одной задачей, если помнить одно правило: слеш в конце
src меняет результат. Запись src: site/ кладёт содержимое каталога
в dest: получится dest/index.html. Запись src: site кладёт сам
каталог: получится dest/site/index.html. Ошибка здесь встречается
почти у всех: задача проходит, а вместо страницы браузер отдаёт
список файлов — потому что на месте index.html оказался каталог.

  backup: true      перед заменой сохранить копию с отметкой времени:
                    index.html.2025-05-14@10-31-07.
  force: false      не перезаписывать существующий файл. Так защищают
                    файлы, которые кто-то правил руками.
  remote_src: true  брать источник на управляемом узле, а не на
                    управляющей машине. Разбирается в шаге 13.

  - name: Положить страницу сайта с сохранением прежней версии
    ansible.builtin.copy:
      src: site/index.html
      dest: /var/www/html/site/index.html
      owner: root
      group: root
      mode: "0644"
      backup: true

ЗАЧЕМ ЭТО В РАБОТЕ: backup: true — не замена системе контроля версий,
а страховка на первый прогон по живому серверу: содержимое конфигураций
всё равно хранят в репозитории, а не в копиях с датой в имени.

Теперь template: тот же шаг, но файл собирается из переменных. Возьмём
шаблон задания cron из files/08_files/templates/cron.j2:

  # {{ ansible_managed }}
  SHELL=/bin/bash
  PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
  MAILTO="{{ cron_mailto }}"

  {{ cron_minute }} {{ cron_hour }} * * * root /usr/bin/logger "{{ inventory_hostname }}: плановая проверка сайта"

ВАЖНО: задание записано одной строкой, и это не мелочь.
Переносить команду в crontab обратным слэшем нельзя: cron
не понимает продолжения строки, первая строка обрывается
на слэше, а вторая читается как отдельная неверная запись.
Длинную команду выносят в отдельный скрипт или в файл,
а в crontab указывают путь к нему.

Переменные cron_minute, cron_hour и cron_mailto заданы в плейбуке,
а inventory_hostname и ansible_managed служебные: первая содержит имя
текущего узла, вторая — строку «Ansible managed» из ansible.cfg.
Так файл на узле сам сообщает, что создан автоматизацией.

  - name: Разложить расписание задач cron
    ansible.builtin.template:
      src: templates/cron.j2
      dest: /etc/cron.d/site-check
      owner: root
      group: root
      mode: "0644"

ВАЖНО: template ищет шаблон в каталоге templates/ рядом с плейбуком
или в каталоге templates/ роли. Если файл лежит в другом месте,
Ansible перечислит в ошибке все проверенные пути: по списку видно,
какой каталог Ansible считает текущим. И ещё: файл в /etc/cron.d
обязан принадлежать root и не быть доступным на запись остальным,
иначе cron отказывается его читать и пишет об этом в журнал.

=========================================================================
ШАГ 5. ПЛЕЙБУК 01_COPY.YML: САЙТ НА WEB1 И WEB2
=========================================================================

Собираем первый плейбук практики. Его полный текст совпадает с файлом
files/08_files/01_copy.yml.

  ---
  # 01_copy.yml — шаг 5 практики 8.
  - name: Разложить статический сайт
    hosts: web
    become: true
    gather_facts: false
    vars:
      site_dir: /var/www/html/site
      file_mode: "0644"
      dir_mode: "0755"
      cron_minute: "17"
      cron_hour: "4"
      cron_mailto: root@localhost
    tasks:
      - name: Создать каталог сайта
        ansible.builtin.file:
          path: "{{ site_dir }}"
          state: directory
          owner: root
          group: root
          mode: "{{ dir_mode }}"

      - name: Скопировать содержимое сайта
        ansible.builtin.copy:
          src: site/
          dest: "{{ site_dir }}/"
          owner: root
          group: root
          mode: "{{ file_mode }}"
          backup: true

      - name: Разложить расписание задач cron
        ansible.builtin.template:
          src: templates/cron.j2
          dest: /etc/cron.d/site-check
          owner: root
          group: root
          mode: "0644"

Здесь hosts: web — группа из инвентаря практики 2, то есть web1 и web2;
become: true нужен для записи в /var/www и в /etc; gather_facts: false —
факты этому плейбуку не нужны, а сбор фактов стоит времени; vars
хранят путь сайта и права, которые в практике 10 переедут в defaults
роли. Обратите внимание: три переменные cron_minute, cron_hour
и cron_mailto объявлены на уровне play, а не у задачи template,
и шаблон cron.j2 использует только их и inventory_hostname, поэтому
отключение фактов ничего не ломает.

Обратите внимание на пару прав: у задачи file — 0755, у задачи copy —
0644. Каталог обязан быть исполняемым для всех, файлы внутри — только
читаемыми. Если поменять их местами, сайт не откроется, а ошибка
будет выглядеть странно: файл на месте, браузер отдаёт 403.

  cd ~/ansible-lab
  ansible-playbook 01_copy.yml

  PLAY RECAP ********************************************************
  web1  : ok=4  changed=4  unreachable=0  failed=0
  web2  : ok=4  changed=4  unreachable=0  failed=0

Три changed — три задачи плейбука, каждая что-то изменила. Ещё один
changed — обработчик перезапуска службы SSH: он сработал после задачи
template, потому что файл /etc/cron.d/site-check появился впервые.
Обработчик попадает и в ok, и в changed, поэтому четвёртая строка
в отчёте — это он. Второй прогон даст changed=0: описание состояния
совпало с состоянием машины.

ПРОВЕРКА: страница отдаётся веб-сервером, а не списком файлов:

  curl -s http://10.0.2.11/site/ | head -3
  <!DOCTYPE html>
  <html lang="ru">

=========================================================================
ШАГ 6. ПЛЕЙБУК 02_PERMISSIONS.YML: SETGID НА КАТАЛОГЕ
=========================================================================

Права на файлы мы расставили при копировании. Но у каталога есть
свойство, которого копированием не задать: наследование группы новыми
файлами. За это отвечает бит setgid.

Пусть сайт наполняют два человека, оба в группе webadmin. Без setgid
новый файл получает группой основную группу того, кто его создал:
у одного это webadmin, у другого — личная группа. Через неделю часть
файлов недоступна части команды, и никто не может объяснить почему.
С битом setgid каталог назначает группу новым файлам сам. Обозначается
он числом 2755 или символически как g+s; в Ansible пишем числом
строкой.

Полный текст плейбука — в файле files/08_files/02_permissions.yml.
Ключевые задачи:

  - name: Проверить, какие файлы лежат в каталоге сайта
    ansible.builtin.find:
      paths: "{{ site_dir }}"
      file_type: file
      recurse: true
    register: site_files

  - name: Поставить права на файлы сайта
    ansible.builtin.file:
      path: "{{ item.path }}"
      owner: root
      group: root
      mode: "{{ file_mode }}"
    loop: "{{ site_files.files }}"
    loop_control:
      label: "{{ item.path }}"

  - name: Поставить на каталог сайта права с битом setgid
    ansible.builtin.file:
      path: "{{ site_dir }}"
      state: directory
      owner: root
      group: root
      mode: "{{ setgid_mode }}"

Переменные плейбука: site_dir: /var/www/html/site, file_mode: "0644",
dir_mode: "0755", setgid_mode: "2755". Кроме этих задач в плейбуке
есть stat и assert из шага 12: они проверяют, что права на каталог
действительно стали 2755. В выкладке выше нет двух вспомогательных
задач из полного файла: «Убедиться, что каталог сайта существует»
(та же задача file, что и в шаге 5) и «Показать найденные файлы»
(debug со списком путей).

  ansible-playbook 02_permissions.yml

  PLAY RECAP ********************************************************
  web1  : ok=8  changed=3  unreachable=0  failed=0
  web2  : ok=8  changed=3  unreachable=0  failed=0

Три changed — это создание каталога сайта, права на файлы и бит setgid
на каталоге. Обработчиков у этого плейбука нет, поэтому ok отличается
от changed на задачи, которые ничего не меняли: find, debug, stat
и assert.

ПОЧЕМУ ИМЕННО ТАК: setgid поставлен только на каталог сайта, а не
на все каталоги в /var/www. Права — часть договорённости между людьми,
которые работают с машиной, и менять их «за компанию» с соседними
каталогами нельзя: у соседей свои договорённости.

ПРОВЕРКА: посмотрите на права каталога и найдите букву s в группе:

  ssh engineer@web1 'ls -ld /var/www/html/site'
  drwxr-sr-x 2 root root 4096 мая 14 10:31 /var/www/html/site

ЗАЧЕМ ЭТО В РАБОТЕ: setgid на каталоге — самый дешёвый способ
избавиться от вечной проблемы «файл создан не с той группой».
Он не заменяет разграничение доступа, но снимает целый класс
обращений в поддержку.

=========================================================================
ШАГ 7. LINEINFILE: ДВЕ СТРОКИ В КОНФИГУРАЦИИ SSHD
=========================================================================

Теперь самая частая задача в работе: поменять одну строку в файле,
который мы не писали и не хотим переписывать целиком. Для этого три
модуля, и первый — lineinfile. Он ищет в файле строку по регулярному
выражению regexp: нашёл — заменяет её на line, не нашёл — дописывает
line в конец файла или в указанное место.

  path         файл, который правим. Обязателен.
  line         строка, которая должна оказаться в файле.
  regexp       по какому образцу искать существующую строку.
  state        present (по умолчанию) или absent — удалить строку.
  insertafter  вставить после строки, найденной по этому выражению.
  insertbefore вставить перед строкой, найденной по этому выражению.
  backrefs     true — использовать группы выражения в line
               (подробно — в практике 11).
  validate     команда проверки файла до подмены. Разбирается ниже.
  backup       true — сохранить копию файла перед изменением.

Сама задача: закроем два входа, которые открыты по умолчанию почти
везде, — вход root по SSH и вход по паролю.

ПОЧЕМУ ЭТО ДЕЛАЮТ ЧЕРЕЗ ОТДЕЛЬНЫЙ ФАЙЛ, А НЕ ПРАВКОЙ ОСНОВНОГО.
Файл /etc/ssh/sshd_config принадлежит пакету openssh-server. Пакет
обновляется — и при обновлении может заменить файл, вернув настройки
к исходным. Тогда наша правка исчезнет, и никто этого не заметит:
служба поднимется с ослабленной конфигурацией.

Начиная с OpenSSH 8.2 основной файл содержит строку Include, которая
подключает каталог /etc/ssh/sshd_config.d/. Всё, что лежит в нём,
читается как продолжение основного файла, а сами файлы принадлежат
нам, а не пакету. Поэтому свои две строки мы положим
в /etc/ssh/sshd_config.d/20-sshd-hardening.conf.

Здесь важно не перепутать порядок. sshd для каждого параметра берёт
ПЕРВОЕ найденное значение, а файлы каталога подставляет по алфавиту:
Include разворачивает sshd_config.d/*.conf в лексикографическом
порядке. На наших Ubuntu уже лежит 50-cloud-init.conf. Имя 20-...
идёт раньше имени 50-... по алфавиту, значит, наш файл читается
первым, и наши значения побеждают. Имя 55-... читалось бы после
cloud-init, и тот перекрыл бы наши настройки. Ошибка коварна тем,
что плейбук отработает без жалоб: файл на месте, а действует не он.

Рядом с нашим файлом в этом же каталоге лежит 10-lab-nopassword.conf
из практики 2. Там префикс 10, здесь 20: имена разные, и по одному
взгляду на каталог видно, чей файл что делает. Два файла с одинаковым
префиксом тоже допустимы, sshd разберёт их по полному имени
(10-lab-... раньше 10-sshd-...), но разные префиксы прозрачнее,
и именно поэтому мы взяли 20, а не 10. Правило одно: префикс обязан
быть меньше 50, иначе cloud-init победит, а наши строки не подействуют.

Строки, которые включаем: PermitRootLogin no запрещает вход root
по SSH полностью, PasswordAuthentication no оставляет только вход
по ключу. Обе строки безопасны для нашего стенда: доступ по ключу
ed25519 из практики 1, а root мы не используем. На стенде с доступом
по паролю эти строки закроют вам вход, и снимок виртуальной машины
из практики 1 останется единственной страховкой.

  - name: Запретить вход root по SSH
    ansible.builtin.lineinfile:
      path: "{{ sshd_dropin }}"
      regexp: '^#?\s*PermitRootLogin\s'
      line: "PermitRootLogin no"
      state: present
      backup: true
      validate: "sshd -t -f %s"
    notify: Перезапустить службу SSH

  - name: Запретить вход по паролю
    ansible.builtin.lineinfile:
      path: "{{ sshd_dropin }}"
      regexp: '^#?\s*PasswordAuthentication\s'
      line: "PasswordAuthentication no"
      state: present
      backup: true
      validate: "sshd -t -f %s"
    notify: Перезапустить службу SSH

  handlers:
    - name: Перезапустить службу SSH
      ansible.builtin.service:
        name: "{{ ssh_service }}"
        state: restarted

Имя службы берётся из переменной ssh_service, которую практика 2
объявила в group_vars/debian.yml и group_vars/redhat.yml: ssh
на Ubuntu и sshd на Rocky Linux. Условие в задаче не нужно — различие
между семействами уже выражено данными.

Перед этими задачами плейбук создаёт каталог sshd_config.d и сам файл
задачей file со state: touch, а после них проверяет конфигурацию
командой sshd -t и читает действующие значения командой sshd -T.
Полный текст — в файле files/08_files/03_lineinfile.yml. Там есть
переменная sshd_dropin с путём к файлу (та самая строка
/etc/ssh/sshd_config.d/20-sshd-hardening.conf), у задачи file —
параметры modification_time: preserve и access_time: preserve,
а после задач lineinfile идут команды sshd -t и sshd -T
с changed_when: false и assert, который разбирает вывод sshd -T
и проверяет действующие значения.

Теперь про параметр, который отличает аккуратную правку конфигурации
от опасной:

  validate: "sshd -t -f %s"

Ansible не пишет файл сразу на место. Он готовит изменённый текст
во временном файле, подставляет его путь вместо %s и запускает
указанную команду. Если sshd -t отвечает ошибкой, файл на место
не подменяется, задача падает, а рабочий конфиг остаётся прежним,
и служба продолжает работать.

ЗАЧЕМ ЭТО В РАБОТЕ: без validate опечатка в sshd_config применяется,
и sshd не стартует. Следствие — вы теряете доступ к машине, потому
что попали на неё именно по SSH. На стенде это лечится снимком,
на рабочем сервере — выездом в дата-центр или консолью управления.

ВАЖНО: validate нужен для любой правки, у которой есть команда
проверки: sshd -t -f %s, visudo -cf %s. Для многофайловых
конфигураций (nginx) он не подходит: nginx проверяет конфигурацию
целиком, а не один файл из conf.d, поэтому проверку делают отдельной
задачей после раскладки (практика 12). Если команда принимает файл
не последним аргументом, смотрите справку модуля: некоторые модули
подставляют имя файла только на место %s.

  ansible-playbook 03_lineinfile.yml

  PLAY RECAP ********************************************************
  web1  : ok=8  changed=3  unreachable=0  failed=0
  web2  : ok=8  changed=3  unreachable=0  failed=0

Обработчик в этом прогоне сработал один раз, хотя notify стоит
у двух задач: это поведение handlers из практики 4 — обработчик
запускается не на каждый notify, а один раз в конце play. Он виден
в отчёте наравне с задачами и попадает и в ok, и в changed: три
changed — это созданный файл настроек и две правки lineinfile,
а ok=8 — семь задач плюс сработавший обработчик.

ПРОВЕРКА: смотрите на действующие значения, которые sshd прочитал
со всех файлов, а не на содержимое нашего файла и не на строку
changed. Правильную команду выполняет сам плейбук:

  ssh engineer@web1 'sudo sshd -T | grep -E "permitrootlogin|passwordauthentication"'
  permitrootlogin no
  passwordauthentication no

Второй прогон плейбука обязан дать changed=0: обе строки уже есть,
а обработчик не получает ни одного notify.

ЧЕГО НЕ ДЕЛАТЬ: не открывайте второй терминал, чтобы «на всякий
случай проверить, работает ли вход по паролю». После включения
PasswordAuthentication no пароль больше не действует, и вы потратите
время на выяснение того, что и должно было случиться.

Проверка действующего значения встроена в плейбук: после правки он
читает вывод sshd -T, а assert разбирает его и требует точного
совпадения. Наличие строки в файле здесь ничего не доказывает — файл
может быть перекрыт другим файлом каталога sshd_config.d:

  - name: Прочитать действующие значения настроек
    ansible.builtin.shell:
      cmd: >-
        sshd -T | grep -E
        -e '^permitrootlogin '
        -e '^passwordauthentication '
    register: sshd_effective
    changed_when: false
    failed_when: sshd_effective.rc not in [0, 1]

  - name: Отказаться работать, если настройки не применились
    ansible.builtin.assert:
      that:
        - sshd_effective.stdout is search('(?m)^permitrootlogin no$')
        - sshd_effective.stdout is search('(?m)^passwordauthentication no$')
      fail_msg: >-
        sshd -T не показывает наши значения: действующая конфигурация
        отличается от описанной. Проверьте, что файл
        20-sshd-hardening.conf читается раньше 50-cloud-init.conf
        и ни один файл каталога sshd_config.d его не перекрывает.
      success_msg: "Обе настройки действуют."

failed_when здесь нужен, потому что grep возвращает 1, когда ни одна
строка не найдена: это не ошибка запуска, а ответ «такого значения
в действующей конфигурации нет», и разбирает его assert.

=========================================================================
ШАГ 8. INSERTAFTER, INSERTBEFORE, STATE: ABSENT И BACKREFS
=========================================================================

lineinfile умеет больше, чем замену существующей строки.

ПЕРВЫЙ приём. Строки в файле нет, и она должна появиться в нужном
месте, а не в конце. За это отвечает insertafter:

  - name: Разрешить вход группе администраторов
    ansible.builtin.lineinfile:
      path: /etc/ssh/sshd_config.d/20-sshd-hardening.conf
      line: "AllowGroups sudo wheel"
      insertafter: '^PermitRootLogin'
      validate: "sshd -t -f %s"

Правильное значение insertafter — регулярное выражение, а не имя
строки. Если совпадений нет, строка дописывается в конец файла,
и задача завершается успешно: успешная задача не означает, что строка
оказалась там, где ждали. Параметр insertbefore вставляет перед
найденной строкой, а специальное значение insertafter: EOF означает
«в конец файла».

ВТОРОЙ приём. Строка в файле есть, и её надо убрать — state: absent
вместе с regexp:

  - name: Убрать разрешение входа по паролю для локальной сети
    ansible.builtin.lineinfile:
      path: /etc/ssh/sshd_config.d/20-sshd-hardening.conf
      regexp: '^Match Address 10\.0\.2\.0/24$'
      state: absent
      validate: "sshd -t -f %s"

ВАЖНО: при state: absent параметр line не нужен, а regexp обязателен.
Без regexp модуль не знает, что удалять, и задача падает. Это защита
от удаления строки по имени, но не защита от слишком широкого
выражения: regexp '^#' снесёт все комментарии в файле.

ТРЕТИЙ приём. Надо дописать строку, только если её нет, и никогда
не заменять существующую. Так делают, когда значением управляет
кто-то другой, а нам важно не дать строке пропасть:

  - name: Дописать баннер входа, если его ещё нет
    ansible.builtin.lineinfile:
      path: /etc/ssh/sshd_config.d/20-sshd-hardening.conf
      line: "Banner /etc/issue.net"
      insertafter: EOF
      create: true
      validate: "sshd -t -f %s"

Параметр create: true создаёт файл, если его вдруг нет. Как и state:
touch из шага 7, он полезен, когда файл может отсутствовать, но
не должен затирать содержимое.

ЧЕТВЁРТЫЙ приём. backrefs: true меняет поведение модуля на
противоположное: если regexp не совпал, задача ничего не делает
и завершается успешно, а line не дописывается. Группы регулярного
выражения подставляются в line по номерам. Это приём из практики 11;
здесь важно запомнить, что backrefs убирает «дописывание в конец»,
из-за которого строки и размножаются. После правки конфигурации
смотрите не на строку changed, а на действующее значение:

  ssh engineer@web1 'sudo sshd -T | grep permitrootlogin'
  permitrootlogin no

=========================================================================
ШАГ 9. BLOCKINFILE: ЦЕЛЫЙ БЛОК ПОД УПРАВЛЕНИЕМ
=========================================================================

lineinfile управляет одной строкой. Когда строк несколько и они
связаны между собой, берут blockinfile: он кладёт в файл блок
и обрамляет его маркерами.

  # BEGIN ANSIBLE MANAGED BLOCK
  ...строки блока...
  # END ANSIBLE MANAGED BLOCK

Между этими двумя строками blockinfile считает своей территорией.
При каждом прогоне блок находится по маркерам, содержимое сравнивается
и заменяется целиком, если изменилось. Строки за пределами маркеров
не трогаются никогда — этим blockinfile и ценен.

Содержимое блока задаётся так же, как у copy: готовым файлом в src
или строкой в block. Строку удобно брать из файла через lookup:

  - name: Добавить машины стенда в /etc/hosts
    ansible.builtin.blockinfile:
      path: /etc/hosts
      block: "{{ lookup('ansible.builtin.file', 'conf/hosts.append') }}"
      marker: "# {mark} ANSIBLE MANAGED BLOCK: стенд курса"
      owner: root
      group: root
      mode: "0644"
      backup: true

Так содержимое блока видно в репозитории отдельно от плейбука,
а плейбук остаётся коротким. Содержимое файла
files/08_files/conf/hosts.append:

  10.0.2.5   control
  10.0.2.11  web1
  10.0.2.12  web2
  10.0.2.13  db1

Значение marker по умолчанию — английское «# {mark} ANSIBLE MANAGED
BLOCK», и трогать его без причины не стоит: блок ищут именно
по этой строке. Мы добавляем к ней пояснение, чтобы в файле
с несколькими управляемыми блоками было видно, чей это блок.
Подстановка {mark} обязательна: вместо неё Ansible пишет BEGIN или END.

Полный текст плейбука — в файле files/08_files/04_blockinfile.yml.
После задачи blockinfile он читает блок командой grep с changed_when:
false, ограничением failed_when: hosts_block.rc not in [0, 1]
и печатает строки через debug, чтобы результат был виден в отчёте,
а не только на узле.

  ansible-playbook 04_blockinfile.yml

  TASK [Показать строки блока] ***************************************
  ok: [web1] => {
      "hosts_block.stdout_lines": [
          "# BEGIN ANSIBLE MANAGED BLOCK: стенд курса",
          "# END ANSIBLE MANAGED BLOCK: стенд курса"
      ]
  }

Второй прогон даст changed=0. Теперь поменяйте в файле conf/hosts.append
одну строку и запустите снова: модуль найдёт границы блока по маркерам,
заменит содержимое между ними и снова даст changed=1, причём ровно
один раз — границы не размножатся.

ПОЧЕМУ ИМЕННО ТАК: blockinfile — компромисс между lineinfile
и template. template переписывает файл целиком и требует, чтобы весь
файл был наш. lineinfile правит по одной строке и не умеет «эти пять
строк всегда вместе». На файлах вроде /etc/hosts или
/etc/security/limits.conf blockinfile почти всегда уместнее, чем
пять задач lineinfile.

ЧЕГО НЕ ДЕЛАТЬ: не правьте вручную строки внутри управляемого блока.
Следующий прогон их затрёт, потому что блок заменяется целиком. Если
настройку надо менять руками — её место за пределами маркеров.

=========================================================================
ШАГ 10. REPLACE: ЗАМЕНА ПО ВСЕМУ ФАЙЛУ
=========================================================================

Третий инструмент правки — replace. Он не ищет строку целиком,
а заменяет все совпадения регулярного выражения во всём файле:

  - name: Заменить старый комментарий в настройках sshd
    ansible.builtin.replace:
      path: /etc/ssh/sshd_config.d/20-sshd-hardening.conf
      regexp: '^#\s*PermitRootLogin\s+.*$'
      replace: '# PermitRootLogin: изменено плейбуком практики 8'
      backup: true

  path      файл, в котором идёт замена.
  regexp    что искать.
  replace   на что заменить. Пустая строка удаляет найденное.
  backup    true — сохранить копию файла до замены.
  validate  проверить результат до подмены файла.
  after     искать только после строки, найденной по этому выражению.
  before    искать только до строки, найденной по этому выражению.

Параметры after и before задают не границы файла, а границы участка
поиска. Они нужны, когда одинаковые строки встречаются в файле
несколько раз, а менять надо только часть.

Отличие replace от lineinfile в двух словах: lineinfile следит
за тем, чтобы в файле была нужная строка; replace следит за тем,
чтобы не было ненужного образца. Первый — про описание состояния,
второй — про разовую уборку: переименование параметра после обновления
пакета, замена старого адреса сервера, чистка комментариев.

ЗАЧЕМ ЭТО В РАБОТЕ: replace хорошо работает как переходный шаг.
Например, после обновления пакета параметр переименовали, и надо
поправить конфигурации на сотне машин, не переписывая их целиком.
Если дальше файл снова становится управляемым блоком, replace
из плейбука убирают: состоянием управляет blockinfile.

ПОЧЕМУ ИМЕННО ТАК: регулярные выражения — отдельная большая тема,
и здесь мы берём только простейшие образцы: начало строки,
необязательный символ комментария, пробелы. Жадность, якоря, группы
и обратные ссылки разбираются в практике 11. Запомните главное: если
выражение не совпало, replace молча ничего не делает и задача
завершается успешно. Молчание — главная опасность этого модуля.
Поэтому перед запуском прогоните выражение на копии файла тем же
диалектом, что и Ansible: grep -nP (подробно в практике 11). Минута
проверки экономит прогон по всему парку.

=========================================================================
ШАГ 11. FIND И STAT: РЕШЕНИЯ ПО ФАЙЛАМ, А НЕ ПО ДОГАДКАМ
=========================================================================

Иногда решение зависит от того, что на машине уже есть. Гадать
(«наверное, каталог пустой») нельзя: ответ надо получить у машины.
Для этого два модуля.

stat сообщает про один объект: существует ли он, каталог это или файл,
каковы права, владелец, размер, время изменения. Результат кладут
в register и потом читают:

  - name: Узнать состояние каталога сайта
    ansible.builtin.stat:
      path: /var/www/html/site
    register: site_stat

Поля результата, которые нужны чаще всего: stat.exists — объект есть
или нет; stat.isdir, stat.isreg, stat.islnk — каталог, файл, ссылка;
stat.mode — права строкой из четырёх цифр, например 2755;
stat.pw_name и stat.gr_name — владелец и группа; stat.size — размер
в байтах; stat.mtime — время последнего изменения. Все поля сразу
видно в выводе debug с var: site_stat.

find ищет объекты по условиям и возвращает список: paths — где искать
(обязателен, список каталогов); patterns — образцы имён вроде '*.log',
это не регулярные выражения, а обычные маски оболочки; use_regex —
если true, patterns читаются как регулярные выражения; recurse — true,
если искать и во вложенных каталогах; file_type — file, directory,
link или any; age — отбор по возрасту (30d — старше 30 дней,
-1w — младше недели); size — отбор по размеру (10M — больше 10 МБ,
-10M — меньше); плюс подразумевается по умолчанию, его не пишут,
  а минус меняет направление;
hidden — учитывать скрытые файлы.

Задача «удалить старые файлы» делается в два шага: сначала find,
потом file с state: absent в цикле по найденному.

  - name: Найти архивы старше недели
    ansible.builtin.find:
      paths: /tmp
      patterns: 'site-*.tar.gz'
      age: 1w
      recurse: false
    register: old_builds

  - name: Удалить найденное
    ansible.builtin.file:
      path: "{{ item.path }}"
      state: absent
    loop: "{{ old_builds.files }}"
    loop_control:
      label: "{{ item.path }}"

ПОЧЕМУ ИМЕННО ТАК: два шага вместо одной команды shell с find -delete
дают то, чего команда дать не может. Список удаляемых файлов виден
в отчёте, а в режиме --check плейбук ничего не удалит, а покажет, что
удалил бы. С командой shell режим --check бессилен: Ansible не знает,
что она собирается сделать.

ЗАЧЕМ ЭТО В РАБОТЕ: find и stat превращают плейбук из инструкции
в программу, которая сначала смотрит, а потом решает. Отсюда растут
все условные задачи: удалить старое, если новое уже на месте;
перезапустить службу, только если конфигурация изменилась.

ЧЕГО НЕ ДЕЛАТЬ: не используйте find вместо file для проверки одного
объекта и не полагайтесь на то, что find вернул «всё». У параметра
recurse значение false по умолчанию, и на дереве каталогов модуль
вернёт только верхний уровень. Проверяйте это не по строке ok,
а по длине списка в отчёте.

=========================================================================
ШАГ 12. STAT И ASSERT: ПРОВЕРКА ПРЕДПОЛОЖЕНИЙ
=========================================================================

Данные, полученные stat и find, кто-то должен проверить. В инженерной
практике это делает assert: он превращает предположение в условие,
которое либо выполняется, либо останавливает плейбук с понятным
текстом. Условия пишутся на Jinja2 без фигурных скобок: значения
подставляются сами, а site_dir_stat.stat.mode == '2755' читается как
«права каталога ровно 2755», а не «примерно похожи».

  - name: Отказаться работать при расхождении
    ansible.builtin.assert:
      that:
        - site_dir_stat.stat.exists
        - site_dir_stat.stat.isdir
        - site_dir_stat.stat.mode == '2755'
        - site_dir_stat.stat.pw_name == 'root'
      fail_msg: >-
        Каталог /var/www/html/site: права {{ site_dir_stat.stat.mode }},
        владелец {{ site_dir_stat.stat.pw_name }}. Ожидалось 2755
        и root:root.
      success_msg: "Каталог сайта описан верно."
      quiet: true

Параметр quiet: true убирает строку успеха из вывода: так делают,
когда проверок много и в отчёте нужны только сработавшие. Обе
задачи — stat и assert — уже есть в файле
files/08_files/02_permissions.yml, и при верных правах вы увидите
только ok.

ЗАЧЕМ ЭТО В РАБОТЕ: assert — самый дешёвый способ поймать ошибку
на первом узле вместо последнего. Если каталог сайта не создан или
права разъехались, плейбук останавливается здесь и говорит, что
именно не так, а не падает через двадцать задач на попытке записать
файл в несуществующий каталог.

ВАЖНО: assert проверяет то, что вы уже получили. Если stat не
запускался, поля stat не существует, и условие упадёт с ошибкой
о неопределённой переменной, а не с вашим fail_msg. Правило простое:
сначала stat или find, потом assert по их результату, и только потом
действия, которые на этот результат опираются.

=========================================================================
ШАГ 13. АРХИВЫ: ARCHIVE И UNARCHIVE
=========================================================================

Каталог целиком удобно передавать архивом. В Ansible для этого два
модуля: archive упаковывает, unarchive распаковывает.

  - name: Упаковать каталог сайта в архив
    ansible.builtin.archive:
      path:
        - /var/www/html/site
      dest: "/tmp/site-{{ inventory_hostname }}.tar.gz"
      format: gz
      mode: "0640"

  path    что упаковать: путь или список путей. Обязателен.
  dest    имя архива. Обязателен.
  format  gz, bz2, xz, zip, tar. По умолчанию gz.
  remove  true — удалить исходные файлы после упаковки.
  mode    права на получившийся архив.

Имя архива собирается из inventory_hostname. Это не украшение: если
собирать архивы со всех машин в один каталог, без имени узла в имени
файла они затрут друг друга, и заметите вы это только при распаковке.

Теперь распаковка. Здесь есть параметр, который путают чаще всего:
remote_src: false (по умолчанию) означает, что архив сначала
копируется на управляемый узел с управляющей машины, а потом
распаковывается там; remote_src: true — что архив уже лежит
на управляемом узле и копировать его не надо. Отсюда правило:
распаковываете свой архив, собранный на управляющей машине, — пишите
remote_src: false или не пишите его вообще; распаковываете архив,
который уже лежит на узле, — обязательно remote_src: true.

  - name: Распаковать архив на узле, если он ещё не распакован
    ansible.builtin.unarchive:
      src: "/tmp/site-{{ inventory_hostname }}.tar.gz"
      dest: /srv/site_build
      remote_src: true
      creates: /srv/site_build/site/index.html
      owner: root
      group: root
      mode: "0644"

Параметр creates: если указанный путь уже существует, распаковка
не выполняется вообще — так делают для операций, которые нельзя
повторять. Параметр extra_opts передаёт дополнительные ключи для tar;
в этой практике он нужен редко.

Полный текст плейбука — в файле files/08_files/05_archive.yml. Там
есть переменные site_dir, build_dir и archive_path (имя архива
/tmp/site-<имя узла>.tar.gz), задача file для каталога сборки
и задача unarchive с creates: "{{ build_dir }}/site/index.html".
Кроме сборки и распаковки в нём есть задача fetch, которая забирает
архив на управляющую машину (flat: true означает «положить файл прямо
в dest, не создавая дерево каталогов узла»), и задача command
с tar -tzf, которая печатает список файлов в архиве:

  ansible-playbook 05_archive.yml

  TASK [Показать список файлов в архиве] *****************************
  ok: [web1] => {
      "archive_list.stdout_lines": [
          "var/www/html/site/index.html"
      ]
  }

Второй прогон даст changed=0 у задач file и unarchive, но задача
archive пересоберёт архив: у этого модуля нет условия «не пересобирать,
если содержимое не менялось» — проверять дерево дороже, чем собрать
архив заново. Если повторная сборка мешает, добавьте условие
when: not archive_stat.stat.exists по результату stat.

ПОЧЕМУ ИМЕННО ТАК: archive — инструмент передачи, а не резервного
копирования. Ежедневные резервные копии делает не плейбук Ansible,
а специализированная система, которая умеет хранение, ротацию
и восстановление.

ВАЖНО: бинарные файлы и архивы в репозиторий курса не кладут. Каталог
files/08_files содержит только текстовые файлы: страницу, таблицу
стилей, образцы конфигураций и шаблон. Архив создаётся на стенде
прогоном плейбука — ровно так, как мы это только что сделали.

=========================================================================
ШАГ 14. ИТОГ: САЙТ, ПРАВА И ПОВТОРНЫЙ ПРОГОН
=========================================================================

На web1 и web2 сейчас должно быть: каталог /var/www/html/site
с правами 2755 и владельцем root:root; файлы index.html и style.css
с правами 0644 внутри него; файл /etc/cron.d/site-check с заданием
из шаблона cron.j2; файл /etc/ssh/sshd_config.d/20-sshd-hardening.conf
с двумя настройками и правами 0644; блок машин стенда в /etc/hosts
между маркерами BEGIN и END; архив /tmp/site-web1.tar.gz и его копия
в каталоге backup/ на управляющей машине.

Каждый пункт появился из описания состояния, а не из команды.
Проверим это прогоном всех плейбуков подряд. Порядок важен: сначала
каталог и файлы, потом права, потом конфигурации, потом архив.

  cd ~/ansible-lab
  ansible-playbook 01_copy.yml
  ansible-playbook 02_permissions.yml
  ansible-playbook 03_lineinfile.yml
  ansible-playbook 04_blockinfile.yml
  ansible-playbook 05_archive.yml

  PLAY RECAP ********************************************************
  web1  : ok=...  changed=1  unreachable=0  failed=0
  web2  : ok=...  changed=1  unreachable=0  failed=0

Один changed из пяти плейбуков — пересборка архива из шага 13. Всё
остальное уже в описанном состоянии, и обработчик перезапуска SSH
в отчёт не попадает: уведомлять его нечем, задачи ничего не меняют.

ЗАЧЕМ ЭТО В РАБОТЕ: такой прогон — не учебное упражнение, а обычная
проверка перед тем, как отдать плейбук коллегам. Если повторный
прогон что-то меняет, значит, описание неполное: где-то состояние
зависит от того, что было раньше, а не от того, что должно быть.
Именно эту проверку в практике 16 будет делать molecule.

Посмотрим на дерево и права целиком, одной командой:

  ssh engineer@web1 'find /var/www/html -printf "%M %u:%g %p\n"'

  drwxr-sr-x root:root /var/www/html/site
  -rw-r--r-- root:root /var/www/html/site/index.html
  -rw-r--r-- root:root /var/www/html/site/style.css

Буква s в правах каталога — это setgid из шага 6. Файлы читаются
всеми и не пишутся никому, кроме root: ровно то, что нужно
для статического сайта. Код 200 на обеих машинах означает, что
каталог доступен на чтение и веб-сервер отдаёт файл:

  for h in 10.0.2.11 10.0.2.12; do
      curl -s -o /dev/null -w "$h %{http_code}\n" http://$h/site/
  done
  10.0.2.11 200
  10.0.2.12 200

Если на одной машине 200, а на другой 403, сравните вывод find
с примером выше: почти всегда дело в правах на каталог, а не
в содержимом файла.

=========================================================================
ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: Destination directory /var/www/html/site does not exist

  fatal: [web1]: FAILED! => {"changed": false, "msg": "Destination
  directory /var/www/html/site does not exist"}

Модуль copy не создаёт промежуточные каталоги: он кладёт файл в уже
существующий каталог. Порядок проверки: каталог действительно есть
(ls -ld /var/www/html/site); в плейбуке перед копированием есть задача
file со state: directory — именно она создаёт каталог, а не copy;
путь в dest совпадает с путём в задаче file буква в букву, потому что
разница между site и site/ меняет результат копирования (шаг 4);
переменная в path не пустая — пустое значение превращает путь
в /var/www/html, и копирование идёт не туда.

ИСПРАВЛЕНО: в прежней версии курса отдельной задачи, создающей
каталог, не было: предполагалось, что каталог появился при установке
веб-сервера. На чистой машине это не так, и практика падала на первой
же задаче копирования. В новой версии каталог сайта описывается
отдельной задачей с именем, и в отчёте видно, что он был создан.

ПРОБЛЕМА: mode must be in octal or symbolic notation

  fatal: [web1]: FAILED! => {"changed": false, "msg": "mode must be in
  octal or symbolic notation"}

Модуль получил значение, которое не является ни числом в восьмеричной
записи, ни символической записью. Порядок проверки: как записаны права
в задаче — правильно mode: "0644" строкой в кавычках, а число 644
в YAML читается как десятичное, и это другое значение; нет ли
арифметики в выражении вроде mode: "{{ file_mode + 0 }}" — она даёт
число, а не строку прав; нет ли пробелов в переменной из group_vars
(значение " 0644" ломает разбор); есть ли поле mode у элемента цикла,
когда задача написана как mode: "{{ item.mode }}".

ПРОБЛЕМА: lineinfile вставляет строку повторно при каждом прогоне

  TASK [Запретить вход по паролю] ***********************************
  changed: [web1]

  ssh engineer@web1 'grep -n PasswordAuthentication /etc/ssh/sshd_config.d/20-sshd-hardening.conf'
  3:PasswordAuthentication no
  9:PasswordAuthentication no

Модуль не нашёл строку по регулярному выражению и каждый раз дописывал
новую. Причина всегда одна: regexp не совпадает с тем, что реально
лежит в файле. Порядок проверки: что именно в файле — сравните строку
посимвольно, включая пробелы и регистр (cat -A покажет скрытые
символы); не якорьте лишнего, потому что '^PasswordAuthentication no$'
не совпадёт со строкой, в конце которой есть пробел; помните, что
точка в выражении — любой символ, а не точка, для точки пишут \.
(практика 11); уберите дубликаты, исправив regexp и удалив лишние
строки тем же модулем со state: absent.

ЧЕГО НЕ ДЕЛАТЬ: не «лечите» это параметром insertafter: EOF. Строка
всё равно будет добавляться на каждом прогоне, потому что поиск идёт
по regexp, а insertafter задаёт только место вставки.

ПРОБЛЕМА: validate не пропускает файл, и он не подменяется

  fatal: [web1]: FAILED! => {"changed": false, "msg": "failed to
  validate: sshd -t -f /home/engineer/.ansible/tmp/.../sshd_config
  line 3: Bad configuration option: PermitRootLoginn"}

Это правильное поведение, и оно спасло вам доступ к машине.
Порядок проверки: прочитайте текст ошибки от validate — в нём указан
номер строки и имя параметра, этого достаточно, чтобы найти опечатку;
убедитесь, что файл на узле не изменился, ведь Ansible подменяет файл
только после успешной проверки; проверьте, что валидатор вызывается
с нужным файлом — на месте имени файла обязан стоять %s, иначе
проверка пойдёт по основному конфигу, а не по изменённому.

ВАЖНО: не убирайте validate, чтобы «плейбук прошёл». Задача с ошибкой
в конфигурации обязана падать. Если sshd не стартует после перезапуска,
вы теряете доступ к машине по SSH, то есть теряете её совсем.

ПРОБЛЕМА: unarchive не находит файл, хотя он есть на узле

  fatal: [web1]: FAILED! => {"changed": false, "msg": "Could not find
  or access '/tmp/site-web1.tar.gz' on the Ansible Controller."}

Модуль unarchive по умолчанию считает, что архив лежит на управляющей
машине, и ищет его там. Порядок проверки: где на самом деле файл —
если на узле, в задаче нужен remote_src: true; существует ли путь
в src на управляющей машине, когда remote_src не указан; не пустой
ли архив, потому что нулевой файл проходит проверку на существование
и падает уже при распаковке, с сообщением от tar. Правило простое:
архив создан плейбуком на узле — значит, распаковывается на узле,
значит, remote_src: true; архив лежит в репозитории или собран
на управляющей машине — remote_src не указываем.

ПРОБЛЕМА: chmod: changing permissions: Operation not permitted

  fatal: [web1]: FAILED! => {"changed": false, "msg": "chmod failed",
  "stdout": "chmod: changing permissions of
  '/var/www/html/site/index.html': Operation not permitted"}

Задача выполняется без прав root, а файл принадлежит другому
пользователю. Порядок проверки: есть ли в play ключ become: true —
владельца и права меняет только root; как ведёт себя sudo, потому что
без NOPASSWD из практики 1 задача падает иначе, с сообщением про
пароль; не стоит ли на файле иммутабельный атрибут chattr +i, который
не отменяет даже root; не смонтирована ли файловая система только
для чтения — это видно в выводе команды mount по признаку ro.

ПРОБЛЕМА: файлы на месте, но браузер отдаёт 403 Forbidden

Содержимое скопировано, задача завершилась успешно, а страница
не открывается. Порядок проверки: права на каталог, потому что
у каталога обязан быть бит x для тех, кто читает файл внутри,
а каталог с правами 0644 — типовая причина; права на файл, которых
0644 достаточно, так как файлу бит x не нужен; директива веб-сервера,
если сайт лежит вне /var/www/html, ведь по умолчанию выход
из каталога запрещён; имя файла — он должен называться именно
index.html, и список файлов в каталоге покажет это за секунду.

ИСПРАВЛЕНО: в прежней версии курса содержимое сайта копировалось
с правами mode=0555: «чтобы никто не испортил». Файл с 0555 нельзя
перезаписать, не сняв права, поэтому следующая задача обновления сайта
падала, а руками файл правился только через sudo chmod. В новой
версии на файлы ставятся 0644: сайт отдаётся на чтение, а менять его
может только root, то есть плейбук.

ЧЕГО НЕ ДЕЛАТЬ: не правьте конфигурацию задачей вида
shell: sed -i 's/PermitRootLogin yes/PermitRootLogin no/' с файлом
/etc/ssh/sshd_config. Она делает то же самое, но у неё три изъяна:
она сообщает changed при каждом прогоне, потому что Ansible не знает,
изменила ли команда файл; она не проверяет конфигурацию до подмены,
поэтому опечатка в выражении закрывает доступ к машине; она не
создаёт копию файла и не оставляет в отчёте следа о том, какая строка
заменена. Модуль lineinfile решает все три вопроса сразу.

ИСПРАВЛЕНО: в прежней версии курса права ставились значением mode=777
«чтобы точно заработало». На файлах сайта это означает, что содержимое
страницы может переписать любой пользователь машины, а на каталогах —
что любой может удалить чужие файлы. В новой версии права описываются
по назначению: 0644 на файлы, 0755 на каталоги и 2755 на каталог сайта
с битом setgid.

1. Содержимое сайта лежит на обеих машинах, права описаны верно:

     ssh engineer@web1 'find /var/www/html/site -printf "%M %u:%g %p\n"'
     drwxr-sr-x root:root /var/www/html/site
     -rw-r--r-- root:root /var/www/html/site/index.html

   Буква s в правах группы каталога — бит setgid из шага 6.

2. Страница отдаётся веб-сервером на обеих машинах:

     for h in 10.0.2.11 10.0.2.12; do
         curl -s -o /dev/null -w "$h %{http_code}\n" http://$h/site/
     done
     10.0.2.11 200
     10.0.2.12 200

3. Задание cron разложено из шаблона и имеет правильные права:

     ssh engineer@web1 'ls -l /etc/cron.d/site-check; cat /etc/cron.d/site-check'
     -rw-r--r-- 1 root root ... /etc/cron.d/site-check
     # Ansible managed
     17 4 * * * root /usr/bin/logger "web1: плановая проверка сайта"

4. Настройки sshd лежат в отдельном файле, и sshd их принимает.
   Проверка идёт командой sshd -T, а не чтением файла: важно
   действующее значение, а не то, что написано в нашем файле.

     ssh engineer@web1 'sudo sshd -T | grep -E "permitrootlogin|passwordauthentication"'
     permitrootlogin no
     passwordauthentication no

5. Блок в /etc/hosts обрамлён маркерами и не размножился:

     ssh engineer@web1 'grep -c "ANSIBLE MANAGED BLOCK" /etc/hosts'
     2

   Два вхождения — BEGIN и END. Если число больше, блок был добавлен
   повторно, и причину надо искать в параметре marker.

6. Архив собран и забран на управляющую машину:

     ls -l backup/web1/
     -rw-r----- 1 engineer engineer ... site-web1.tar.gz

7. Повторный прогон пяти плейбуков даёт changed только у архива:

     ansible-playbook 01_copy.yml
     ansible-playbook 02_permissions.yml
     ansible-playbook 03_lineinfile.yml
     ansible-playbook 04_blockinfile.yml
     ansible-playbook 05_archive.yml
     web1  : changed=1  failed=0
     web2  : changed=1  failed=0

   Один changed — пересборка архива из шага 13, и это ожидаемо.
   Обработчик перезапуска SSH в changed не попадает: ни одна задача
   его не уведомила, поэтому в отчёте он не появляется вовсе.

УБИРАТЬ ЗА СОБОЙ: частично. Каталог /srv/site_build и архивы
в /tmp на узлах в следующей практике не нужны:

  ansible web -b -m ansible.builtin.file -a "path=/srv/site_build state=absent"
  ansible web -b -m ansible.builtin.shell -a "rm -f /tmp/site-*.tar.gz"

Второй командой мы сознательно пользуемся shell: модуль file не
понимает маски в имени. Если такая уборка нужна регулярно, её пишут
плейбуком через find и file со state: absent, как в шаге 11.

Настройки sshd и блок в /etc/hosts убирать не нужно: они остаются
на узлах до конца курса. Сайт в /var/www/html/site тоже остаётся:
в практике 10 его заменит роль web_admin.
