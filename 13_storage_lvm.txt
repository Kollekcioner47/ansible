=========================================================================
ШАГ 1. ФИЗИЧЕСКИЙ ТОМ, ГРУППА ТОМОВ И ЛОГИЧЕСКИЙ ТОМ
=========================================================================

Диск — это набор секторов. Чтобы хранить на нём файлы, нужны три слоя:
таблица разделов (какие области диска кому принадлежат), файловая
система (как внутри области лежат файлы) и точка монтирования (где
файловая система видна в дереве каталогов).

LVM добавляет между разделом и файловой системой ещё один слой:

  * ФИЗИЧЕСКИЙ ТОМ (PV) — раздел или диск, отданный под LVM: в практике
    /dev/sdb1. Его создаёт pvcreate, и это делает модуль lvg;
  * ГРУППА ТОМОВ (VG) — пул места из физических томов: в практике
    группа data. Место в ней нарезается экстентами по 4 МиБ;
  * ЛОГИЧЕСКИЙ ТОМ (LV) — «раздел внутри пула», его получает файловая
    система: в практике webdata.

  /dev/sdb1       группа томов data      логический том webdata
  физический  ->  пул 10 ГБ, из них  ->  /dev/mapper/data-webdata
  том             6 ГБ отдано тому           |
                                             v
                                     ext4 или xfs на /srv/data

У логического тома два имени, и оба ведут к одному устройству:
/dev/mapper/data-webdata и /dev/data/webdata. В плейбуках курса
используется первое: оно одинаково на обоих семействах ОС.

ЗАЧЕМ ЭТО В РАБОТЕ: без LVM, чтобы увеличить раздел, его пришлось бы
размонтировать и пересоздать. С LVM место добавляется на ходу, без
остановки сервиса.

ЧЕГО НЕ ДЕЛАТЬ: не заводите LVM, если в пул нечего будет добавить,
и не выбирайте тип файловой системы «по вкусу»: различие описано
переменной, а не размножено по задачам условиями when.

ШАГ 2. ФАЙЛЫ ПРАКТИКИ И ПЕРЕМЕННЫЕ ПО СЕМЕЙСТВАМ
=========================================================================

Копируем файлы практики в рабочий каталог курса. Каталог vars
копируется целиком — плейбуки ссылаются на него по имени:

  cd ~/ansible-lab
  cp -r /путь/к/репозиторию/files/13_storage_lvm/. .
  ls
  01_inspect.yml  02_parted.yml  03_lvm.yml  04_filesystem.yml
  05_mount.yml  06_resize.yml  07_full_storage.yml  vars

Различия между Ubuntu и Rocky Linux собраны в два файла переменных,
как в практике 9. Файл для Ubuntu — files/13_storage_lvm/vars/Debian.yml:

  ---
  # Переменные семейства Debian (Ubuntu 26.04): web1 и web2.
  # Файл читается задачей ansible.builtin.include_vars в pre_tasks —
  # так же, как vars/Debian.yml в практике 9.

  # Второй диск стенда: 10 ГБ, есть только на управляемых узлах.
  # Учебное значение. В рабочем проекте диск задают переменной группы,
  # а не литералом внутри плейбука.
  storage_disk: /dev/sdb
  storage_partition: "{{ storage_disk }}1"

  # Имена из единого реестра сущностей курса: группа томов data,
  # логический том webdata, точка монтирования /srv/data.
  storage_vg: data
  storage_lv: webdata
  storage_mount: /srv/data

  # Размер логического тома: начальный (шаг 5) и после расширения
  # (шаги 8 и 9). Точное число, а не процент: процент от свободного места
  # не идемпотентен — на каждом прогоне он разный.
  storage_lv_size: 6G
  storage_lv_size_extended: 8G

  # Файловая система: на Ubuntu — ext4, на Rocky Linux — xfs.
  storage_fstype: ext4

  # Чем расширяется файловая система: ext4 растёт resize2fs,
  # xfs — xfs_growfs. Модуль выбирает инструмент сам, эти имена
  # нужны для объяснения и для ручных проверок.
  storage_grow_tool: resize2fs

  # Опции монтирования для /etc/fstab. noatime рядом с defaults:
  # на диске с данными не нужно записывать время доступа при чтении.
  storage_mount_opts: "defaults,noatime"

  # Пакеты для работы с дисками и файловыми системами. Имена пакетов
  # совпадают с RedHat-семейством, а набор инструментов разный.
  storage_packages:
    - parted
    - lvm2
    - e2fsprogs

Файл для Rocky Linux — files/13_storage_lvm/vars/RedHat.yml. Имена
переменных те же, значения другие; ниже — отличающиеся строки
(полностью файл лежит в каталоге курса):

  # xfs умеет расти на смонтированной файловой системе,
  # но не умеет уменьшаться.
  storage_fstype: xfs

  # Инструмент xfs работает с точкой монтирования, а не с устройством.
  storage_grow_tool: xfs_growfs

  # mkfs.xfs живёт в пакете xfsprogs.
  storage_packages:
    - parted
    - lvm2
    - xfsprogs

Файл выбирается по факту ansible_os_family, значение которого — Debian
или RedHat. Подключается он задачей include_vars в pre_tasks:

  pre_tasks:
    - name: "Прочитать переменные для семейства ОС"
      ansible.builtin.include_vars:
        file: "vars/{{ ansible_os_family }}.yml"

ПОЧЕМУ ИМЕННО ТАК: include_vars читает файл во время прогона, когда
факты уже собраны, поэтому «vars/{{ ansible_os_family }}.yml»
превращается в vars/Debian.yml на web1 и в vars/RedHat.yml на db1.
Читается он в pre_tasks — до первой задачи, которой нужны переменные.

ПРОВЕРКА: переменные storage_* лежат в vars/ и подключаются задачей
include_vars внутри плейбука — в ad-hoc команде их нет, и debug
с var=storage_fstype ответит VARIABLE IS NOT DEFINED!. Смотреть надо
на саму машину: какая файловая система у неё основная.

  ansible web1 -b -m ansible.builtin.setup -a "filter=ansible_mounts"
  web1 | SUCCESS => {
      "ansible_facts": {
          "ansible_mounts": [
              { "device": "/dev/sda1", "mount": "/", "fstype": "ext4", ... }
          ]
      },
      "changed": false
  }
  ansible db1 -b -m ansible.builtin.setup -a "filter=ansible_mounts"
  db1 | SUCCESS => {
      "ansible_facts": {
          "ansible_mounts": [
              { "device": "/dev/sda1", "mount": "/", "fstype": "xfs", ... }
          ]
      },
      "changed": false
  }

Задача include_vars выбирает файл по факту ansible_os_family:
vars/Debian.yml на web1 и web2, vars/RedHat.yml на db1 — и там
storage_fstype равен ext4 или xfs. Тот же тип получит том
в /srv/data, и в шаге 6 его показывает blkid: TYPE="ext4"
на web1 и TYPE="xfs" на db1.

=========================================================================
ШАГ 3. ОСМОТР ДИСКОВ: LSBLK, BLKID, FINDMNT, DF -H
=========================================================================

Перед разметкой нужно посмотреть на диск: у команд разметки нет отмены.
Смотреть надо четыре вещи: какие устройства есть и какого они размера
(lsblk), есть ли на диске файловая система (blkid), не смонтировано ли
с него что-то (lsblk, findmnt) и сколько места на корне (df -h).

Плейбук files/13_storage_lvm/01_inspect.yml:

  ---
  # 01_inspect.yml — практика 13, шаг 3: осмотр дисков до любых изменений.
  # Плейбук только читает состояние: здесь нет ни одной задачи,
  # которая что-то меняет на узле.
  # Запуск из каталога ~/ansible-lab:
  #   ansible-playbook 01_inspect.yml

  - name: "Осмотр дисков до разметки"
    hosts: linux
    become: true

    pre_tasks:
      ... include_vars для vars/{{ ansible_os_family }}.yml ...

    tasks:
      - name: "Показать блочные устройства узла"
        ansible.builtin.command:
          cmd: lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINT
        register: lsblk_result
        changed_when: false

      - name: "Вывести дерево блочных устройств"
        ansible.builtin.debug:
          var: lsblk_result.stdout_lines

      - name: "Проверить, что второй диск существует"
        ansible.builtin.stat:
          path: "{{ storage_disk }}"
        register: disk_stat

      - name: "Посмотреть, что смонтировано со второго диска"
        ansible.builtin.command:
          cmd: "lsblk -n -o MOUNTPOINT {{ storage_disk }}"
        register: disk_mounts
        changed_when: false

      - name: "Остановиться, если диска нет или с него что-то смонтировано"
        ansible.builtin.assert:
          that:
            - disk_stat.stat.exists
            - disk_stat.stat.isblk
            - disk_mounts.stdout | trim == ""
          fail_msg: >-
            Диск {{ storage_disk }} не найден или с него что-то смонтировано.
            Дальше диск будет размечаться, поэтому работа остановлена.
          success_msg: "Диск {{ storage_disk }} свободен: размечать можно."

      - name: "Посмотреть, есть ли на диске файловая система"
        ansible.builtin.command:
          cmd: "blkid {{ storage_disk }}"
        register: blkid_result
        changed_when: false
        failed_when: false

      - name: "Вывести ответ blkid вместе с кодом возврата"
        ansible.builtin.debug:
          msg: "rc={{ blkid_result.rc }} stdout={{ blkid_result.stdout }}"

      ... ещё задача: findmnt --source раздела и вывод кода возврата ...

Запускаем:

  ansible-playbook 01_inspect.yml

  TASK [Показать блочные устройства узла] ***
  ok: [web1]
  ok: [web2]
  ok: [db1]

Задача с lsblk отчитывается ok, а не changed: параметр changed_when: false
говорит Ansible, что команда ничего не меняет. Это тема шага 10.

Вывод задачи «Вывести дерево блочных устройств» (сокращён):

  ok: [web1] => {
      "lsblk_result.stdout_lines": [
          "NAME   SIZE TYPE FSTYPE MOUNTPOINT",
          "sda     20G disk",
          "├─sda1  19G part ext4   /",
          "sdb     10G disk"
      ]
  }

ВАЖНО: blkid на чистом диске отвечает rc=2 и пустым stdout. Это не сбой,
а ответ «файловой системы нет»: поэтому у задачи failed_when: false.
Если бы в stdout был TYPE="ext4", разметку надо остановить.

ЧЕГО НЕ ДЕЛАТЬ: не начинайте разметку, если осмотр не запускался:
в работе смотрят ещё lsscsi, lsof, pvs и vgs.


=========================================================================
ШАГ 4. РАЗМЕТКА ВТОРОГО ДИСКА: COMMUNITY.GENERAL.PARTED
=========================================================================

ЧЕГО НЕ ДЕЛАТЬ: не запускайте этот плейбук на рабочей машине и на
своём компьютере. Модуль создаёт таблицу разделов на устройстве из
параметра device: если там окажется диск с данными, данные пропадут
молча. И не подставляйте имя диска прямо в задачу: устройство должно
приходить переменной storage_disk, потому что на другом стенде это
может быть /dev/vdb или /dev/nvme0n1, а на NVMe раздел называется
иначе — не /dev/sdb1, а /dev/nvme0n1p1. В наших файлах значение задано
в vars, и его можно переопределить для группы, хоста или ключом -e.

Плейбук files/13_storage_lvm/02_parted.yml:

  ---
  # 02_parted.yml — практика 13, шаг 4: разметка второго диска.
  #
  # ОПАСНО: плейбук размечает диск. Работать только на учебном стенде
  # и только со вторым диском. Запуск такого плейбука на машине с данными
  # уничтожит эти данные: модуль с другим label переписывает таблицу
  # разделов целиком.
  #
  # Запуск из каталога ~/ansible-lab:
  #   ansible-playbook 02_parted.yml

  - name: "Разметка второго диска"
    hosts: linux
    become: true

    pre_tasks:
      ... include_vars для vars/{{ ansible_os_family }}.yml ...

    tasks:
      ... пакеты: parted, lvm2 и инструменты файловых систем ...

      - name: "Проверить, что второй диск существует"
        ansible.builtin.stat:
          path: "{{ storage_disk }}"
        register: disk_stat

      - name: "Посмотреть, что смонтировано со второго диска"
        ansible.builtin.command:
          cmd: "lsblk -n -o MOUNTPOINT {{ storage_disk }}"
        register: disk_mounts
        changed_when: false

      - name: "Остановиться, если диска нет или с него что-то смонтировано"
        ansible.builtin.assert:
          that:
            - disk_stat.stat.exists
            - disk_stat.stat.isblk
            - disk_mounts.stdout | trim == ""
          fail_msg: >-
            Диск {{ storage_disk }} не найден или с него что-то смонтировано.
            Разметка уничтожит данные, поэтому плейбук остановлен.
          success_msg: "Диск {{ storage_disk }} свободен, можно размечать."

      - name: "Создать таблицу разделов GPT и раздел 1 на весь диск"
        community.general.parted:
          device: "{{ storage_disk }}"
          number: 1
          label: gpt
          name: data
          flags:
            - lvm
          state: present
        register: parted_result

      - name: "Попросить ядро перечитать таблицу разделов"
        ansible.builtin.command:
          cmd: "partprobe {{ storage_disk }}"
        when: parted_result.changed

      - name: "Дождаться, пока ядро увидит раздел"
        ansible.builtin.command:
          cmd: "lsblk -n -o NAME {{ storage_partition }}"
        register: part_check
        changed_when: false
        retries: 5
        delay: 2
        until: part_check.rc == 0

      - name: "Прочитать сведения о диске после разметки"
        community.general.parted:
          device: "{{ storage_disk }}"
          number: 1
          unit: MiB
          state: info
        register: disk_after

      - name: "Проверить, что раздел создан и помечен флагом lvm"
        ansible.builtin.assert:
          that:
            - disk_after.partitions | length == 1
            - "'lvm' in disk_after.partitions[0].flags"
          fail_msg: "Раздела с флагом lvm на {{ storage_disk }} нет."
          success_msg: "Раздел 1 на {{ storage_disk }} создан и помечен lvm."

РАЗБОР ПАРАМЕТРОВ:
  * device — диск, с которым работаем; number — номер раздела, без него
    модуль не станет ничего делать;
  * label — тип таблицы разделов. Берём gpt вместо старой msdos:
    нет предела в четыре раздела, у разделов есть имена; name задаёт
    имя раздела, для GPT его принято указывать;
  * flags: [lvm] — пометка «раздел отдан под LVM»: файловой системы
    на нём нет, а пометка видна в parted и lsblk;
  * state: present — раздел должен существовать;
  * part_start и part_end — границы раздела, по умолчанию 0% и 100%.
    В задаче они не указаны намеренно: у существующего раздела модуль
    их не проверяет — ловушка шага 10.

ПОЧЕМУ МОДУЛЬ, А НЕ SHELL С PARTED. Модуль сначала читает состояние
диска и только потом решает, что делать. Если раздел уже есть, он
ничего не создаёт и отчитывается ok. Команда parted в shell выполняется
всегда: повторный запуск на размеченном диске пересоздаёт таблицу
разделов и уничтожает данные. Кроме того, модулю нужна утилита parted
на узле — её ставит первая задача файла. Сам модуль живёт в коллекции
community.general: короткое имя parted в плейбуке не найдётся.

Что происходит при запуске (сокращённо):

  ansible-playbook 02_parted.yml

  TASK [Создать таблицу разделов GPT и раздел 1 на весь диск]
  changed: [web1] => {
      "changed": true,
      "disk": { ... "dev": "/dev/sdb", "table": "gpt" ... },
      "partitions": [
          { "begin": 1.0, "end": 10240.0, "flags": ["lvm"],
            "fstype": "", "name": "data", "num": 1 }
      ]
  }
  changed: [web2]
  changed: [db1]

ВАЖНО, ПРО ЯДРО И РАЗДЕЛ. После разметки файл устройства /dev/sdb1
обычно появляется сразу: таблицу перечитывает udev. Но в виртуалке
ядро может узнать о разделе не сразу, и следующая задача упадёт
с сообщением Device /dev/sdb1 not found. Поэтому таблицу перечитывают
командой partprobe и ждут появления раздела в lsblk. Команда выполняется
только после изменения таблицы (when), на втором прогоне пропускается.

ПРОВЕРКА: посмотрите на диск со стороны системы:

  ansible all -b -m ansible.builtin.command -a "lsblk -o NAME,SIZE,TYPE,FSTYPE /dev/sdb"
  NAME   SIZE TYPE FSTYPE
  sdb     10G disk
  └─sdb1  10G part

  ansible all -b -m ansible.builtin.command -a "parted /dev/sdb unit MiB print"
  Partition Table: gpt
  Number  Start    End       Size      File system  Name  Flags
   1      1.00MiB  10240MiB  10239MiB               data  lvm

ЗАЧЕМ ЭТО В РАБОТЕ: пометка lvm и имя раздела нужны людям, а не
файловой системе: по выводу parted видно, что это за устройство.

ШАГ 5. ГРУППА ТОМОВ DATA И ЛОГИЧЕСКИЙ ТОМ WEBDATA

Файл files/13_storage_lvm/03_lvm.yml:

  ---
  # 03_lvm.yml — практика 13, шаг 5: группа томов data и логический том webdata.
  # Запуск из каталога ~/ansible-lab:
  #   ansible-playbook 03_lvm.yml

  - name: "LVM: группа томов и логический том"
    hosts: linux
    become: true

    pre_tasks:
      ... include_vars для vars/{{ ansible_os_family }}.yml ...

    tasks:
      ... пакеты: parted, lvm2 и инструменты файловых систем ...

      - name: "Создать группу томов data на разделе второго диска"
        community.general.lvg:
          vg: "{{ storage_vg }}"
          pvs:
            - "{{ storage_partition }}"
          state: present

      - name: "Создать логический том webdata начального размера"
        community.general.lvol:
          vg: "{{ storage_vg }}"
          lv: "{{ storage_lv }}"
          size: "{{ storage_lv_size }}"
          shrink: false
          state: present

      ... ещё задача: вывод vgs для проверки ...

РАЗБОР:
  * community.general.lvg описывает группу томов: vg — имя, pvs —
    список физических томов. Модуль сам выполнит pvcreate для нового
    раздела и vgcreate для группы, а если группа уже есть, но список
    pvs вырос, — vgextend;
  * community.general.lvol описывает логический том: vg — группа,
    lv — имя, size — размер, state: present — «том должен быть»;
  * shrink: false — осознанное решение. По умолчанию модуль считает
    уменьшение тома допустимым и при размере меньшем, чем текущий,
    пытается уменьшить том, а уменьшение без force: true запрещено,
    и задача падает. В практике файлы шагов описывают разные размеры
    одного тома: шаг 5 — 6G, шаг 8 — 8G. Без shrink: false повторный
    прогон шага 5 отматывал бы состояние назад.

ЗАЧЕМ ЭТО В РАБОТЕ: место в группе нарезается экстентами, по умолчанию
по 4 МиБ, и экстент задаёт шаг, с которым можно менять размер. Размер
экстента фиксирует параметр pesize модуля lvg; если группа создана
с другим размером, изменить его нельзя.

ПРОВЕРКА: смотрим состояние LVM:

  ansible all -b -m ansible.builtin.command -a "vgs"

    data   1   1   0 wz--n- <10.00g <4.00g

  ansible all -b -m ansible.builtin.command -a "lvs --units g"
    LV      VG   Attr       LSize
    webdata data -wi-ao---- 6.00g

Свободного места меньше четырёх гигабайт, хотя том занимает шесть

ШАГ 6. ФАЙЛОВАЯ СИСТЕМА: EXT4 НА UBUNTU, XFS НА ROCKY
=========================================================================

Файл files/13_storage_lvm/04_filesystem.yml:

  ---
  # 04_filesystem.yml — практика 13, шаг 6: файловая система на логическом томе.
  # Тип файловой системы берётся из переменной по семейству ОС:
  # ext4 на Ubuntu, xfs на Rocky Linux.
  #
  # Запуск из каталога ~/ansible-lab:
  #   ansible-playbook 04_filesystem.yml

  - name: "Файловая система на логическом томе"
    hosts: linux
    become: true

    pre_tasks:
      ... include_vars для vars/{{ ansible_os_family }}.yml ...

    tasks:
      ... пакеты: parted, lvm2 и инструменты файловых систем ...

      - name: "Создать файловую систему на логическом томе"
        community.general.filesystem:
          fstype: "{{ storage_fstype }}"
          dev: "/dev/mapper/{{ storage_vg }}-{{ storage_lv }}"
          state: present

ПОЧЕМУ РАЗНЫЕ ФАЙЛОВЫЕ СИСТЕМЫ. ext4 — привычная файловая система
Ubuntu, xfs — файловая система по умолчанию в семействе RedHat:
на Rocky Linux ставить на данные что-то другое означает идти против
поддержки. Различие спрятано в переменной storage_fstype, а задача
одна и та же, поэтому в плейбуке нет ни одного when.

ЧТО УМЕЮТ ОБЕ, А ЧТО НЕТ:
  * ext4 растёт и уменьшается; уменьшение — только на размонтированной
    файловой системе, командой resize2fs;
  * xfs растёт только смонтированным (xfs_growfs), а уменьшить xfs
    нельзя вообще: только пересобрать файловую систему, потеряв данные;
  * у самого модуля community.general.filesystem есть параметр resizefs:
    true — он растягивает файловую систему на всё устройство. В практике
    расширением занимается lvol: так том и файловая система меняются
    одной задачей.

ЧЕГО НЕ ДЕЛАТЬ: не добавляйте сюда force: true. Этот параметр означает
«создай файловую систему заново, даже если она уже есть»: mkfs
выполняется на каждом прогоне, changed=0 не наступит никогда, а данные
пропадут. Без force модуль проверяет устройство через blkid, видит свою
файловую систему и выходит с changed=false. Если на устройстве файловая
система другого типа, модуль не станет её затирать, а остановится:
это разобрано в секции про поломки.
ПРОВЕРКА: смотрим, что получилось на каждом семействе:

  ansible web1 -b -m ansible.builtin.command -a "blkid /dev/mapper/data-webdata"
  /dev/mapper/data-webdata: UUID="8f2c1d4e-..." TYPE="ext4"

  ansible db1 -b -m ansible.builtin.command -a "blkid /dev/mapper/data-webdata"
  /dev/mapper/data-webdata: UUID="b41d79a0-..." TYPE="xfs"

ЗАЧЕМ ЭТО В РАБОТЕ: тип файловой системы выбирают под задачу, а не по
вкусу. В курсе важно другое — что различие описано переменной, а не
размножено по задачам условиями when.

ШАГ 7. МОНТИРОВАНИЕ: ANSIBLE.POSIX.MOUNT И /etc/FSTAB
=========================================================================

Файл files/13_storage_lvm/05_mount.yml:

  ---
  # 05_mount.yml — практика 13, шаг 7: монтирование и запись в /etc/fstab.
  # state: mounted означает «строка в fstab есть и том смонтирован сейчас».
  #
  # Запуск из каталога ~/ansible-lab:
  #   ansible-playbook 05_mount.yml

  - name: "Монтирование логического тома"
    hosts: linux
    become: true

    pre_tasks:
      ... include_vars для vars/{{ ansible_os_family }}.yml ...

    tasks:
      - name: "Создать точку монтирования"
        ansible.builtin.file:
          path: "{{ storage_mount }}"
          state: directory
          owner: root
          group: root
          mode: "0755"

      - name: "Смонтировать том и записать его в fstab"
        ansible.posix.mount:
          path: "{{ storage_mount }}"
          src: "/dev/mapper/{{ storage_vg }}-{{ storage_lv }}"
          fstype: "{{ storage_fstype }}"
          opts: "{{ storage_mount_opts }}"
          dump: "0"
          passno: "2"
          state: mounted

      - name: "Смонтировать всё, что описано в fstab"
        ansible.builtin.command:
          cmd: mount -a
        changed_when: false

      ... ещё задачи: findmnt по точке монтирования и assert по его выводу ...

ДВА СОСТОЯНИЯ, КОТОРЫЕ ЛЕГКО ПЕРЕПУТАТЬ:
  * state: present — строка есть в /etc/fstab, но сейчас том может быть
    не смонтирован. Так готовят запись заранее, например перед
    перезагрузкой;
  * state: mounted — строка в fstab есть И том смонтирован сейчас.
    Это то, что нужно в практике: состояние «работает»;
  * state: unmounted — строка в fstab остаётся, а том размонтирован;
  * state: remounted — том размонтируется и монтируется заново при
    каждом прогоне. Это действие, а не состояние: в описании состояния
    ему не место.

ОПЦИИ МОНТИРОВАНИЯ. В файле стоит opts: "defaults,noatime".
  * defaults — набор опций по умолчанию: rw,suid,dev,exec,auto,nouser,
    async. Его можно не писать, но с ним видно, что база именно такая;
  * noatime — не обновлять время последнего доступа при чтении файла:
    меньше записей. Выигрыш скромный, и честно об этом сказать:
    с 2009 года ядро и так применяет relatime. noatime — осознанный
    выбор, а не ускорение в два раза;
  * dump: "0" и passno: "2" — поля строки fstab: dump устарел и всегда
    равен 0; passno задаёт порядок проверки при загрузке (0 — не
    проверять, 1 — корень, 2 — остальные).

ПОЧЕМУ ЭТО ВАЖНО ДЛЯ ЗАГРУЗКИ. fstab читается при загрузке. Строка
с несуществующим устройством или с неверным типом файловой системы
приводит к тому, что systemd ждёт устройство и уходит в emergency mode:
машина не загружается. Поэтому fstab проверяют до перезагрузки: сначала
задачей mount -a, затем вручную через findmnt --verify. Модуль
ansible.posix.mount сам проверку в fstab не делает: он пишет строку
и монтирует, а остальные строки файла его не интересуют.

ПРОВЕРКА: смотрим, что том смонтирован и что записано в fstab:

  ansible all -b -m ansible.builtin.command -a "findmnt /srv/data"
  TARGET    SOURCE                    FSTYPE OPTIONS
  /srv/data /dev/mapper/data-webdata  ext4   rw,noatime,relatime

  ansible all -b -m ansible.builtin.command -a "findmnt --verify"
  0 parse errors, 0 errors, 0 warnings

ЗАЧЕМ ЭТО В РАБОТЕ: перед разметкой смотрят не только lsblk, но и
lsscsi, lsof, pvs и vgs: нужно точно знать, чьё это устройство.

  ---
  # 06_resize.yml — практика 13, шаг 8: расширение логического тома

  #
  # resizefs: true заставляет модуль расширить и файловую систему:
  # ext4 — через resize2fs, xfs — через xfs_growfs. Разница инструментов
  # от нас скрыта, но знать её нужно: xfs растёт только смонтированным.
  #
  # Запуск из каталога ~/ansible-lab:
  #   ansible-playbook 06_resize.yml

  - name: "Расширение логического тома и файловой системы"
    hosts: linux
    become: true

    pre_tasks:
      ... include_vars для vars/{{ ansible_os_family }}.yml ...

    tasks:
      - name: "Расширить логический том вместе с файловой системой"
        community.general.lvol:
          vg: "{{ storage_vg }}"
          lv: "{{ storage_lv }}"
          size: "{{ storage_lv_size_extended }}"
          resizefs: true
          shrink: false
          state: present

      ... ещё задача: df -h по точке монтирования после расширения ...

ДВА ИНСТРУМЕНТА, КОТОРЫЕ СКРЫВАЕТ МОДУЛЬ. Модуль lvol видит, что том
стал больше, и, из-за resizefs: true, расширяет файловую систему:
  * ext4 растёт командой resize2fs, и она работает на смонтированной
    файловой системе — это и называется расширением на ходу;
  * xfs растёт командой xfs_growfs, и ей передают точку монтирования,
    а не устройство. Поэтому xfs расширяется только смонтированным.
В плейбуке разницы не видно, а в выводе видна: ext4 показывает в df -h
7.8G, а xfs — 8.0G: так считают сами инструменты.

ВАЖНО: файловая система растёт только до размера устройства. Если
сначала не расширить том, resize2fs и xfs_growfs ответят, что система
уже занимает всё устройство. Порядок один: свободное место — расширить
раздел — pvresize — lvextend — расширить файловую систему.

ПРОВЕРКА: до и после расширения:

  ansible all -b -m ansible.builtin.command -a "df -h /srv/data"

  ... после прогона ...
  /dev/mapper/data-webdata  7.8G   24K  7.5G   1% /srv/data

=========================================================================
ШАГ 10. ГЛАВНОЕ УПРАЖНЕНИЕ: ПОВТОРНЫЙ ПРОГОН С CHANGED=0
=========================================================================

Запустите итоговый плейбук второй раз, ничего не меняя:

  ansible-playbook 07_full_storage.yml

  PLAY RECAP
  db1  : ok=16  changed=0  unreachable=0  failed=0  skipped=1
  web1 : ok=16  changed=0  unreachable=0  failed=0  skipped=1
  web2 : ok=16  changed=0  unreachable=0  failed=0  skipped=1

changed=0 означает, что описание совпало с состоянием машин. Для диска
это самый сложный случай в курсе: у раздела нет имени, и модуль
сравнивает написанное с тем, что ядро сообщает о диске. Сравнивает он
не всё — именно там и теряется идемпотентность.

ШЕСТЬ ПРИЧИН, ПО КОТОРЫМ CHANGED БЫВАЕТ НЕ НУЛЕВЫМ:

  1. ЧИТАЮЩИЕ КОМАНДЫ БЕЗ CHANGED_WHEN. Задача с ansible.builtin.command
     — это всегда «я выполнил команду», то есть changed. lsblk, blkid,
     findmnt, df и mount -a ничего не меняют, поэтому у них стоит
     changed_when: false. Без него changed=0 не получится.

  2. FILESYSTEM С FORCE: TRUE. Модуль создаёт файловую систему заново
     на каждом прогоне: changed всегда, а данные уничтожены. Правильно —
     без force: модуль проверяет устройство через blkid, видит свою
     файловую систему и выходит с changed=false.

  3. РАЗМЕР ТОМА ПРОЦЕНТОМ ИЛИ СО ЗНАКОМ. Значения size: 100%FREE,
     size: +2G, size: -512M в документации community.general.lvol
     названы не идемпотентными: результат считается заново от текущего
     состояния. Нужен точный размер, как в файлах практики: size: 8G.
     Есть и обратная ловушка: если размер меньше текущего, модуль
     пытается уменьшить том и падает с сообщением Sorry, no shrinking
     of webdata without force=true. Поэтому в файлах стоит shrink: false.

  4. PARTED БЕЗ LABEL И ЕГО «НЕПРОВЕРЯЕМЫЕ» ПАРАМЕТРЫ. Тип таблицы
     разделов сравнивается с параметром label, у которого есть значение
     по умолчанию msdos. Если label не указать, а на диске уже GPT,
     модуль переделает таблицу в msdos и уничтожит разделы. Пишите
     label всегда и ровно тот, который нужен. Дальше тоньше: у уже
     существующего раздела модуль сверяет только номер, имя и флаги.
     Параметры part_start, part_end и fs_type применяются при создании
     раздела, а у готового не проверяются. Проверьте это на стенде:
     добавьте в задачу part_end: 5GiB и запустите плейбук дважды —
     второй прогон покажет ok, хотя раздел остался на 10 ГБ. Чтобы
     размер раздела действительно проверялся и при необходимости
     менялся, нужен отдельный параметр resize: true. changed=0 в этом
     случае означает «описание неполное», а не «диск описан точно».

  5. MOUNT СО STATE: REMOUNTED, СЛУЖБЫ СО STATE: RESTARTED, ПАКЕТЫ
     СО STATE: LATEST. Это действия, а не состояния: они выполняются
     при каждом прогоне и всегда дают changed. Нужны state: mounted
     и state: present.

  6. КОМАНДА, КОТОРУЮ СПАСАЕТ ТОЛЬКО WHEN. Задача с partprobe — это
     ansible.builtin.command: сама по себе она сообщает changed
     на каждом прогоне и не знает, изменила ли что-нибудь.
     changed_when: false здесь не годится: команда действительно
     меняет состояние, когда таблицу перечитали. Поэтому в файлах
     практики она помечена when: parted_result.changed и на втором
     прогоне не выполняется вовсе. Уберите when — и changed=0
     пропадёт, хотя диск тот же.

ПРОВЕРКА: найдите, какая задача отчитывается changed, и прочитайте
логику её модуля (ansible-doc -s community.general.parted). changed=0
означает, что все написанные свойства модуль умеет сравнивать;
свойства, которые он не сравнивает, живут в описании как обещание.

ЧЕГО НЕ ДЕЛАТЬ: не добивайтесь changed=0, дописывая changed_when: false
к задаче, которая действительно меняет диск. Отчёт станет красивым,
а описание — ложным: на новой машине диск не будет размечен, а плейбук
скажет, что всё в порядке. Причину (процент вместо размера, force,
state: remounted) ищут, а не прячут.

ВАЖНО: --check не гарантирует, что изменений не будет: модули разметки
и монтирования в этом режиме сообщают «изменится» приблизительно.


=========================================================================
ШАГ 11. ЧТО ОТЛИЧАЕТ РАБОТУ ОТ УЧЕБНОГО ПРИМЕРА
=========================================================================

ПЕРВОЕ: ЦЕНА ОШИБКИ. Ошибка в имени диска в стенде лечится снимком ВМ,
в работе тот же прогон уничтожает данные. Поэтому перед разметкой
смотрят не только lsblk, но и lsscsi, lsof, pvs и vgs.

ВТОРОЕ: ИМЕНА УСТРОЙСТВ. /dev/sdb — не имя, а адрес: в fstab в работе
пишут UUID=... или LABEL=..., а не /dev/sdb1. Мы монтируем
/dev/mapper/data-webdata: имена LVM устойчивы к порядку дисков.

ТРЕТЬЕ: МЕСТО НЕ РАСТЁТ САМО. За свободным местом следят мониторингом
(vgs, df -h), к дискам с данными в fstab добавляют nofail. И помните
про асимметрию: уменьшить xfs нельзя вообще, а ext4 — только в окно
обслуживания.


=========================================================================
ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: Device /dev/sdb1 not found.

  fatal: [web1]: FAILED! => {"changed": false, "msg": "Device /dev/sdb1 not found."}

Так отвечает community.general.filesystem, когда устройства нет. Причина
почти всегда одна: ядро ещё не увидело раздел. Проверяйте по порядку:

  1. Есть ли раздел: lsblk /dev/sdb
  2. Есть ли файл устройства: ls -l /dev/sdb1
  3. Перечитать таблицу: partprobe /dev/sdb
  4. Сверить имя раздела с файлом переменных:
     grep -n storage_partition ~/ansible-lab/vars/Debian.yml

Пункт 4 выполняется на управляющей машине: переменные storage_*
подключает include_vars внутри плейбука, в ad-hoc команде их нет —
debug с var=storage_partition ответит VARIABLE IS NOT DEFINED!.

Если файл появился после partprobe, вернитесь к шагу 4: в задаче
разметки для этого стоит until по lsblk.

ПРОБЛЕМА: '/dev/sdb1' is already used as ext4, use force=true to overwrite

  fatal: [web1]: FAILED! => {"changed": false, "msg": "'/dev/sdb1' is already used as ext4, use force=true to overwrite"}

Причина: на устройстве уже есть файловая система другого типа —
например, storage_fstype поменяли с ext4 на xfs. Проверка: blkid
на разделе и на томе, сравнение вывода со значением storage_fstype.

ЧЕГО НЕ ДЕЛАТЬ: не лечите это параметром force: true: он не разрешит
конфликт, а создаст файловую систему заново и уничтожит данные.

ПРОБЛЕМА: Sorry, no shrinking of webdata without force=true.

  fatal: [web1]: FAILED! => {"changed": false, "msg": "Sorry, no shrinking of webdata without force=true."}

Причина: в задаче указан размер меньше текущего. Так бывает, когда
запускают 03_lvm.yml (6G) после 06_resize.yml (8G), убрав shrink: false.
Фактический размер смотрят через lvs --units g. force: true не решение:
уменьшение тома обрезает файловую систему.

ПРОБЛЕМА: The argument 'part_end' doesn't respect required format /
parted: invalid token

  fatal: [web1]: FAILED! => {"changed": false, "msg": "The argument 'part_end' doesn't respect required format. The size unit is case sensitive.", "err": [10.0, "gb"]}

Причина: размер записан с неверной единицей — 10gb вместо 10GB.
parted принимает B, KB, MB, GB, KiB, MiB, GiB и %, причём регистр букв
важен. Модуль проверяет формат раньше parted; если ошибку вернёт сам
parted, в err будет строка вида parted: invalid token: 10gb.

ПРОБЛЕМА: Error: Partition(s) on /dev/sdb are being used.

  fatal: [web1]: FAILED! => {"changed": false, "msg": "Error while running parted script: ...", "err": "Error: Partition(s) on /dev/sdb are being used."}

Причина: диск занят — с него что-то смонтировано, на нём активны тома
LVM или лежит swap. Порядок проверки: что смонтировано
(findmnt --source /dev/sdb1, lsblk -f /dev/sdb), кто держит файлы
(fuser -vm /srv/data), затем освобождение: umount /srv/data,
lvchange -an data/webdata, vgchange -an data.

При размонтировании можно получить umount: /srv/data: target is busy
или mount: Device or resource busy — это то же самое: сначала находят
процесс, потом размонтируют.

ПРОБЛЕМА: mount: /srv/data: unknown filesystem type 'xfs'.
  mount: /srv/data: unknown filesystem type 'xfs'.
  Чаще на этом месте: mount: /srv/data: wrong fs type, bad option, bad superblock on /dev/mapper/data-webdata, missing codepage or helper program, or other error.

Причина: в fstab и в задаче указан тип, которого на устройстве нет:
файловая система не создана, создана на другом томе или это другой тип.
Проверка: blkid /dev/mapper/data-webdata. Пустой вывод — файловой
системы нет, вернитесь к шагу 6.

ПРОБЛЕМА: /dev/mapper/data-webdata needs to be mounted for XFS operations

  fatal: [db1]: FAILED! => {"changed": false, "msg": "/dev/mapper/data-webdata needs to be mounted for XFS operations"}

Причина: xfs_growfs работает с точкой монтирования, поэтому xfs
расширяется только смонтированным. Та же причина стоит за симптомом
«файловая система не расширилась, потому что том не расширили»: сначала
вырастает том, потом файловая система. Проверки: findmnt /srv/data,
lvs --units g, df -h /srv/data. Если том вырос, а файловая система
нет, дело в порядке задач: mount должен идти до расширения. И отдельно
про уменьшение: xfs не уменьшается вообще, вернуть место можно только
пересборкой файловой системы.

ПРОБЛЕМА: после правки fstab машина не загрузилась

  [FAILED] Failed to mount /srv/data.
  [DEPEND] Dependency failed for Local File Systems.
  You are in emergency mode. After logging in, type "journalctl -xb" ...

Причина: строка в fstab ссылается на устройство, которого при загрузке
нет. С консоли гипервизора: mount -o remount,rw /, закомментировать
строку в /etc/fstab, перезагрузиться, починить описание. Чтобы этого
не случилось, после правки fstab запускают mount -a и findmnt --verify,
и только потом перезагружают машину.

ЧЕГО НЕ ДЕЛАТЬ: не размечайте диск руками по ssh:

  ssh engineer@web1 "sudo parted -s /dev/sdb mklabel gpt mkpart primary 0% 100%"

Способ не идемпотентен: второй запуск mklabel уничтожает таблицу
разделов вместе с данными, а результата никто не проверяет — команда
завершилась без ошибки, и кажется, что всё хорошо. В курсе разметку
делает модуль, перед ней стоят проверки, а после неё — assert.

ПОЧЕМУ ИМЕННО ТАК: файловая система создаётся не командой mkfs через
shell, а модулем community.general.filesystem без force. На повторном
прогоне mkfs либо падает, либо (с ключом -f) пересоздаёт файловую
систему и уничтожает данные; модуль проверяет устройство через blkid
и на существующей файловой системе ничего не делает.

ПОЧЕМУ ИМЕННО ТАК: строку в fstab пишет ansible.posix.mount, а не
lineinfile. Правка через lineinfile ничего не проверяет, и кривая
запись обнаруживается только после перезагрузки, когда машина уже не
поднимается; модуль mount добавляет строку вместе с монтированием,
а до перезагрузки выполняются mount -a и findmnt --verify.

     db1  : ok=16  changed=0  unreachable=0  failed=0  skipped=1

     ansible all -b -m ansible.builtin.command -a "vgs"
     ansible all -b -m ansible.builtin.command -a "lvs --units g"

   На всех трёх узлах группа data и том webdata размером 8.00g;
   у раздела таблица gpt и флаг lvm (parted /dev/sdb unit MiB print).

4. Файловая система своя на каждом семействе:

     ansible web1 -b -m ansible.builtin.command -a "blkid /dev/mapper/data-webdata"
     ansible db1  -b -m ansible.builtin.command -a "blkid /dev/mapper/data-webdata"

   На web1 и web2 — TYPE="ext4", на db1 — TYPE="xfs".

5. Том смонтирован, записан в fstab, и fstab проверен:

     ansible all -b -m ansible.builtin.command -a "findmnt /srv/data"
     ansible all -b -m ansible.builtin.command -a "mount -a"
     ansible all -b -m ansible.builtin.command -a "findmnt --verify"

   findmnt показывает /dev/mapper/data-webdata и опцию noatime, а
   findmnt --verify отвечает «0 parse errors, 0 errors, 0 warnings».

он понадобится дальше.
