Практика 2. Инвентаризация и подключение клиентов.

ЭТА ПРАКТИКА ПРЕВРАЩАЕТ СПИСОК АДРЕСОВ ИЗ КОМАНДНОЙ СТРОКИ В ФАЙЛ.
Здесь появятся инвентарь, конфигурация Ansible, переменные для групп
и хостов, а вход по паролю на узлах будет запрещён. Все следующие
практики работают с этим инвентарём и к его устройству не возвращаются.


=========================================================================
ЧТО МЫ СДЕЛАЕМ
=========================================================================

Опишем три узла в файле inventory.ini: группы по назначению, группы
по семейству операционной системы и группу, собранную из групп.
Разберём, чем имя машины отличается от адреса.

Создадим ansible.cfg: семь параметров — inventory, host_key_checking,
remote_user, interpreter_python, stdout_callback, callback_result_format
и forks, — четыре места чтения конфигурации и приоритет между ними.
Перенесём подключение в group_vars и host_vars, чтобы пользователь
и ключ были заданы один раз на парк, а различия между Ubuntu
и Rocky Linux стали переменными, а не условиями.

Посмотрим на инвентарь глазами Ansible, отключим вход по паролю
и проверим подключение модулем ansible.builtin.ping. Обзорно, без
практики, разберём Windows и сетевые устройства: подробно это
в приложении app_3_windows_network.txt.

В конце научимся выбирать машины шаблонами: по имени группы, по маске,
пересечением и исключением.

=========================================================================
ШАГ 1. ИНВЕНТАРЬ: СПИСОК МАШИН ОТДЕЛЬНО ОТ КОМАНД
=========================================================================

В практике 1 список машин жил прямо в командной строке:

  ansible all -i '10.0.2.11,10.0.2.12,10.0.2.13' -m ansible.builtin.ping

Так можно один раз проверить пару машин. Для работы это не годится:
список пришлось бы набирать в каждой команде, его нельзя положить
в систему контроля версий и нельзя приложить к описанию задач.
Инвентарь (inventory) — это список машин Ansible, записанный в файл.
В нём три сущности: машины (хосты), к которым Ansible подключается;
группы — именованные наборы машин; переменные, привязанные к машине
или к группе. Инвентарь бывает статический (файл, который правит
человек — он у нас) и динамический (скрипт или плагин, который
отдаёт список машин сам; об этом в практике 16).

ПОЧЕМУ ИМЕННО ТАК: YAML удобнее, когда структура вложенная — пять
уровней подгрупп и переменные у каждой. У нас структура плоская:
три машины и пять групп. В INI она видна целиком на одном экране,
и это важнее гибкости, которая здесь не нужна. Вырастет инвентарь —
YAML можно взять в любой момент: в одном запуске разрешено указать
оба файла, каждый разберёт свой плагин.

Создадим рабочий каталог курса:

  mkdir -p ~/ansible-lab
  cd ~/ansible-lab
  pwd
  /home/engineer/ansible-lab


=========================================================================
ШАГ 2. ПИШЕМ INVENTORY.INI
=========================================================================

  cat > inventory.ini <<'EOF'
  # Инвентарь учебного стенда курса. Формат INI.
  #
  # Слева — имя машины, по которому Ansible её знает. Справа —
  # переменная ansible_host: адрес, по которому идёт подключение.

  [web]
  web1 ansible_host=10.0.2.11
  web2 ansible_host=10.0.2.12

  [db]
  db1 ansible_host=10.0.2.13

  [linux:children]
  web
  db

  [debian:children]
  web

  [redhat:children]
  db
  EOF

ВАЖНО: в тексте практики содержимое файла напечатано с отступом
в два пробела — это отступ текста, а не файла. В самом файле строки
начинаются с первого столбца, и закрывающее слово EOF тоже: иначе
heredoc не закончится, и команда будет ждать ввода.

web1 ansible_host=10.0.2.11 — строка машины. Первое слово — имя,
по которому Ansible знает машину: оно используется в командах,
в шаблонах и в паттернах. ansible_host=10.0.2.11 — переменная этой
машины: адрес, к которому Ansible подключается. Без неё Ansible
подключался бы по имени — на стенде оно разрешается через /etc/hosts
из практики 1; явный адрес надёжнее.

[linux:children] — группа из групп: в секции с :children перечислены
не машины, а группы, которые в неё входят. Так же устроены
[debian:children] и [redhat:children]. Группа all существует всегда
и содержит все машины инвентаря: описывать её не нужно, Ansible
создаёт её сам. Кроме all есть группа ungrouped — машины, не
указанные ни в одной группе; у нас таких нет.

ПОЧЕМУ ИМЕННО ТАК: имя машины и её адрес разделены намеренно.
Адрес меняется — имя остаётся. Когда у web1 сменится адрес, правка
будет ровно в одном месте, а команды, шаблоны и паттерны продолжат
работать: они написаны по именам. Если бы в инвентаре стояли адреса,
шаблон web* перестал бы совпадать вообще.

ПРОВЕРКА: инвентарь работает уже сейчас, без конфигурации:

  ansible all -i inventory.ini -m ansible.builtin.ping
  web1 | SUCCESS => {
      "changed": false,
      "ping": "pong"
  }
  web2 | SUCCESS => { ... "ping": "pong" }
  db1 | SUCCESS => { ... "ping": "pong" }

ВАЖНО: с этого момента адреса машин записаны в одном месте —
в inventory.ini. Если поправить адрес в команде, а не в файле,
следующий запуск вернётся к старому значению.


=========================================================================
ШАГ 3. ANSIBLE.CFG: ФАЙЛ НАСТРОЕК
=========================================================================

Настройки Ansible живут в файле ansible.cfg в рабочем каталоге:

  cat > ansible.cfg <<'EOF'
  # Конфигурация Ansible для каталога ansible-lab.
  # Секция называется [defaults] — во множественном числе.

  [defaults]
  inventory = ./inventory.ini
  host_key_checking = False
  remote_user = engineer
  interpreter_python = auto_silent
  stdout_callback = default
  callback_result_format = yaml
  forks = 10
  EOF

Имя секции здесь — не украшение: Ansible ищет настройки по именам
секций, и секцию [defaults] он знает, а секцию [default] — нет.

ИСПРАВЛЕНО: в прежней версии курса этот файл начинался со строки
[default] — без буквы s на конце. Секцию с таким именем Ansible
не знает: файл он прочитал, знакомых имён в нём не нашёл и оставил
все настройки по умолчанию. Ошибки при этом не было — и это самое
неприятное: ansible --version честно показывал, что файл найден.

  config file = /home/engineer/ansible-lab/ansible.cfg

Проверка одна — спросить у самого Ansible, откуда взято значение:

  ansible-config dump --only-changed | grep -i host_key
  DEFAULT_HOST_KEY_CHECKING(/home/engineer/ansible-lab/ansible.cfg) = False

Теперь по параметрам. inventory = ./inventory.ini — откуда брать
список машин; путь относительный, он отсчитывается от текущего
каталога, поэтому команды выполняются из ~/ansible-lab.
remote_user = engineer — пользователь, под которым Ansible
подключается по умолчанию; в практике 1 мы передавали его флагом -u.
interpreter_python = auto_silent — искать Python на узле самому
и не рассказывать об этом в выводе; в практике 1 в ответе модуля ping
было поле discovered_interpreter_python — результат той самой находки.
forks = 10 — сколько машин обрабатывается одновременно; по умолчанию
их пять, для трёх машин значение роли не играет, но привычка ставить
его осознанно окупается на большом парке.

host_key_checking = False — не проверять ключ узла при подключении:
Ansible не сверяет отпечаток с ~/.ssh/known_hosts и не спрашивает
подтверждения. На стенде это удобно: машины пересобирают, после
переустановки ключ узла меняется, и SSH отказывается подключаться.

ЧЕГО НЕ ДЕЛАТЬ: не переносите host_key_checking = False на рабочие
серверы. Проверка ключа узла защищает от подмены машины: без неё
ключ и пароль уходят тому, кто первым ответил на нужном адресе.
В рабочей среде ключи узлов разносят заранее, например командой
ssh-keyscan, и проверку не отключают.

stdout_callback = default — какой плагин печатает вывод команды
ansible-playbook; default — обычный человекочитаемый вывод, а у ad-hoc
команд (ansible) вывод свой, урезанный, и этот параметр на них
не влияет. callback_result_format = yaml — в каком виде плагин
показывает результат задачи: по умолчанию это json, одна длинная
строка, а yaml читается глазами лучше. Начиная с практики 4
результаты мы будем видеть именно так.

ЧЕГО НЕ ДЕЛАТЬ: не пишите stdout_callback = yaml. Так делали
в прежних версиях: плагин yaml тогда входил в поставку. Сегодня он
из коллекции community.general удалён, и такая строка останавливает
работу:

  ERROR! Invalid callback for stdout specified: yaml

Формат вывода задаётся ключом callback_result_format.

ЧЕТЫРЕ МЕСТА, ОТКУДА ANSIBLE БЕРЁТ КОНФИГУРАЦИЮ. Читается не всё,
что найдено, а только первый файл из списка:

  1. ANSIBLE_CONFIG — переменная окружения, если она задана;
  2. ./ansible.cfg — файл в текущем каталоге;
  3. ~/.ansible.cfg — файл в домашнем каталоге пользователя;
  4. /etc/ansible/ansible.cfg — общесистемный файл.

Порядок и есть приоритет: первый найденный файл выигрывает,
остальные не читаются вообще. Поэтому наш ansible.cfg в ansible-lab
сильнее общесистемного, а переменная ANSIBLE_CONFIG сильнее всех.
И ещё одно правило, которое ловит на ровном месте: переменные
окружения сильнее файла, поэтому ANSIBLE_FORKS=2 перекроет forks = 10.


=========================================================================
ШАГ 4. GROUP_VARS И HOST_VARS: ПОДКЛЮЧЕНИЕ ДЛЯ ГРУППЫ И ХОСТА
=========================================================================

ansible.cfg описывает Ansible целиком. Переменные описывают машины,
и их удобнее держать рядом с инвентарём — в каталогах group_vars
и host_vars: Ansible читает их сам, без единой ссылки в команде.

  mkdir -p group_vars host_vars
  cat > group_vars/all.yml <<'EOF'
  ---
  # Переменные для всех машин стенда: файл читается для каждой
  # группы и каждого хоста инвентаря.

  # Подключение: пользователь engineer и ключ ed25519 из практики 1.
  ansible_user: engineer
  ansible_ssh_private_key_file: /home/engineer/.ssh/id_ed25519

  # Кто отвечает за машину. Для web1 значение переопределено
  # в host_vars/web1.yml.
  lab_owner: не назначен
  EOF

ansible_user и ansible_ssh_private_key_file — переменные подключения.
Ansible берёт их раньше значений из ansible.cfg: переменные сильнее
конфигурации. Поэтому remote_user = engineer и ansible_user: engineer
не спорят, а дополняют друг друга, и пользователя с ключом можно
переопределить для группы или одной машины, не трогая общий файл.

ВАЖНО: держите эти два значения одинаковыми. Разные значения — это
подключение под одним пользователем и долгий разбор вопроса «почему
не тот пользователь». Если пользователь на стенде один, выбирайте
одно место и не дублируйте.

Теперь различия между семействами. Ubuntu и Rocky Linux отличаются
именами служб и пакетов, и эти различия удобно держать переменными:

  cat > group_vars/debian.yml <<'EOF'
  ---
  # Переменные для машин семейства Debian (Ubuntu: web1 и web2).

  # Имена служб и пакетов на Ubuntu отличаются от Rocky Linux.
  ssh_service: ssh
  web_package: apache2
  web_service: apache2
  firewall_package: ufw
  EOF

  cat > group_vars/redhat.yml <<'EOF'
  ---
  # Переменные для машин семейства RedHat (Rocky Linux: db1).

  ssh_service: sshd
  web_package: httpd
  web_service: httpd
  firewall_package: firewalld
  EOF

ПОЧЕМУ ИМЕННО ТАК: каталог группы назван debian, а не ubuntu.
Семейство операционной системы Ansible называет Debian или RedHat,
и группы в инвентаре названы так же — имена файлов совпали
с именами групп. Магии здесь нет: группу можно назвать как угодно,
но тогда и файл придётся называть так же. И это данные, а не условия:
мы не пишем «если Ubuntu, то apache2», мы пишем web_package: apache2
для Debian и web_package: httpd для RedHat. Условия when появятся
в практике 7, и различия между семействами уже будут описаны.

Наконец, переменные одной машины:

  cat > host_vars/web1.yml <<'EOF'
  ---
  # Переменные одной машины: их видит только web1.
  # Остальные узлы берут lab_owner из group_vars/all.yml.

  # Переменные хоста сильнее переменных группы.
  lab_owner: ivan
  EOF

Переменные хоста сильнее переменных группы, а переменные группы all
слабее переменных любой другой группы. Проверим это в шаге 5:
у web1 в lab_owner будет ivan, у web2 и db1 — не назначен.

ЗАЧЕМ ЭТО В РАБОТЕ: в реальном парке у машин одного назначения
почти всё общее, но одна-две всегда выбиваются: другой ключ, другой
пользователь, другой диск. Держать такие отличия в host_vars —
самый дешёвый способ не размножать описание задач под каждую машину.

ВАЖНО: каталоги group_vars и host_vars Ansible ищет рядом
с инвентарём или рядом с плейбуком. У нас и то и другое лежит
в ~/ansible-lab, поэтому файлы находятся сами. Если перенести
inventory.ini в другой каталог, переменные перестанут применяться —
молча, без единой ошибки.


=========================================================================
ШАГ 5. СМОТРИМ НА ИНВЕНТАРЬ ГЛАЗАМИ ANSIBLE
=========================================================================

Файл можно прочитать глазами, но важнее понимать, что из него понял
Ansible. Для этого есть отдельная команда — ansible-inventory.

  ansible-inventory --graph
  @all:
    |--@debian:
    |  |--@web:
    |  |  |--web1
    |  |  |--web2
    |--@linux:
    |  |--@db:
    |  |  |--db1
    |  |--@web:
    |  |  |--web1
    |  |  |--web2
    |--@redhat:
    |  |--@db:
    |  |  |--db1
    |--@ungrouped:

Символ @ отмечает группы, строки без него — машины. Видно главное:
web1 и web2 попали сразу в три группы — web, debian и linux, — а db1
тоже в три: db, redhat и linux. Группа ungrouped пуста. Порядок групп
в выводе зависит от того, как они записаны в файле.

Полный список — в формате JSON:

  ansible-inventory --list
  {
      "_meta": {
          "hostvars": {
              "web1": {
                  "ansible_host": "10.0.2.11",
                  "lab_owner": "ivan",
                  ...
              },
              "web2": { ... },
              "db1": { ... }
          }
      },
      "all": { "children": ["debian", "linux", "redhat", "ungrouped"] },
      "db": { "hosts": ["db1"] },
      "debian": { "children": ["web"] }
  }

Переменные одной машины — то, с чем работает задача:

  ansible-inventory --host web1
  {
      "ansible_host": "10.0.2.11",
      "ansible_ssh_private_key_file": "/home/engineer/.ssh/id_ed25519",
      "ansible_user": "engineer",
      "firewall_package": "ufw",
      "lab_owner": "ivan",
      "ssh_service": "ssh",
      "web_package": "apache2",
      "web_service": "apache2"
  }

Здесь видны сразу и host_vars (lab_owner: ivan), и переменные группы
debian, в которую входит web1. Если запросить db1, ответ будет
другим: firewall_package: firewalld, web_package: httpd.

ПРОВЕРКА: переменная хоста победила групповую:

  ansible-inventory --host web1 | grep lab_owner
      "lab_owner": "ivan",


=========================================================================
ШАГ 6. ПОДКЛЮЧЕНИЕ LINUX: КЛЮЧ, ЗАПРЕТ ПАРОЛЯ, PING
=========================================================================

  ansible all -m ansible.builtin.ping
  web1 | SUCCESS => { ... "ping": "pong" }
  web2 | SUCCESS => { ... "ping": "pong" }
  db1 | SUCCESS => { ... "ping": "pong" }

ansible.builtin.ping — полное имя модуля, FQCN: пространство имён
ansible, коллекция builtin, модуль ping. Полное имя однозначно:
короткое ping может оказаться модулем из другой коллекции, и тогда
выполнится не то, что вы имели в виду. В ad-hoc командах короткие
имена разрешены, но в материалах курса мы пишем полные имена везде;
правило разбирается в практике 4.

ВАЖНО: модуль ping — это не команда ping. Он не отправляет
ICMP-пакеты: Ansible подключается по SSH, запускает на узле Python
и получает в ответ pong. Проверка сети — отдельная задача, например
ansible all -m ansible.builtin.command -a "ping -c1 10.0.2.5".
Недоступный узел даст не «ping не прошёл», а строку UNREACHABLE.

Теперь запретим вход по паролю. Делаем это после того, как вход
по ключу проверен: если ключ не работает, а пароль запрещён,
останется только консоль виртуальной машины. На каждом узле создаём
файл в /etc/ssh/sshd_config.d:

  ssh engineer@web1 'sudo tee /etc/ssh/sshd_config.d/10-lab-nopassword.conf >/dev/null' <<'EOF'
  PasswordAuthentication no
  KbdInteractiveAuthentication no
  EOF

Ту же команду повторите для web2 и db1: содержимое одинаковое для
Ubuntu и Rocky Linux. Проверяем настройку до перезапуска службы:
sshd -t разбирает конфигурацию и молчит, если всё в порядке,
а sshd -T печатает итоговые значения с учётом Include и Match.

  ssh engineer@web1 'sudo sshd -t && sudo sshd -T | grep -i passwordauthentication'
  passwordauthentication no

ПОЧЕМУ ИМЕННО ТАК: файл назван 10-lab-nopassword.conf, а не
99-lab-nopassword.conf. sshd берёт первое найденное значение
параметра, а файлы из Include читает по алфавиту. Файл с именем,
которое идёт после 50-cloud-init.conf, проиграл бы ему: на облачных
образах Ubuntu этот файл ставит PasswordAuthentication yes. Имя
с меньшим числом — не косметика, а работающее решение.

Перезагружаем конфигурацию: на Ubuntu служба называется ssh,
на Rocky Linux — sshd.

  ssh engineer@web1 'sudo systemctl reload ssh'
  ssh engineer@web2 'sudo systemctl reload ssh'
  ssh engineer@db1 'sudo systemctl reload sshd'

ПРОВЕРКА: пароль больше не принимается, а ключ работает.

  ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no engineer@web1
  engineer@web1: Permission denied (publickey).

  ssh -o BatchMode=yes engineer@web1 hostname
  web1

ВАЖНО: после этого перестанет работать ssh-copy-id — он копирует
ключ, заходя по паролю. Ключи для новых учётных записей кладёт
модуль ansible.builtin.authorized_key: им мы займёмся в практике 9.
И помните про Ubuntu: там SSH может работать через сокет, и тогда
активна не служба, а сокет. Если после reload пароль всё ещё
принимается, смотрите systemctl status ssh и ssh.socket,
а затем перезапустите сокет: systemctl restart ssh.socket.

ЧЕГО НЕ ДЕЛАТЬ: не отключайте вход по паролю «заодно» на машинах,
куда у вас один путь. Порядок всегда такой: сначала проверенный
ключ и второй способ попасть на машину — консоль, резервный
пользователь, — и только потом запрет пароля.

=========================================================================
ШАГ 7. WINDOWS: ДРУГОЙ СПОСОБ ПОДКЛЮЧЕНИЯ (ОБЗОРНО)
=========================================================================

Этот шаг и следующий — без практики: машин под них в стенде нет.
Linux-узел отвечает по SSH и имеет Python. У Windows-машины нет
ни того, ни другого в привычном виде: Ansible работает с ней
по WinRM — службе удалённого управления Windows. Меняется не
инвентарь, а способ подключения и набор модулей. Что нужно:

  * на управляющей машине — библиотека pywinrm:
      pip install pywinrm
  * коллекция с модулями:
      ansible-galaxy collection install ansible.windows
  * на самой Windows-машине — включённый WinRM; для учебного
    стенда это делает скрипт ConfigureRemotingForAnsible.ps1.

Инвентарь выглядит привычно (адрес подставьте свой: машины Windows
в стенде курса нет):

  [windows]
  win1 ansible_host=<адрес машины Windows>

  [windows:vars]
  ansible_connection=winrm
  ansible_port=5986
  ansible_winrm_transport=ntlm
  ansible_winrm_server_cert_validation=ignore
  ansible_user=Administrator

  ansible win1 -i windows.ini -m ansible.windows.win_ping

ЗАЧЕМ ЭТО В РАБОТЕ: в российских компаниях парк чаще linux-парк,
поэтому подробно Windows в курсе не разбирается. Но когда его всё же
нужно настраивать, инвентарь, группы и переменные остаются теми же —
меняются модули и способ подключения. Подробно: приложение
app_3_windows_network.txt.


=========================================================================
ШАГ 8. СЕТЕВЫЕ УСТРОЙСТВА: ТА ЖЕ ЛОГИКА, ДРУГОЙ ТРАНСПОРТ (ОБЗОРНО)
=========================================================================

У коммутатора нет Python, и модуль на него не скопировать. Ansible
работает с такими устройствами через подключение network_cli: заходит
по SSH и обменивается текстовыми командами командной строки
устройства. Инвентарь (адрес снова свой — коммутатора в стенде нет):

  [switches]
  sw1 ansible_host=<адрес коммутатора>

  [switches:vars]
  ansible_connection=network_cli
  ansible_network_os=cisco.ios.ios
  ansible_user=admin

Подключение network_cli даёт коллекция ansible.netcommon, а модули —
коллекции под конкретного производителя: cisco.ios, arista.eos,
juniper.junos, community.network:

  ansible-galaxy collection install ansible.netcommon cisco.ios

Пример команды для устройства — тот же шаблон, что и везде:

  ansible sw1 -i switches.ini -m cisco.ios.ios_command -a "commands='show version'"

Ни шаблонов Jinja2, ни фактов в привычном виде здесь нет:
конфигурация устройства — это набор строк, а не файл, который можно
положить на место. Поэтому задачи для сети выглядят иначе. Подробно:
приложение app_3_windows_network.txt.


=========================================================================
ШАГ 9. ШАБЛОНЫ ХОСТОВ И ГРУПП: ВЫБОР МАШИН
=========================================================================

Ansible умеет выбирать машины шаблонами (patterns) — по имени группы,
по имени машины и по маске. Полезная привычка: сначала посмотреть,
кого выбрал шаблон, и только потом подключаться. Для этого есть
--list-hosts.

  ansible 'web' --list-hosts
    hosts (2):
      web1
      web2

  ansible 'web*' --list-hosts
    hosts (2):
      web1
      web2

Пересечение и исключение. Двоеточие разделяет условия, символ &
оставляет только общее, символ ! убирает:

  ansible 'web:&debian' --list-hosts
    hosts (2):
      web1
      web2

  ansible 'linux:!db1' --list-hosts
    hosts (2):
      web1
      web2

Одиночное исключение тоже работает: '!db1' — это то же самое,
что 'all:!db1'. Почему шаблон в кавычках: символ & в оболочке
означает запуск команды в фоне, а ! — обращение к истории команд.

  ansible all --limit 'web:&debian' -m ansible.builtin.ping
  web1 | SUCCESS => { ... "ping": "pong" }
  web2 | SUCCESS => { ... "ping": "pong" }

  ansible all --limit '!db1' -m ansible.builtin.ping
  ...две строки SUCCESS: web1 и web2

ВАЖНО: шаблон ищет имя из инвентаря, а не адрес. Команда
ansible '10.0.2.11' --list-hosts не найдёт ничего: 10.0.2.11 — это
значение переменной ansible_host, а не имя машины.

ЗАЧЕМ ЭТО В РАБОТЕ: --limit — это способ запустить описание всего
парка, но применить его к части машин: «прогони на всех, кроме db1»,
«только на новых узлах». Без него пришлось бы заводить отдельный
инвентарь на каждый случай.


=========================================================================
ШАГ 10. СЕМЕЙСТВА ОС: ПЕРЕМЕННЫЕ ВМЕСТО УСЛОВИЙ
=========================================================================

В парке две машины на Ubuntu и одна на Rocky Linux. В шаге 4 мы
записали различия между ними переменными. Посмотрим, что получилось:

  ansible-inventory --host web1 | grep -E 'web_|firewall_'
      "firewall_package": "ufw",
      "web_package": "apache2",
      "web_service": "apache2"

  ansible-inventory --host db1 | grep -E 'web_|firewall_'
      "firewall_package": "firewalld",
      "web_package": "httpd",
      "web_service": "httpd"

Один и тот же запрос, разные значения — и ни одного условия
в задачах. Описание, которое поставит web_package и запустит
web_service, будет работать на обоих семействах без единой строчки
«если»: различие уже выражено данными. Второе применение видно
здесь же: служба SSH называется по-разному, и это тоже переменная —
ssh_service. Одна и та же задача сможет перезагрузить её и на Ubuntu,
и на Rocky Linux.

ПОЧЕМУ ИМЕННО ТАК: так различия между семействами собираются
в двух файлах, а не расползаются по задачам. Практика 7 добавит
условия when — они нужны там, где различие не выражается значением
переменной, например когда набор шагов для семейств разный.

ВАЖНО: не пишите в задачах имя пакета или службы напрямую.
На одном семействе это заработает, на другом — нет, и выяснится
это позже, чем хотелось бы, и не там, где искали причину.

ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: [WARNING]: Unable to parse ... as an inventory source

  [WARNING]: Unable to parse /home/engineer/ansible-lab/inventory.ini as an inventory source
  [WARNING]: No inventory was parsed, only implicit localhost is available

Ansible не нашёл инвентарь по тому пути, который получился, и остался
с одной машиной localhost. Чаще всего дело не в содержимом файла,
а в пути: в ansible.cfg написано inventory = ./inventory.ini, а команда
запущена не из ~/ansible-lab. Проверяйте по порядку:

  1. Где мы находимся и что лежит рядом:

     pwd
     ls -l inventory.ini

  2. Какой файл конфигурации взят и что Ansible видит в инвентаре:

     ansible --version | grep 'config file'
     ansible-inventory --list -i inventory.ini

ПРОБЛЕМА: [WARNING]: Could not match supplied host pattern, ignoring: web3

  [WARNING]: Could not match supplied host pattern, ignoring: web3

Шаблон не совпал ни с одним именем машины или группы. Ansible
не считает это ошибкой: он предупреждает и продолжает работу
с теми машинами, которые совпали. Опасен случай, когда не совпало
ничего: команда «успешно» не делает ничего. Проверяйте:

  1. Что вообще есть в инвентаре:

     ansible-inventory --graph

  2. Кого выбирает шаблон, без подключения к машинам:

     ansible 'web3' --list-hosts

ПРОБЛЕМА: Host key verification failed.

  web1 | UNREACHABLE! => {
      "changed": false,
      "msg": "Failed to connect to the host via ssh: Host key verification failed.",
      "unreachable": true
  }

Узел предъявил ключ, которого нет в ~/.ssh/known_hosts управляющей
машины, или ключ не совпадает с записанным. Так бывает после
пересоздания виртуальной машины: у неё новый ключ узла, а в файле
остался старый. Проверяйте по порядку:

  1. Применилась ли настройка host_key_checking:

     ansible-config dump --only-changed | grep -i host_key
     DEFAULT_HOST_KEY_CHECKING(/home/engineer/ansible-lab/ansible.cfg) = False

     Если в скобках (default) — значение из файла не взято.
     Первое, что смотрим: имя секции в ansible.cfg (шаг 3).

  2. Что записано про этот узел и подключается ли SSH руками:

     ssh-keygen -F web1
     ssh -o StrictHostKeyChecking=no engineer@10.0.2.11 hostname

ПРОБЛЕМА: UNREACHABLE! Failed to connect to the host via ssh

  db1 | UNREACHABLE! => {
      "changed": false,
      "msg": "Failed to connect to the host via ssh: ssh: connect to host 10.0.2.13 port 22: No route to host",
      "unreachable": true
  }

Это не ошибка Ansible: он пересказывает то, что ответил SSH. Причина
либо в сети и службе SSH на узле, либо в параметрах подключения,
которые Ansible взял из инвентаря и переменных. Проверяйте:

  1. Машина отвечает по сети и порт SSH открыт:

     ping -c1 10.0.2.13
     nc -z -w2 10.0.2.13 22

  2. Работает ли обычный вход по ключу:

     ssh -o BatchMode=yes engineer@db1 hostname

  3. Что Ansible подставляет для этой машины:

     ansible-inventory --host db1

ПРОБЛЕМА: [WARNING]:  * Failed to parse ... with yaml plugin

  [WARNING]:  * Failed to parse /home/engineer/ansible-lab/inventory.yml with yaml plugin: YAML inventory has invalid structure, it should be a dictionary, got: <class 'list'>
  [WARNING]: Unable to parse /home/engineer/ansible-lab/inventory.yml as an inventory source

Файл назван .yml, значит, Ansible читает его как YAML, — а внутри
INI-строки или просто список машин без групп. Так бывает, когда
формат меняют на середине работы и переименовывают файл, не меняя
содержимое. Другая, более частая ошибка — YAML в переменных:
сломанный файл group_vars или host_vars отвечает так:

  ERROR! We were unable to read either as JSON nor YAML, these are the errors we got from each:
  JSON: Expecting value: line 1 column 1 (char 0)
  YAML: ...

  1. Какой файл не читается — он назван в тексте ошибки.

  2. Совпадают ли расширение и содержимое: в файле .ini не должно
     быть YAML-отступов, а в файле .yml — секций в квадратных
     скобках.

  3. Двоеточия внутри значений берутся в кавычки, табуляций в YAML
     быть не должно вообще:

     lab_owner: "engineer: сменный"
     grep -Pn "\t" group_vars/all.yml

ПРОБЛЕМА: одна и та же машина записана в инвентаре несколько раз

Пример из прежней версии курса: хост linux1 стоял в файле трижды —
казалось, что «так надёжнее». Причина: повторная строка не создаёт
вторую машину. Ansible добавляет того же хоста и перезаписывает его
переменные значениями из повторной строки. Пока строки одинаковые,
вреда нет; как только в одной из них окажется другой адрес, победит
последняя — молча, и в выводе ошибки не будет. Проверяйте:

  1. Дубликаты строк в файле (пустой вывод — повторов нет):

     grep -v '^#' inventory.ini | grep -v '^$' | sort | uniq -d

  2. Сколько машин видит Ansible — должно быть ровно три:

     ansible linux --list-hosts

ИСПРАВЛЕНО: в прежней версии курса инвентарь выглядел так:

  [linux]
  linux1 ansible_host=10.0.2.11
  linux1 ansible_host=10.0.2.11
  linux1 ansible_host=10.0.2.11

Смысл был в другом: одна машина играла все роли сразу, поэтому её
и «размножили». В новой версии роли разведены по группам: web и db —
назначение, debian и redhat — семейство, linux — всё вместе.
