=========================================================================
ШАГ 1. ГДЕ ANSIBLE ИЩЕТ РОЛИ
=========================================================================

Ansible не ищет роль по всему диску. Места поиска перечислены
в документации в таком порядке:

  1. внутри коллекций, если коллекции используются;
  2. каталог roles/ в том же каталоге, где лежит плейбук;
  3. каталоги из параметра roles_path — слева направо;
  4. каталог, в котором лежит сам файл плейбука.

Значение roles_path по умолчанию:

  ~/.ansible/roles:/usr/share/ansible/roles:/etc/ansible/roles

Именно поэтому роль, поставленная командой ansible-galaxy role install
без всяких настроек, потом находится: она попадает в ~/.ansible/roles.
Настроить путь можно параметром roles_path в ansible.cfg или
переменной окружения ANSIBLE_ROLES_PATH: файл в текущем каталоге
сильнее ~/.ansible.cfg, а переменная окружения сильнее файла.

ВАЖНО: значение из ansible.cfg ЗАМЕНЯЕТ список по умолчанию, а не
дополняет его. Если написать roles_path = ./roles, каталог
~/.ansible/roles перестанет участвовать в поиске, и роли,
поставленные раньше без настроек, «пропадут». Поэтому в проекте
практики перечислены все нужные каталоги.

ПРОВЕРКА: посмотрите, что Ansible видит сейчас, до правки ansible.cfg:

  ansible-config dump | grep -i roles_path
  DEFAULT_ROLES_PATH(default) = ['/home/engineer/.ansible/roles', '/usr/share/ansible/roles', '/etc/ansible/roles']

ШАГ 2. ПРОЕКТ ПРАКТИКИ: ANSIBLE.CFG И ИНВЕНТАРЬ
=========================================================================

Собираем отдельный проект, чтобы не ломать проект практики 10:

  mkdir -p ~/ansible-lab/15_galaxy/roles
  cp -r ~/ansible-lab/10_roles/roles/web_admin ~/ansible-lab/15_galaxy/roles/
  cp -r files/15_galaxy_collections/. ~/ansible-lab/15_galaxy/
  cp ~/ansible-lab/10_roles/inventory.ini ~/ansible-lab/15_galaxy/
  cp ~/ansible-lab/10_roles/site.yml ~/ansible-lab/15_galaxy/
  cp -r ~/ansible-lab/10_roles/group_vars ~/ansible-lab/15_galaxy/
  cd ~/ansible-lab/15_galaxy

Порядок команд важен: сначала копируется роль из практики 10, потом
поверх неё ложится каталог из files/ — он добавляет в роль два файла,
meta/argument_specs.yml и README.md.

site.yml и group_vars тоже берутся из проекта практики 10, и это не
«на всякий случай». Роль без плейбука не запустить, а проверка
аргументов в шаге 13 делается прогоном site.yml: мы передадим роли
значение через -e и посмотрим, что скажет проверка. group_vars нужен,
чтобы play работал с теми же значениями, что в практике 10. Своей
копии этих двух файлов в каталоге курса нет: site.yml и group_vars
уже напечатаны и разобраны в практике 10.

site.yml вызывает нашу роль web_admin: apache2 на web1 и web2
и httpd на db1, то есть порт 80. С nginx из практики 12, который
слушает 8080, он не спорит.

Настройки проекта — файл ansible.cfg из files/15_galaxy_collections
(пояснения в его комментариях повторяют то, что сказано в шаге 1):

  [defaults]
  inventory = ./inventory.ini
  host_key_checking = False
  remote_user = engineer
  interpreter_python = auto_silent
  stdout_callback = default
  callback_result_format = yaml
  forks = 10

  # Значение из ansible.cfg заменяет список по умолчанию целиком.
  # Первый каталог — ещё и место установки: роль из Galaxy ляжет
  # в ./galaxy_roles.
  roles_path = ./galaxy_roles:./roles:/usr/share/ansible/roles

  # ansible-galaxy дописывает к этому пути каталог ansible_collections,
  # поэтому установка пойдёт в ./collections/ansible_collections.
  collections_path = ./collections:/usr/share/ansible/collections

Три каталога в roles_path — это не «на всякий случай». ./galaxy_roles
отведён ролям из Galaxy: именно туда их ставит ansible-galaxy.
./roles — своим ролям, здесь лежит web_admin из практики 10.
/usr/share/ansible/roles — ролям, поставленным пакетами операционной
системы; он понадобится в шаге 12 для системной роли.

ПОЧЕМУ ИМЕННО ТАК: можно было ничего этого не писать и брать готовое
из ~/.ansible. Мы перечисляем пути явно, потому что тогда на вопрос
«почему не нашлось» отвечает один файл проекта, а не догадки о том,
что лежит в домашнем каталоге у соседа.

ШАГ 3. REQUIREMENTS.YML: РОЛИ И КОЛЛЕКЦИИ ОДНИМ ФАЙЛОМ
=========================================================================

Файл requirements.yml описывает, что нужно скачать с Galaxy. Он один
на проект: ключ roles — роли, ключ collections — коллекции.

  roles:
    # Готовая роль веб-сервера nginx. Для ролей ansible-galaxy понимает
    # только точную версию: диапазоны он для ролей не поддерживает.
    - name: geerlingguy.nginx
      version: "3.1.4"

  collections:
    # ansible.posix — модули firewalld, sysctl, mount. Нужна своей роли
    # web_admin и практике 13. Запись ниже читается так: «не ниже 1.5.4
    # и ниже 2.0.0». Верхняя граница страхует от мажорного обновления.
    - name: ansible.posix
      version: ">=1.5.4,<2.0.0"

    # community.general — модули ufw, lvg, lvol. Курс использует её
    # в практиках 9, 10 и 13. Здесь только нижняя граница: мажорные
    # версии выходят вместе с ansible-core, и курс на них рассчитан.
    - name: community.general
      version: ">=8.0.0"

    # ansible.netcommon — подключение к сетевым устройствам
    # (network_cli). В стенде не применяется, разбор — приложение 3.
    - name: ansible.netcommon
      version: ">=5.0.0"

    # Системные роли RHEL лежат на Automation Hub, а не на Galaxy,
    # и требуют токен, поэтому строка закомментирована (шаг 12).
    #
    # - name: redhat.rhel_system_roles
    #   version: ">=1.21.0"
    #   source: https://console.redhat.com/api/automation-hub/

Что здесь важно понять:

  * роль и коллекция описываются одинаково: name плюс version;
  * поле source задаёт другой сервер, если коллекция лежит не на
    galaxy.ansible.com, а, например, на Automation Hub;
  * ставить оба типа вместе умеет команда без уточнения типа:
    ansible-galaxy install -r requirements.yml. Команды
    ansible-galaxy role install -r и collection install -r берут
    из того же файла только своё;
  * точная версия нужна, когда важна воспроизводимость: тот же файл
    через год поставит то же самое. Диапазон нужен, когда важна
    совместимость: «подойдёт любая версия не старше такой-то».
    Для ролей Galaxy диапазоны не поддерживает — только для
    коллекций.

ЧЕГО НЕ ДЕЛАТЬ: не оставляйте version пустым «пока, для скорости».
Без версии вы получаете не «ту же роль», а «самую свежую роль»,
и разбираться, почему вчерашний плейбук сегодня упал, придётся
с нуля. Это правило одинаково верно и для ролей, и для коллекций.

ПРОВЕРКА: файл разбирается как YAML:

  python3 -c "import yaml; print(yaml.safe_load(open('requirements.yml'))['roles'])"
  [{'name': 'geerlingguy.nginx', 'version': '3.1.4'}]

ШАГ 5. ГОТОВАЯ РОЛЬ: GEERLINGGUY.NGINX И ПОРТ 8080
=========================================================================

В практике 10 мы написали свою роль веб-сервера. Теперь возьмём
готовую: geerlingguy.nginx. Она ставит nginx и ведёт его
конфигурацию; подробности — в README роли, который лежит рядом
с её задачами в galaxy_roles/geerlingguy.nginx.

Плейбук из files/15_galaxy_collections/01_galaxy_role.yml:

  - name: nginx из Galaxy на машинах группы web
    hosts: web
    become: true
    gather_facts: true

    vars:
      # Документированные переменные роли geerlingguy.nginx.
      # nginx_remove_default_vhost убирает виртуальный хост, который
      # пакет nginx ставит сам: тот слушает порт 80 и мешает apache2.
      nginx_remove_default_vhost: true
      nginx_service_state: started
      nginx_service_enabled: true

      # Свой виртуальный хост: слушает 8080 и отдаёт ту же страницу,
      # что и apache2, — каталог /var/www/html из практики 10.
      nginx_vhosts:
        - listen: "8080 default_server"
          server_name: "{{ inventory_hostname }}"
          root: "/var/www/html"
          index: "index.html"
          filename: "lab-8080.conf"

    tasks:
      # Роли выполняются до задач play, поэтому правило ufw добавляется
      # уже после запуска nginx. Порт SSH открыт ролью web_admin ранее.
      - name: Открыть порт 8080 в межсетевом экране
        community.general.ufw:
          rule: allow
          port: "8080"
          proto: tcp

    roles:
      - role: geerlingguy.nginx

Комментарии в начале файла повторяют сказанное здесь: переменные
взяты из README роли, а порт 8080 выбран из-за занятого порта 80.

ПОЧЕМУ ИМЕННО ТАК: список nginx_vhosts взят из документации роли,
а не придуман. Своя роль отзывалась бы на переменную web_admin_port,
но у чужой роли свои имена, и угадать их нельзя. Правило простое:
ищем в README роли раздел Role Variables и работаем только с тем, что
там написано. Нет нужного параметра — берём другую роль или пишем
свою.

ЗАЧЕМ ЭТО В РАБОТЕ: конфликт портов — типовая причина падения готовой
роли на машине, где уже что-то работает. Роль при этом исправна: она
ставит nginx с той конфигурацией, которую вы ей дали. Смотрим не на
роль, а на занятые порты машины.

  ansible-playbook 01_galaxy_role.yml

  PLAY [nginx из Galaxy на машинах группы web]

  ...задачи роли geerlingguy.nginx (пакет, конфигурация, виртуальный
  хост, служба), затем правило ufw: роли идут до задач play.

  PLAY RECAP
  web1 : ok=12 changed=9 unreachable=0 failed=0
  web2 : ok=12 changed=9 unreachable=0 failed=0

Play идёт по группе web, поэтому в отчёте обе машины, а не только
web1. Число задач внутри готовой роли зависит от её версии: ok у вас
может быть другим.

Оба веб-сервера отвечают и отдают одну страницу:

  curl -s http://10.0.2.11:8080 | grep '<h1>'
  curl -s http://10.0.2.11 | grep '<h1>'
    <h1>Веб-узел учебного стенда Ansible</h1>

nginx на 8080 и apache2 на 80 отдают один каталог /var/www/html:
чужая роль встала рядом со своей и не сломала её. Второй прогон
плейбука даёт changed=0 — и у задач роли, и у правила ufw.

ПРОВЕРКА: если changed не ноль, найдите в выводе задачу со строкой
changed: [имя] — она и есть причина.

ШАГ 6. СВОЯ РОЛЬ ИЛИ ГОТОВАЯ: ПРАВИЛО ВЫБОРА
=========================================================================

Теперь у нас два веб-сервера и две роли. Сравним их по одному
признаку: сколько работы делает каждая и кто за неё отвечает.

  * своя роль web_admin: восемь задач, шаблон страницы, обработчик.
    Пишем сами, потому что нужен именно наш сайт, наш владелец
    машины на странице и наши имена переменных;
  * готовая geerlingguy.nginx: ставит nginx, ведёт конфигурацию,
    умеет виртуальные хосты и upstream. Пишем не мы, но отвечает
    за неё автор роли: обновления, совместимость с новыми версиями
    ОС, разбор ошибок.

Правило выбора, которым пользуются в работе:

  * БЕРЁМ ГОТОВОЕ, если роль делает ровно то, что нужно, и её кто-то
    поддерживает: обновляет под новые версии ОС, отвечает на вопросы,
    принимает исправления. У готовой роли есть версии, README
    и история изменений — значит, её поведение предсказуемо;
  * ПИШЕМ САМИ, если нужен контроль над поведением: свои шаблоны,
    свои права, свой порядок задач, своя логика по семействам ОС.
    Готовая роль с десятками переменных ради двух задач — лишняя
    зависимость и лишний повод разбираться в чужой логике.

ЗАЧЕМ ЭТО В РАБОТЕ: взять роль с Galaxy — значит взять на себя её
обновления и её ошибки. Поэтому у роли в проекте должна быть
закреплённая версия и понятное назначение, иначе через год никто
не вспомнит, зачем она здесь.

ЧЕГО НЕ ДЕЛАТЬ: не копируйте чужую роль в проект и не правьте её
«под себя» под своим именем. Так теряются обновления, а ошибка
в правке становится вашей, хотя выглядит как чужая. Нужно другое
поведение — используйте документированные переменные роли либо
напишите свою.

ШАГ 7. СВОЙ СКЕЛЕТ РОЛИ: --ROLE-SKELETON
=========================================================================

В практике 10 роль создавалась командой ansible-galaxy role init
с готовым набором каталогов. Этот набор можно заменить своим: в
команде есть ключ --role-skeleton. В скелете лежат те же файлы, что
появятся в новой роли, но с расширением .j2: такие файлы Ansible
рендерит как шаблоны Jinja2 и отбрасывает расширение.

Заготовка лежит в files/15_galaxy_collections/skeleton. Вот её
описание роли — файл skeleton/meta/main.yml.j2:

  galaxy_info:
    role_name: "{{ role_name }}"
    author: "{{ author }}"
    description: "{{ description }}"
    company: "{{ company }}"
    license: "{{ license }}"
    min_ansible_version: "{{ min_ansible_version }}"

    platforms:
      - name: Ubuntu
        versions:
          - all
      - name: EL
        versions:
          - all

    galaxy_tags:
      - lab

  dependencies: []

Строковые значения взяты в кавычки намеренно: описание роли вполне
может содержать двоеточие с пробелом, а без кавычек YAML на этом
ломается. Имена переменных role_name, author, license и остальные
подставляет сама команда role init.

Второй файл заготовки — skeleton/README.md.j2: шапка README
с подстановками role_name, description, author и license, а ниже
разделы Requirements, Role Variables, Dependencies, Example Playbook,
License и Author Information, каждый с подсказкой, что в нём писать.

Создаём роль по своему скелету:

  cd ~/ansible-lab/15_galaxy
  ansible-galaxy role init --role-skeleton=./skeleton my_role
  - Role my_role was created successfully

  find my_role -type f | sort
  my_role/README.md
  my_role/meta/main.yml

ВАЖНО: у шаблона отбрасывается только расширение .j2. Поэтому файл
в скелете назван README.md.j2, а не README.j2: во втором случае
в роли появился бы файл README без расширения, и Galaxy не показал
бы его как описание роли.

ПОЧЕМУ ИМЕННО ТАК: свой скелет — способ договориться о стандарте
в команде. В заготовку кладут то, что должно быть в каждой роли:
структуру README, поля galaxy_info, заготовку argument_specs. Новая
роль получается уже оформленной, а не «допишем документацию потом».

ЧЕГО НЕ ДЕЛАТЬ: не заменяйте своим скелетом штатный. Ключ
--role-skeleton указывают явно и только там, где он нужен: иначе
новая роль потеряет каталоги tasks, handlers, defaults и vars,
и вызов роли будет молча ничего не делать.

ПРОВЕРКА: своей роли пока нет ни задач, ни обработчиков — она
и не должна ничего делать. Убедитесь, что Ansible её находит:

  ansible-galaxy role list | grep my_role
  # /home/engineer/ansible-lab/15_galaxy/roles
  - my_role, (unknown version)

=========================================================================
ШАГ 8. КОЛЛЕКЦИИ: УСТАНОВКА, СПИСОК, ПРОВЕРКА, --FORCE
=========================================================================

Коллекция — это набор модулей, плагинов и ролей в одном пакете.
Пространство имён (namespace) стоит в имени первым: ansible.posix,
community.general, ansible.netcommon. Первое слово — кто отвечает
за содержимое, второе — что внутри.

  ansible-galaxy collection install community.general
  ansible-galaxy collection install 'community.general:>=8.0.0,<12.0.0'
  ansible-galaxy collection install -r requirements.yml
  ansible-galaxy collection install community.general --force
  ansible-galaxy collection install community.general --upgrade

Двоеточие с диапазоном в командной строке берётся в кавычки: знаки
больше и меньше оболочка понимает по-своему.

  ansible-galaxy collection list

  # /home/engineer/ansible-lab/15_galaxy/collections/ansible_collections
  Collection        Version
  ----------------- -------
  ansible.netcommon 6.1.0
  ansible.posix     1.7.0
  community.general 11.4.0

Проверка целостности установленного — команда verify: она сравнивает
контрольные суммы файлов на диске с тем, что записано
в MANIFEST.json коллекции, и при необходимости сверяется с сервером.

  ansible-galaxy collection verify community.general
  ansible-galaxy collection verify community.general --offline

Ключ --offline проверяет только локальные файлы, без обращения
к Galaxy. Коллекцию, поставленную из каталога или из git, так
не проверить: для неё в MANIFEST.json нет данных о сервере.

ЧТО ЗНАЧИТ --FORCE. Две версии одной коллекции рядом ужиться
не могут: Ansible загрузит ровно одну. Поэтому переустановка другой
версии — это замена:

  ansible-galaxy collection install 'community.general:11.4.0' --force

Без --force команда скажет, что коллекция уже установлена, и ничего
не тронет. У ролей поведение похожее, но своё сообщение:

  [WARNING]: - geerlingguy.nginx (3.1.4) is already installed - use --force to change version to 3.0.0

ПОЧЕМУ ИМЕННО ТАК: --force нужен не «чтобы точно поставилось»,
а чтобы сознательно заменить версию. Ставить с --force в скрипте
всегда нельзя: это стирает разницу между «версия уже правильная»
и «поставили заново, потому что не разобрались».

ВАЖНО: коллекция, поставленная вручную, не обновляется вместе
с пакетом ansible. Обновить её может только ansible-galaxy — ключом
--upgrade или повторной установкой точной версии. В рабочем проекте
для этого и держат requirements.yml.

=========================================================================
ШАГ 9. FQCN: ПОЧЕМУ ПОЛНОЕ ИМЯ НАДЁЖНЕЕ КОРОТКОГО
=========================================================================

Модуль можно назвать коротко, а можно полным именем (Fully Qualified
Collection Name) — с пространством имён и коллекцией:

  ufw                     короткое имя
  community.general.ufw   полное имя

Короткое имя работает, пока коллекция ровно одна. Как только
в проекте оказываются две коллекции с одинаковым модулем, Ansible
выбирает первую по своему порядку поиска, и плейбук начинает вести
себя по-разному на разных машинах. Ошибки при этом нет: задача
выполняется, просто не тем модулем.

Полное имя однозначно: коллекция названа, значит вопрос «чей модуль»
не возникает ни у Ansible, ни у читателя. В курсе полные имена
используются везде — в том числе в своей роли web_admin, где стоят
community.general.ufw и ansible.posix.firewalld.

ЗАЧЕМ ЭТО В РАБОТЕ: в большом проекте коллекций десятки, и часть
имён совпадает. Правило «в плейбуках и ролях — только FQCN»
проверяется линтером (практика 16) и снимает целый класс загадочных
расхождений между стендом и рабочим контуром. Короткие имена
остаются только в ad-hoc командах, где писать ansible.builtin.
в каждой строке бессмысленно.

=========================================================================
ШАГ 10. REQUIREMENTS.MIN.YML: МИНИМАЛЬНЫЙ НАБОР
=========================================================================

Второй файл требований описывает не «что нам интересно», а «без чего
не живёт стенд». Это удобно для изолированного контура и для
проверки в CI, где лишние загрузки — потерянное время.

  collections:
    - name: ansible.posix
      version: ">=1.5.4,<2.0.0"

    - name: community.general
      version: ">=8.0.0"

  ansible-galaxy collection install -r requirements.min.yml

Готовых ролей из Galaxy в этом файле нет: роль nginx — учебный
пример, а не зависимость стенда. И самого ansible-core здесь быть
не может: ansible-galaxy умеет ставить только роли и коллекции,
а движок ставится pip в виртуальное окружение (практика 1).

В больших проектах встречается и третье имя — collections/requirements.yml:
файл рядом с каталогом коллекций описывает только коллекции. Смысл тот же:
один файл и закреплённые версии, только без ролей.

ЗАЧЕМ ЭТО В РАБОТЕ: два файла требований — обычная практика.
requirements.yml описывает всё, что нужно проекту, requirements.min.yml
или requirements-prod.yml — узкий список для конкретного контура.
Одинаковые версии в обоих файлах — единственное, что удерживает
стенд и рабочий контур похожими.

=========================================================================
ШАГ 11. ПРОВЕРКА УСТАНОВЛЕННОГО: 03_COLLECTIONS_CHECK.YML
=========================================================================

Смотреть на список коллекций глазами каждый раз неудобно, поэтому
проверим его плейбуком. Файл
files/15_galaxy_collections/03_collections_check.yml:

  - name: Проверить установленные коллекции
    hosts: localhost
    gather_facts: false
    connection: local

    vars:
      required_collections:
        - ansible.posix
        - community.general

    tasks:
      - name: Получить список коллекций в формате JSON
        ansible.builtin.command:
          argv:
            - ansible-galaxy
            - collection
            - list
            - --format
            - json
        register: collections_json
        changed_when: false

      - name: Разобрать ответ в словарь «каталог — коллекции»
        ansible.builtin.set_fact:
          collections_by_path: "{{ collections_json.stdout | from_json }}"

      # dict2items превращает словарь в список пар «ключ — значение»,
      # flatten склеивает списки из всех каталогов: item.0 — полное имя
      # коллекции, item.1 — словарь с версией.
      - name: Собрать пары «коллекция — версия» в один словарь
        ansible.builtin.set_fact:
          collection_versions: >-
            {{ collection_versions | default({}) | combine({ item.0: item.1.version }) }}
        loop: "{{ collections_by_path.values() | map('dict2items') | flatten }}"
        loop_control:
          label: "{{ item.0 }}"

      - name: Показать установленные и нужные коллекции
        ansible.builtin.debug:
          msg: >-
            {{ item }} — {{ collection_versions[item] | default('не установлена') }}
        loop: "{{ required_collections }}"

      - name: Проверить, что все нужные коллекции установлены
        ansible.builtin.assert:
          that:
            - item in collection_versions
          fail_msg: >-
            Коллекция {{ item }} не найдена. Установите её командой
            ansible-galaxy install -r requirements.yml
          success_msg: "{{ item }} {{ collection_versions[item] }}"
        loop: "{{ required_collections }}"

Две вещи, которые здесь стоит заметить. Первая: hosts: localhost вместе
с connection: local — команда ansible-galaxy выполняется на управляющей
машине, а не на узле. Вторая: changed_when: false — модуль
ansible.builtin.command всегда сообщает changed, потому что не умеет
сравнивать состояние; список коллекций ничего не меняет, и мы
говорим об этом Ansible прямо.

  ansible-playbook 03_collections_check.yml

  TASK [Показать установленные и нужные коллекции]
  ok: [localhost] => (item=ansible.posix) => {"msg": "ansible.posix — 1.7.0"}

  TASK [Проверить, что все нужные коллекции установлены]
  ok: [localhost] => (item=ansible.posix) => {"msg": "ansible.posix 1.7.0"}
  ok: [localhost] => (item=community.general) => {"msg": "community.general 11.4.0"}

  PLAY RECAP
  localhost : ok=5 changed=0 unreachable=0 failed=0 skipped=0 rescued=0 ignored=0

ПРОВЕРКА: уберите одну коллекцию из списка required_collections —
плейбук должен упасть на задаче assert с текстом fail_msg, а не
пропустить проверку молча.

=========================================================================
ШАГ 12. СИСТЕМНЫЕ РОЛИ RHEL: ПАКЕТ RHEL-SYSTEM-ROLES
=========================================================================

До сих пор мы брали роли с Galaxy — то есть у сообщества. У системных
ролей RHEL другой источник: их выпускает вендор, они входят в состав
операционной системы и ставятся пакетом. На Rocky Linux пакет
называется rhel-system-roles.

Ставим пакет на Rocky (на Ubuntu его нет и не будет: он собран только
для семейства RedHat):

  ssh engineer@db1
  sudo dnf install -y rhel-system-roles

Роли из пакета ложатся в системный каталог, который мы уже
перечислили в roles_path:

  ls -d /usr/share/ansible/roles/rhel-system-roles.* | head -3
  /usr/share/ansible/roles/rhel-system-roles.certificate
  /usr/share/ansible/roles/rhel-system-roles.selinux
  /usr/share/ansible/roles/rhel-system-roles.timesync

  ansible-galaxy collection list | grep -i rhel

Вторая команда нужна для второго варианта поставки: те же роли
вендор отдаёт коллекцией redhat.rhel_system_roles на Automation Hub.
Если коллекция установлена, роль вызывается полным именем —
redhat.rhel_system_roles.timesync. Проверьте на своей машине, какой
из двух вариантов доступен, и используйте его: имена у них разные,
и угадывать тут нечего.

Плейбук из files/15_galaxy_collections/02_system_role_timesync.yml:

  - name: Синхронизация времени системной ролью timesync
    hosts: redhat
    become: true
    gather_facts: true

    vars:
      # Документированные переменные роли timesync.
      #
      # ВАЖНО: роль ЗАМЕНЯЕТ конфигурацию chrony целиком, а не
      # дополняет её: перечисленные здесь серверы становятся
      # единственными источниками времени на машине.
      timesync_ntp_servers:
        - hostname: 0.ru.pool.ntp.org
          iburst: true
          pool: true
      timesync_min_sources: 1

    roles:
      - role: rhel-system-roles.timesync

    tasks:
      # Роль выполняется до задач play, поэтому chrony уже настроен.
      - name: Показать, с какими источниками работает chrony
        ansible.builtin.command:
          cmd: chronyc sources
        register: chrony_sources
        changed_when: false

      - name: Напечатать список источников времени
        ansible.builtin.debug:
          var: chrony_sources.stdout_lines

  ansible-playbook 02_system_role_timesync.yml

  TASK [Напечатать список источников времени]
  ok: [db1] => {"chrony_sources.stdout_lines": ["MS Name/IP address         Stratum Poll Reach LastRx Last sample", "^* 0.ru.pool.ntp.org            2   6    17    34    -12us[  -45us] +/-   28ms"]}

  PLAY RECAP (сокращённо: показано только то, что относится к делу)
  db1 : changed=2 failed=0

Полную строку PLAY RECAP для системной роли не приводим: внутри неё
своих задач больше, чем в учебной роли web_admin, и их число зависит
от версии пакета rhel-system-roles. В play, кроме роли, всего две
задачи — chronyc sources и печать списка источников. changed=2 —
это работа роли: новый chrony.conf и перезапуск службы.

ЧЕМ СИСТЕМНАЯ РОЛЬ ОТЛИЧАЕТСЯ ОТ РОЛИ С GALAXY:

  * её выпускает вендор и поставляет вместе с операционной системой.
    Значит, версия роли согласована с версией ОС, а не «какая
    попалась на Galaxy»;
  * документация на неё лежит в документации ОС, а не в README
    на GitHub: переменные описаны, поддерживаемые платформы
    перечислены;
  * её тестируют на этой платформе до выпуска. Роль с Galaxy такой
    гарантии не даёт: её проверял автор, и, возможно, только
    на своей версии Ubuntu;
  * обновляется она вместе с системой: dnf update обновит и роль.
    Роль с Galaxy обновляется только через ansible-galaxy.

Цена другой стороны: системная роль меняет конфигурацию по своим
правилам. В комментарии к timesync_ntp_servers сказано главное —
роль заменяет конфигурацию chrony целиком. Прежние серверы времени,
записанные руками, после прогона исчезнут. Это документированное
поведение роли, а не ошибка.

ЧЕГО НЕ ДЕЛАТЬ: не запускайте системные роли «на посмотреть» на
машине, конфигурацию которой не готовы потерять. Это не учебная роль
с одним шаблоном: у неё хватает прав, чтобы переписать настройки
службы целиком.

ПРОВЕРКА: убедитесь, что роль пришла из пакета, а не с Galaxy:

  rpm -q rhel-system-roles
  rhel-system-roles-1.24.0-1.el10.noarch

=========================================================================
ШАГ 13. ДОКУМЕНТИРОВАНИЕ СВОЕЙ РОЛИ
=========================================================================

Роль без документации — это роль, которую нельзя передать. Два файла
закрывают вопрос: meta/argument_specs.yml описывает аргументы так,
что их понимает сам Ansible, а README.md — человек.

Файл roles/web_admin/meta/argument_specs.yml из files/15_galaxy_collections
(начало и два аргумента из десяти; остальные описаны так же):

  # meta/argument_specs.yml — описание аргументов роли web_admin.
  #
  # Файл читает сам Ansible: перед первой задачей роли он подставляет
  # задачу проверки аргументов и сверяет значения с этим описанием.
  # Неверный тип или неизвестный аргумент останавливают прогон
  # с понятным текстом.
  #
  # Значения по умолчанию здесь ПОВТОРЯЮТ defaults/main.yml: само
  # значение Ansible берёт из defaults, а описание нужно, чтобы
  # документация роли (ansible-doc -t role web_admin) была полной.
  #
  # Переменные из vars/main.yml здесь НЕ описаны намеренно: их
  # переопределить нельзя, значит аргументами роли они не являются.
  ---
  argument_specs:
    main:
      short_description: Веб-сервер и учебная страница сайта на Ubuntu и Rocky Linux
      description:
        - Ставит и включает веб-сервер (apache2 на Debian, httpd на RedHat),
          раскладывает страницу сайта из шаблона index.j2 и оформление
          style.css, открывает порт в межсетевом экране.
        - Ветка выбирается по факту ansible_os_family. Нужны коллекции
          ansible.posix и community.general и права root.
      author:
        - engineer
      options:
        web_admin_deploy_site:
          type: bool
          required: false
          default: false
          description: Разворачивать ли страницу сайта. Для группы web значение переопределено в group_vars/web.yml.
        web_admin_port:
          type: int
          required: false
          default: 80
          description: Порт сайта. Его открывает межсетевой экран и проверяет обработчик роли.
        ...
        web_admin_service_state:
          type: str
          required: false
          default: started
          choices:
            - started
            - restarted
            - stopped
          description: Состояние службы веб-сервера. Значение restarted применять не рекомендуется.

Что происходит при ошибке в аргументах:

  * неверный тип значения — роль останавливается до первой задачи
    с текстом Validation of arguments failed;
  * неизвестный аргумент, переданный роли, — тоже остановка: в тексте
    будет список Supported parameters include, то есть перечень
    допустимых имён;
  * переменная, которая лежит в group_vars и в спецификации не
    описана, проверку не проходит и не мешает: спецификация сверяет
    только те имена, которые в ней перечислены.

ПОЧЕМУ ИМЕННО ТАК: типы проверяются с приведением. Значение «8080»
в кавычках — это строка, но она приводится к числу, и проверка
проходит. А «8080/tcp» к числу не приводится, и роль останавливается.
Проверка ловит не «кавычки», а значения, из которых нельзя сделать
то, что нужно роли.

Связь с defaults/main.yml прямая: в спецификацию попадают ровно те
переменные, которые вызывающий вправе задать, то есть переменные
из defaults. Для каждой из них там есть значение по умолчанию, и оно
же указано в описании. Файлы, которые переопределить нельзя
(vars/main.yml), в спецификацию не попадают.

Документация для человека — файл roles/web_admin/README.md из
files/15_galaxy_collections. Он собран по разделам, которые ждут
от роли на Galaxy и в чужом проекте:

  # Роль `web_admin`

  Ставит веб-сервер (`apache2` на Debian, `httpd` на RedHat), включает
  его и оставляет запущенным, раскладывает страницу сайта из шаблона
  `index.j2` и оформление `style.css`, открывает порт сайта и порт SSH
  в межсетевом экране (`ufw` на Ubuntu, `firewalld` на Rocky).

  ## Requirements
  ## Role Variables
  ## Dependencies
  ## Example Playbook
  ## Argument Validation
  ## Idempotence
  ## License
  ## Author Information

  ...в каждом разделе — короткий ответ: что нужно до запуска, какие
  переменные переопределяются, чего роль не умеет, как её вызвать.

Пять разделов здесь обязательные, и вот почему: «что делает» — первое,
что читает человек, ищущий роль для своей задачи; «переменные» — то,
чем роль управляют, и имена без описания бесполезны; «пример вызова» —
то, что копируют в плейбук, и он должен работать как есть;
«зависимости и требования» — коллекции, пакеты, права, без которых
роль падает у первого же читателя; «лицензия и автор» — с кем
говорить, когда роль нужна другая.

ПРОВЕРКА: документация роли видна самому Ansible:

  ansible-doc -t role web_admin
  > WEB_ADMIN    (/home/engineer/ansible-lab/15_galaxy/roles/web_admin)

Проверьте там же, что значения по умолчанию в описании совпадают
с defaults/main.yml: расхождение вводит в заблуждение именно того,
кто читает документацию.

ЧЕГО НЕ ДЕЛАТЬ: не оставляйте README роли заготовкой, которую печатает
ansible-galaxy init: «Role Name, A brief description». По такому файлу
роль в чужой проект никто не возьмёт — непонятно, что она делает,
какие переменные переопределяются и чего она не умеет, а описание
аргументов приходится читать в задачах. Не заменяйте README и пересказом
на занятии: через полгода его не восстановить. И не берите чужую роль
без закреплённой версии: какая версия стоит на стенде, выясняется
только по факту.

ПРОБЛЕМА: ERROR! the role 'geerlingguy.nginx' was not found in ...

  ERROR! the role 'geerlingguy.nginx' was not found in /home/engineer/ansible-lab/15_galaxy/roles:/home/engineer/ansible-lab/15_galaxy/galaxy_roles:/usr/share/ansible/roles

Причин две: роль не установлена или лежит не там, где Ansible её
ищет. Места поиска перечислены в самом сообщении — читайте его
буквально, начиная с первого пути. Проверяйте по порядку: сначала
есть ли роль на диске, потом попадает ли её каталог в список.

  ls -d galaxy_roles/*/ roles/*/ 2>/dev/null
  ansible-config dump | grep -i roles_path
  ansible-galaxy role list

Три частые причины: роль ставили без -r requirements.yml, то есть
в ~/.ansible/roles, а roles_path в ansible.cfg этот каталог больше
не содержит; в requirements.yml стоит другое имя (geerlingguy.nginx
против nginx); роль поставили в каталог, которого нет в roles_path.

ПРОБЛЕМА: конфликт версий коллекций

  ERROR! Failed to resolve the requested dependencies map. Could not guarantee that all requirements are compatible with each other.

Так Ansible отвечает, когда требования противоречат друг другу:
например, одна коллекция требует community.general не ниже 12.0.0,
а диапазон в requirements.yml ограничен версией ниже 12.0.0. Ни одно
решение не удовлетворяет обоим условиям сразу, поэтому установка
прекращается — и это правильное поведение. Проверяйте по порядку:
сначала запустите установку с -vvv и посмотрите, какие версии
требовались; потом ослабьте диапазон в requirements.yml; в последнюю
очередь ставьте конфликтующую коллекцию отдельно.

  ansible-galaxy collection install -r requirements.yml -vvv
  ansible-galaxy collection list | grep -i -e posix -e general

Держать в проекте две версии одной коллекции нельзя: Ansible
загружает ровно одну.

ПРОБЛЕМА: No package rhel-system-roles available.

  web1: No package rhel-system-roles available.

На Ubuntu и Debian та же ситуация выглядит иначе:

  E: Unable to locate package rhel-system-roles

А на Rocky Linux 10 с неподключённым репозиторием или опечаткой
в имени ответ другой:

  Error: Unable to find a match: rhel-system-roles

Пакет собран только для семейства RedHat: RHEL, Rocky Linux,
AlmaLinux. На Ubuntu его нет и не будет — там тот же смысл дают роль
из Galaxy или свой шаблон chrony.conf (практика 12). Проверяйте по
порядку: сначала на какой машине выполняется команда, потом какое
семейство ОС у неё, потом доступен ли пакет в репозиториях.

  cat /etc/os-release | grep -e ^ID -e ^VERSION_ID
  dnf repolist
  dnf search rhel-system-roles
  dnf provides '*/roles/rhel-system-roles.timesync'

Если пакета в репозитории нет, есть два пути: коллекция
redhat.rhel_system_roles с Automation Hub (нужен токен и запись
в requirements.yml с полем source) или коллекция
fedora.linux_system_roles с Galaxy — те же роли, но от сообщества,
без поддержки вендора. Выбирайте осознанно: вместе с коллекцией
вы меняете и того, кто отвечает за результат.

ПРОБЛЕМА: argument_specs отвергает параметр, который выглядит верным

  TASK [web_admin : Validating arguments against arg spec 'main' - Веб-сервер и учебная страница сайта на Ubuntu и Rocky Linux]
  fatal: [web1]: FAILED! => {
      "argument_errors": [
          "argument 'web_admin_port' is of type <class 'str'> and we were unable to convert to int: <class 'str'> cannot be converted to an int"
      ],
      "msg": "Validation of arguments failed:\nargument 'web_admin_port' is of type <class 'str'> and we were unable to convert to int"
  }

Причина не в кавычках, а в значении. Проверка типов в Ansible
приводит значение к нужному типу, поэтому web_admin_port: "8080"
проверку проходит, а web_admin_port: "8080/tcp" или "восемьдесят" —
нет: из них нельзя сделать число. Проверяйте по порядку: сначала
ищите, откуда пришло значение (group_vars, параметры роли,
--extra-vars), потом смотрите ожидаемый тип в спецификации.

  grep -rn 'web_admin_port' group_vars/ roles/web_admin/meta/
  ansible-doc -t role web_admin | grep -A3 web_admin_port

Тот же текст будет и для неизвестного аргумента, но со списком
допустимых имён:

  "msg": "Validation of arguments failed:\nweb_admin_ports. Supported parameters include: web_admin_deploy_site, web_admin_owner, web_admin_port, ..."

Опечатка в имени аргумента — самая частая причина: web_admin_ports
вместо web_admin_port. Спецификация такого имени не знает и сообщает
об этом сразу, не дожидаясь, пока роль отработает наполовину.

ПРОБЛЕМА: роль, вызванная через include_role с vars, «не видит»
свои defaults

  fatal: [web1]: FAILED! => {"msg": "The task includes an option with an undefined variable. The error was: 'web_admin_port' is undefined"}

Причина в области видимости, а не в роли. Значения из defaults/main.yml
и vars/main.yml читаются внутри роли; они не становятся переменными
всего play только потому, что роль их объявила. Поэтому задача play
после include_role, шаблон другого файла или другая роль переменную
web_admin_port не увидят. Проверяйте по порядку: сначала где именно
упала задача — внутри роли или снаружи; потом объявлена ли переменная
в defaults роли или в group_vars проекта.

  ansible-playbook site.yml --list-tasks | grep -n web_admin
  grep -rn 'web_admin_port' group_vars/ roles/web_admin/defaults/

Если переменная нужна снаружи роли, объявите её в group_vars — там
она видна всем. И не путайте это с приоритетом: порядок от слабого
к сильному в объёме курса такой — defaults роли, group_vars, host_vars,
vars плейбука, vars_files, vars роли, параметры роли, set_fact и
register, --extra-vars. Значит, значение, переданное роли параметром,
применяется и побеждает vars/main.yml, а group_vars проигрывает и
параметрам роли, и vars роли. Какое значение дошло до узла, показывает
временная задача с ansible.builtin.debug.

ЧЕГО НЕ ДЕЛАТЬ: не берите чужую роль без версии и не правьте её под
свой стенд прямо в каталоге roles/. Требования к ролям и коллекциям
описывает requirements.yml: имя без версии означает, что повторная
установка через месяц принесёт другую версию. Править чужой код
в проекте тоже нечем: правка теряется при следующей установке.
Всё, что нужно знать о роли, лежит рядом с ней: requirements.yml
с версиями, meta/argument_specs.yml с типами и README.md с примером.
